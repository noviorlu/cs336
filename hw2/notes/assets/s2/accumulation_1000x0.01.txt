s = 0; 重复 1000 次 s += 0.01   正确答案 = 10.0

  s(fp32) += x(fp32)             =  10.0001  ( +0.00%)  

  s(fp16) += x(fp16)             =   9.9531  ( -0.47%)  
  s(fp32) += x(fp16)             =  10.0021  ( +0.02%)  x 自动升到 fp32 再加
  s(fp32) += x(fp16).type(fp32)  =  10.0021  ( +0.02%)  x 手动升到 fp32 再加

  s(bf16) += x(bf16)             =   4.0000  (-60.00%)  
  s(fp32) += x(bf16)             =  10.0098  ( +0.10%)  x 自动升到 fp32 再加
  s(fp32) += x(bf16).type(fp32)  =  10.0098  ( +0.10%)  x 手动升到 fp32 再加

为什么 16 位累加器会错：
  浮点数越大，相邻两个能表示的数之间空隙越大。当空隙比 0.01 还宽，s + 0.01 四舍五入后
  还是 s，这次加法就白做了。
    fp16：s 到 8 以后空隙 0.0078，0.01 勉强比空隙大，每次都被凑整，所以慢慢漂到 9.95
    bf16：s 到 4 以后空隙 0.031，0.01 连空隙一半都不到，直接凑整成 0，卡死在 4.0
  bf16 比 fp16 更糟，因为它把位数拿去换了范围，尾数只剩 7 位（fp16 是 10 位）。

为什么 fp32 累加也不是正好 10：
  浮点数没有「精确」，只有「误差够不够小」。0.01 在二进制里是无限循环小数，任何位宽都存不准：
    fp32 存成 0.0099999998（差 2e-10）   fp16 存成 0.0100021（差 2e-6）   bf16 存成 0.0100098（差 1e-5）
  s(fp32) += x(fp32) 的 +0.0001 来自每次相加的凑整，1000 次攒出来 1e-4，训练里可以忽略。
  s(fp32) += x(fp16) 的 +0.0021 来自 x 出生就偏大 2e-6，fp32 累加器很老实地把它加了 1000 次
  （0.0100021 × 1000 = 10.0021）——升回 fp32 找不回 fp16 已经丢掉的位数。bf16 同理，10.0098。
