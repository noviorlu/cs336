## 1. 从 Unicode 说起

### 1.1 str 和 bytes 是两个层面

```
"café"          ← str：字符（Unicode 码点）的序列
   ↕  encode / decode
b'caf\xc3\xa9'  ← bytes：0–255 的字节序列
```

`encode` 把 str 变成 bytes（按 UTF-8 规则），`decode` 反向，二者互逆。

计算机底层只能存字节（0–255），但字符有 15 万多个，所以需要一套编码规则做映射。这也解释了为什么 `len()` 的结果会变：`len("café")` 是 4（数字符），`len("café".encode())` 是 5（数字节）。

有个小坑：`print(b'caf\xc3\xa9')` 打出来还是 `b'...'`，不会显示成 `café`。bytes 没有"给人看"的形式，想看内容必须显式 `.decode()`。

### 1.2 UTF-8 的变长机制

一个字符占几个字节，由它的码点范围决定：

| 码点范围 | 字节数 | 例子 |
|---|---|---|
| U+0000–U+007F | 1 | ASCII（`c`、`a`、`f`） |
| U+0080–U+07FF | 2 | `é`、`ñ`、希腊/西里尔字母 |
| U+0800–U+FFFF | 3 | 绝大多数常用汉字、假名、韩文 |
| U+10000–U+10FFFF | 4 | emoji、扩展区生僻字（如 `𠮷`） |

这里有个常见误解：**中文不都是 3 字节**。生僻字和扩展区的字在 U+20000 以上，是 4 字节。所以不要记"中文 = 3 字节"，要记「字节数由码点落在哪个范围决定」。

那 UTF-8 怎么做到变长而不产生歧义？靠每个字节的高位前缀自带角色标记（下面的 `x` 是真正承载码点的有效位）：

```
1 字节  U+0000–007F     0xxxxxxx
2 字节  U+0080–07FF     110xxxxx 10xxxxxx
3 字节  U+0800–FFFF     1110xxxx 10xxxxxx 10xxxxxx
4 字节  U+10000–10FFFF  11110xxx 10xxxxxx 10xxxxxx 10xxxxxx
```

`0` 开头是单字节（ASCII），`110`/`1110`/`11110` 开头分别是 2/3/4 字节序列的**首字节**，`10` 开头是**续接字节**。解码器从左往右扫，看一眼首字节前缀就知道后面还要读几个续接字节——这叫自解析。

举个实例，`é` 的码点是 U+00E9，填进 2 字节模板得到 `11000011 10101001`，也就是 `\xc3\xa9`，十进制是 `[195, 169]`。

### 1.3 为什么还有 UTF-16 和 UTF-32

三者都是"码点 → 字节"的编码方案，区别在编码单位的宽度：

| 编码 | 基本单位 | 一个字符占几字节 | 当初的动机 | 现在的定位 |
|---|---|---|---|---|
| UTF-8 | 1 字节 | 变长 1~4 | 兼容 ASCII、省空间、避开 `\x00` | 事实标准（超过 98% 的网页） |
| UTF-16 | 2 字节 | 变长 2 或 4 | 早期以为 2 字节（65536 个）够用，图定长好算 | 遗留：Windows / Java / JS 的内部字符串 |
| UTF-32 | 4 字节 | 定长 4 | 想要真定长、装下所有码点 | 极少用，太浪费 |

拿 "hello" 实测一下：UTF-8 是 `[104,101,108,108,111]`，5 个字节，没有 0；UTF-16 每个字符后面跟一个 0，共 12 字节；UTF-32 每个字符后面跟 3 个 0，共 24 字节。

### 1.4 byte-level BPE 好在哪

所有文本先 `encode("utf-8")` 变成 0–255 的字节，BPE 只在字节层面操作。这带来三个好处：

- **初始词表大小固定是 256**。注意不是 128——UTF-8 流里字节会取到 128–255。
- **永远不会遇到未登录词**。任何字符拆到字节都逃不出 0–255，所以不需要 `<unk>` 这个特殊 token。
- **"某字符占几字节"的复杂度被 UTF-8 这一步完全吸收**，训练算法对此完全透明。

### 1.5 一个常见误解：LLM 说中文时串到韩文/日文，不是因为"字节接近"

这是我在做作业时顺带想清楚的一件事。

LLM 并不在字节层面预测，它在 **token ID** 上预测。中文和日文的 token 在词表里是两个不同的 ID，ID 相邻也没有任何语义关系，所以"字节接近导致混淆"这个解释站不住脚。

真正的原因有四条：

1. 训练数据里 CJK 混杂，导致三者在 **embedding 空间**里互为邻居；
2. 中文高质量数据相对稀疏，采样时容易漂移；
3. 采样本身的随机性；
4. tokenizer 不匹配，中文被切得很碎。

所以直觉需要纠正一下：不是字节接近，而是**向量空间里互为邻居**。字节只是最底层的存储形式，模型根本不在那一层"思考"。这一点和后面 §4.2 讲的"罕见 token 的 embedding 几乎收不到梯度信号"是同一件事的两面——见得多的学得准，见得少的那一行几乎没被更新过。

### 1.6 两道书面题

**理解 Unicode**

`chr(0)` 返回的是空字符（Null character, NUL），ASCII 码值 0。它渲染不出任何字形，不占显示空间，但仍然占一个字符位置；C 语言用它作字符串结束标志。

它的 `repr` 显示成 `'\x00'`（可见的转义形式），而 `print` 出来是空的。原因是 repr 面向调试，要精确无歧义，所以用可见转义把控制字符"显示出来"；print 输出字符本身，而终端渲染不了控制字符。

它出现在文本里的效果是：字符存在但渲染不出来。它不会截断字符串（不像 C 里的 `\0`），`len` 仍然把它计入一个位置。

**Unicode 编码**

*为什么在 UTF-8 字节上训练 tokenizer 优于 UTF-16/UTF-32？* 因为 UTF-8 对常见字符只用 1 字节，字节序列比 UTF-16/32 短得多；更关键的是，UTF-16/32 会插入大量填充的 `\x00`，这些 `\x00` 会成为高频字节对，让 BPE 把有限的合并名额浪费在无意义的填充上，学不到真正有用的子词。

这里有两个措辞坑要避开：不要说"UTF-8 是压缩/最优压缩"（它是编码规则，不是压缩算法）；不要说 BPE 是"聚类"（BPE 是频率驱动的贪心合并，不是 clustering）。

*为什么逐字节 decode 是错的？* 因为非 ASCII 字符在 UTF-8 里由多个字节共同编码，逐字节单独 decode 会把它们切断。例子：`"café".encode("utf-8")` 是 `[99,97,102,195,169]`，前三个 ASCII 字节能各自解码，但到 `\xc3`（195）时，它是 2 字节序列的首字节（二进制 `11000011`，`110` 开头声明后面还有 1 个续接字节），单独解码时续接字节缺失，直接报 `UnicodeDecodeError: unexpected end of data`。

*给一个不能 decode 成任何字符的双字节序列。* 核心是违反 UTF-8 的前缀规则（合法双字节必须是 `110xxxxx 10xxxxxx`）。三种非法方式：

| 例子 | 为什么非法 | 报错关键词 |
|---|---|---|
| `bytes([0xff, 0xff])` | `0xff` = `11111111`，前缀 `11111` 不属于任何合法类别 | invalid start byte |
| `bytes([0x80, 0x80])` | `0x80` = `10000000`，`10` 开头是续接字节标记，不能当开头 | invalid start byte |
| `bytes([0xc3, 0x28])` | 首字节 `0xc3` 是合法的 2 字节头，但 `0x28` 是 ASCII，不是 `10` 开头的续接字节 | invalid continuation byte |

推荐答后两个，因为能体现你理解了"续接字节"这个概念。

## 2. BPE Tokenizer

一句话概括 BPE：**从 256 个字节出发，反复把"最常相邻的 token 对"合并成新 token，直到词表达到目标大小。**

整个训练分三步：

```
① 256 个字节 + 特殊 token          → 初始词表
② 语料 → 按特殊 token 切开 → 正则切分 → 转字节 → 统计 {片段: 出现次数}
③ 循环 { 数所有相邻对 → 选最高频的 → 加入词表并记录 → 全局替换 }
```

产出两样东西：**vocab**（`dict[int, bytes]`，ID 到字节串的映射）和 **merges**（`list[tuple[bytes, bytes]]`，按创建顺序排列的合并规则）。

### 2.1 第一步：初始词表

初始词表 = 全部 256 个字节值（ID 0–255）+ 特殊 token。之后每合并一次，词表加 1。

$$\text{vocab\_size} = \underbrace{256}_{\text{初始字节}} + \text{合并次数} + \text{特殊 token 数}$$

反过来就是：**合并次数 = vocab_size − 256 − 特殊 token 数**。比如 TinyStories 用 `vocab_size=10000` 加 1 个特殊 token，就要合并 9743 次。

三种来源的 token，参不参与合并是不一样的：

| 来源 | 参与合并吗 |
|---|---|
| 256 个字节（初始化） | 参与，是合并的原料 |
| 合并产生的 token | 参与 |
| 特殊 token（人为加入） | **不参与**。它是硬边界，不进入 merge 统计，但占一个 ID |

造字节时有两个坑：`bytes([i])`（**方括号**）才是造一个值为 i 的单字节，`bytes(65)` 得到的是 65 个 `\x00`，`bytes('A')` 直接报错。另外把一个词转成字节要用 `list(token.encode("utf-8"))`——`[ord(c) for c in token]` 得到的是**码点**不是 UTF-8 字节，遇到非 ASCII 就错了。

特殊 token 这次只用到 `<|endoftext|>`。它们的共同本质是：人为定义、永不被拆开、占一个固定 ID 但不参与合并。

不同模型放置特殊 token 的位置不一样（GPT-2 放末尾、Llama 放开头），这纯粹是设计选择。实现时还有一点：接口签名是 `list[str]`，别写死"只有一个"——测试里就有多个特殊 token 的用例。

### 2.2 第二步：预分词

这一步不做任何合并，只是准备一张"片段 → 出现次数"的频率表。顺序很重要：

```
原始语料
→ 先按 special_tokens 切开（要 re.escape，因为 token 里含 | 等正则元字符）
→ 每段用 GPT-2 的正则切成 pre-token
→ 每个 pre-token 转成 UTF-8 字节序列 → 统计次数
```

产物长这样：`(l,o,w): 5`、`(l,o,w,e,r): 2`、`(w,i,d,e,s,t): 3`、`(n,e,w,e,s,t): 6`。

**为什么需要这一步？** 做个思想实验：如果不预分词，直接把整个文本当成连续字节流，你会数到大量跨词边界的字节对。后果有三条：

1. **语义割裂**。`dog`、`dog!`、`dog.`、`dog?` 会变成 4 个毫不相干的 ID，语义几乎一样却各学一份，白白浪费词表格子。
2. **跨词的无意义组合**。像 `e␣t`（横跨两个词）这种纯统计噪声会占掉词表，却学不到任何东西。
3. **效率灾难**。不预分词的话，每一轮要数的对数正比于**语料总字节数**；预分词之后，`the` 出现一百万次也只存一份加一个计数，工作量降到正比于**不同词的个数**，小好几个数量级。

切分的边界主要是空格，另外还有标点、数字/字母切换、英文缩写。要注意切出来的片段**不是最终 token**，它只是划定了合并的作用范围，片段内部仍然会被 BPE 继续切成子词。

GPT-2 用的正则（需要 `regex` 包，标准库 `re` 不支持 `\p{L}` 这种 Unicode 属性）：

```
PAT = r"""'(?:[sdmt]|ll|ve|re)| ?\p{L}+| ?\p{N}+| ?[^\s\p{L}\p{N}]+|\s+(?!\S)|\s+"""
```

六个用 `|` 连起来的选项，从左到右优先匹配：① 英文缩写后缀（`'s`/`'ll`/`'ve`/`'re`）② ` ?\p{L}+` 单词 ③ ` ?\p{N}+` 数字 ④ ` ?[^\s\p{L}\p{N}]+` 标点 ⑤ `\s+(?!\S)` 尾随空白 ⑥ `\s+` 兜底。

两个细节值得注意。一是**前导空格吸附**：选项②开头那个 ` ?` 会把空格吸到词的**前面**，所以 `some text` 里的 `text` 会切成 ` text`。这就是为什么 GPT-2 系模型里 ` the` 和 `the` 是两个不同的 token。二是**选项⑤必须排在⑥前面**：交替是从左到右优先匹配，具体规则要放前面、兜底放后面。

实测一下：`re.findall(PAT, "I'll pay $100 now!!")` 得到 `['I', "'ll", ' pay', ' $', '100', ' now', '!!']`。

**我在预分词里修过两个 bug，关键是 pytest 全绿也抓不到它们：**

| bug | 触发条件 | 后果 | 修法 |
|---|---|---|---|
| `re.split("", chunk)` | 特殊 token 列表为空 | pattern 是空串，等于在每个字符之间都切一刀，pre-token 全被打成单字符 | 空 pattern 时直接返回原串，不做 split |
| 分块边界硬编码 `b"<\|endoftext\|>"` | 特殊 token 不叫这个名字 | 找不到切点，边界全退化到文件末尾，32 个进程变成 1 个，并行完全失效（实测在 `<\|sep\|>` 语料上：修前 1 块、修后 32 块） | 用 `special_tokens[0].encode()`；没有特殊 token 时退化成单块 |

第一条后来在 `encode` 里以另一种形式又出现了一次（切分用的正则为空时要置成 `None`）。**同一个"空集合"边界，两个地方都要防。**

顺带一提，这套正则至今仍是主流骨架。GPT-4 的 `cl100k_base` 最重要的改动是**限制数字长度为 `\p{N}{1,3}`**：`12345` 会被切成 `123` + `45`，这样算术任务更稳定，词表也不会被各种长数字撑爆。

### 2.3 第三步：合并循环

每一轮四个动作，循环到词表满为止：

1. **数所有相邻对**（要加权）：遍历频率表，数每个 pre-token 内部的相邻对，乘以该 pre-token 的出现次数。
2. **选最高频的对**：平局时选**字典序更大**的（这正好是 Python `max` 对 `tuple[bytes, bytes]` 的默认行为）。
3. **记录**：新 token 加入词表拿到下一个 ID，该对追加进 merges 列表。**顺序很重要**，encode 时要按这个顺序重放。
4. **替换**：把所有 pre-token 内的该对合并成单个 token。回到第 1 步。

拿前面那个例子逐帧走一遍：

| 轮次 | 数对（只列关键项） | 选谁 | 为什么 | 替换后 |
|---|---|---|---|---|
| 1 | `(e,s):9  (s,t):9  (w,e):8  (l,o):7  (o,w):7` | `(s,t)` | 和 `(e,s)` 平局，字典序 `s`(0x73) > `e`(0x65) | `(w,i,d,e,st)`、`(n,e,w,e,st)` |
| 2 | **`(e,st):9`** ← 新冒出来的 | `(e,st)` | 最高频 | `(w,i,d,est)`、`(n,e,w,est)` |
| 3 | `(l,o):7  (o,w):7` | `(o,w)` | 平局，`o` > `l` | `(l,ow)`、`(l,ow,e,r)` |

最终 `merges = [(s,t), (e,st), (o,w)]`，词表里多了 `b'st'`、`b'est'`、`b'ow'`。

有两个核心理解：

- 这个循环本质上是**反复修改同一张频率表**：扫表 → 选最高频 → 记录 → 就地合并 → 用改动后的表再来一遍。
- **为什么必须串行**：第 2 轮选中的 `(e,st)` 是第 1 轮合并的**产物**，在第 1 轮之前根本不存在。所以无法提前知道第 2 轮会选谁——**这条依赖链无法打破**。（并行的可能性见 §2.6。）

### 2.4 让它跑得快：五个数据结构 + 三项技术

朴素实现每轮都全量重数所有 pair、重建所有词，复杂度是 $O(\text{轮数} \times \text{语料大小})$。我最终的实现靠五个常驻数据结构协同做**增量维护**：

| 结构 | 类型 | 作用 |
|---|---|---|
| `word_ids` | `list[list[int]]` | 每个词的 id 序列，原地修改（下标就是词的标识，必须稳定） |
| `word_counts` | `list[int]` | 每个词的出现次数，下标对齐 |
| `word_pairs` | `list[dict[pair, int]]` | 每个词内部的 pair → 次数，常驻，用来判断成员关系 |
| `pair_counts` | `Counter` | 每个 pair 的全局加权计数——**这是真相源** |
| `pair_to_words` | `dict[pair, set[int]]` | pair → 含有它的词的下标集合，**增量更新的关键索引** |

前三个是"按词组织"的、后两个是"按 pair 组织"的，同一份事实存了两遍——这就是增量维护要付的记账成本。（另外还有一个 `word_nbytes` 记每个词的原始字节数，和合并无关，用途见 §2.8 那个免费的压缩率。）

每一轮的流程变成：从堆里取出 best_pair，**只遍历 `pair_to_words[best_pair]` 里的那些词**（而不是所有词），每个词重建序列，只更新真正变化的 pair 计数。

#### 技术 1：delta 更新

考虑一个词 `[a,b,c,d,e]`（出现 5 次），合并 `(c,d) → X`：

| pair | 合并前 | 合并后 | delta | 要动吗 |
|---|---|---|---|---|
| `(a,b)` | 1 | 1 | **0** | 不动，它离合并点远 |
| `(b,c)`、`(c,d)`、`(d,e)` | 1 | 0 | −1 | 计数 −5，并 push 进堆 |
| `(b,X)`、`(X,e)` | 0 | 1 | +1 | 计数 +5，并 push 进堆 |

**为什么 delta 一定正确**：一个 pair 的全局计数等于各个词的贡献之和。这个词在合并前贡献 `old × count`、合并后贡献 `new × count`，净变化就是 `(new − old) × count`。只把这个 delta 加上去，全局计数就是对的。

而 `delta == 0` 的 pair 计数没变，意味着堆里那条旧条目**依然有效**，不用 push，不变量不会被破坏。

验证一个边界情形 `A B A B` 合并 `(A,B)`：合并前是 `{(A,B):2, (B,A):1}`，合并后是 `{(X,X):1}`，delta 全都对得上。

这个思路是「局部改动、大部分不变」这类增量维护问题的通法。

**增量维护的四条记账纪律**（每一条都是被 bug 逼出来的，静态看代码查不出来）：

- 计数减到 0 的 pair 必须从字典里删掉，否则后面会选到"僵尸对"；
- 遍历 `affected` 集合前必须先拷贝一份，因为循环体里会修改这个 set；
- 从集合里移除用 `.discard()` 而不是 `.remove()`，因为同一个词可能多次贡献同一个 pair（比如 `A B A B`）；
- 从字典里删 key 用 `pop(k, None)` 而不是 `del`，因为这个 key 可能已经在减计数那一步被删过了。

#### 技术 2：懒删除堆

这是个通用技巧，值得单独记一笔。

**问题**：Python 的 `heapq` 不支持高效修改堆里已有元素的优先级（要 O(n) 扫描才能找到它），但 BPE 里 pair 的计数在频繁变化。

**解法**：不改旧的，只 push 新的；旧的留着变成 stale（陈旧条目），弹出时验证一下再丢弃。

堆里每条目是四元组 `(-count, neg(id_a), neg(id_b), pair)`：第一项让高频优先，中间两项是下一节要讲的字典序反转键，最后一项是 pair 本身。

```python
def push(self, pair, count):          # 从不扫描堆，只做 sift-up，O(log n)
    id_a, id_b = pair
    heapq.heappush(self.heap, (-count, self._neg(id_a), self._neg(id_b), pair))

def pop_best(self, pair_counts):      # 和「真相源」核对
    while self.heap:
        neg_count, _, _, pair = heapq.heappop(self.heap)
        if -neg_count == pair_counts.get(pair, 0) and -neg_count > 0:
            return pair               # 堆里的值 == 真值，有效
    return None                       # 否则是 stale，丢弃继续弹
```

几个要点：

- push 一个已存在的 pair 会留下**重复条目**（旧的 stale + 新的有效），这是**故意的**，不是 bug。
- **真相源在别处**：`pair_counts` 才是权威，堆只是一个"大概按优先级排好"的加速结构。
- 正确性靠两条不变量：① **无遗漏**——任何计数大于 0 的 pair，堆里至少有一条携带它当前计数的条目（靠"每次计数变动都紧跟一次 push"保证）；② **可鉴别**——堆里的 key 是 `(pair, count)` 的纯函数，对不上就是 stale。这两条合起来保证：第一个通过校验的弹出结果必然是真正的最优。
- **膨胀治理**：堆只增不减，而 `log n` 里的 n 就是堆长度。我加了个 `maybe_rebuild`，在堆长超过 `2×存活数+1024` 时按当前计数重建。

什么时候该想到这个技巧？**任何"优先队列 + 元素优先级频繁变化"的场合**——Dijkstra 的变体、事件调度、任务队列。标准库的堆不支持 decrease-key，懒删除是最常用的绕过法。判据是：修改频繁，且有一个独立的"真相源"能在 pop 时做验证。

#### 技术 3：用 min-heap 模拟 max，以及 tie-break 反转

规则是"频率高的优先，平局取字节字典序**大**的"，但 `heapq` 是 min-heap，所以：

- 频率：存 `-count`。
- 字节：需要反转字典序，用 `neg_bytes(b) = tuple(-x for x in b) + (1,)`。

**末尾那个哨兵 `(1,)` 是整个实现最大的坑。** `tuple(-x for x in b)` 确实反转了字节值，但元组比较里「前缀相同时短的更小」这条**长度规则没有被反转**，导致 `b'b'` 和 `b'bc'` 会选错。加上一个正数哨兵之后，更长的串在对应位置补的是负数，在 min-heap 里更小，于是复现了"长的更大"。

哨兵必须是正数：用 `0` 会和 `neg_bytes(b'\x00')` 撞车；用补码方案（`b"\xff"`）也会撞（`\x00` 的补码正好是 `\xff`）。

我写了穷举验证：对所有包含 `\x00`/`\xff` 的 1~3 字节串做 66306 组比较，朴素版有 **936 组违反**反序，哨兵版 **0 组违反**。

### 2.6 并行性分析：结论会随规模翻转

| 阶段 | 能并行吗 | 说明 |
|---|---|---|
| 预分词 | 可以，数据并行 | 用 `multiprocessing` 绕开 GIL，按特殊 token 切块。**价值全在这里**——它随数据量线性增长 |
| Merge loop | 看规模 | 每一轮都要"全局决策 + 依赖上一轮结果"，只能在**一轮之内**并行（把受影响的词分给多个 worker） |
| GPU / 线程 | 不行 | GPU 不适合这种符号处理；线程受 GIL 限制，而循环体是 100% Python 字节码 |

merge loop 划不划算，完全取决于每一轮的粒度。对照基准是：往 32 个进程派发一批空任务、再收回来，大约要 300 µs。这是并行的固定入场费，每一轮都要付一次。

| 规模 | 不同 pre-token 数 | 每轮词循环耗时（中位数） | 每轮词循环耗时（均值） |
|---|---|---|---|
| TinyStories valid + vocab 10k | 6 万 | 3.5 µs | — |
| OpenWebText train + vocab 32k | 660 万 | 0.3 ms | **20.5 ms** |

TinyStories 那一行不用算了：一轮的工作量只有 3.5 µs，比 300 µs 的入场费还便宜 85 倍，**并行必然是净亏**。

OWT 这一行要看均值而不是中位数。中位数只有 0.3 ms、均值却有 20.5 ms，两者差 68 倍——这说明**绝大多数轮次都极小，总时间是被少数几轮吃掉的**（合并高频对时受影响的词特别多）。而并行省下的是总时间，所以该拿均值去比：300 µs 相对 20.5 ms 只占 1.5%，这才有得算。反过来，那些占多数的小轮次上并行是纯亏的——真做的话应该按当轮 `affected` 的大小决定走不走并行路径。

如果真要做，**正确的形状是永久分片**：每个 worker 常驻持有 `words[k::N]` 和自己那份局部 `pair_to_words`，父进程每轮只广播 `(id_a, id_b, new_id)`（几十字节），worker 回传局部 delta。而不是每轮把词的 id 序列 pickle 进 worker——实测一轮最多要搬 **714 万个 id**，搬运量正比于工作量，那就白搭了。

**但理论上限只有 2.82×。** 优化后重测的耗时分解是：worker 侧（可并行的那部分）67%、父进程更新 `pair_counts` 和维护堆 28%、`pop_best` 5%。后两项加起来 33% 是串行的，套 Amdahl 定律、按 32 个 worker 算：

$$\frac{1}{0.33 + 0.67/32} = 2.85 \approx 2.82$$

优化前这个上限是 3.92×——因为第 10 条优化砍掉的**正好是 worker 侧那部分**，串行占比被动升高，上限就跟着掉了。**优化串行部分会抬高并行天花板，优化并行部分会压低它**，这个反直觉的联动值得记住。要突破 28% 那块地板，得连堆也分片，复杂度和 tie-break 的风险都要上一个档次。

再算上固定的通信开销约 9.5 s（31743 轮 × 一次 round-trip，300 µs 一轮）：在 owt valid 上 loop 一共才 20 s 左右，光通信就吃掉近一半，净收益只有 1.2×，**不值得**；在 owt train 上轮数完全相同、loop 却有 236 s，通信只占 4%，能到约 2.5×。

**同一份并行代码，在两个语料上一个赚一个赔。** 轮数固定而每轮工作量随语料增长，是并行在这里能成立的唯一原因。

### 2.7 优化方法论：五条教训

先说流程。每条优化都走一遍，不跳步：

**定基线**（跑 3 次取中位数，并把 merges 存下来作为正确性基准）→ **profile 找热点** → **一次只改一条** → **对拍 merges 逐条相同**（不同就直接回滚，不去 debug 性能）→ **测时** → **记账** → **收益低于 5% 就回滚** → 全部做完后在**目标语料**上确认。

#### 教训 1：测量规模决定结论，甚至能让结论反转

同一个改动，懒删除堆在小语料（corpus.en / vocab 500）上和不用堆**差不多甚至略慢**（维护开销约等于省下的扫描），但在 valid / vocab 10000 上是 9.8×。

再比如预分词的 `findall` 改动：单进程下 1.54×，32 进程下只有 1.29×（固定开销占比变大），到 2.23 GB 语料上才回到 1.67×。

所以要准备**两级语料**：迭代用的语料要快（几十秒一轮）**并且保留目标语料的特征**。owt valid（290 MB）合格；TinyStories **不合格**——它的 `affected` 中位数是 1，所有和"每轮粒度"相关的优化在它身上全都测不出来。

#### 教训 2：GC 是隐藏的大头，而且会把正确的优化伪装成负收益

第 10 条优化单独上、GC 开着的时候，测出来是 42.75 → 54.16 s，耗时反而涨了 27%，**看起来是个负优化**，我差点直接回滚。关掉 GC 才发现它其实是 28.21 → 19.93 s，是实打实的 **1.42×**。同一条改动，开关一个跟它毫无关系的东西，结论就从"回滚"变成"采纳"。

原因是：merge loop 每轮要分配几百万个小容器（新序列、per-word dict、heap key 元组），它们**不构成引用环**、靠引用计数就能回收，但分代 GC 仍会在每次 gen-2 扫描时遍历整个存活集合——而这个集合恰好被那些常驻 dict 撑得很大。**分配得越多，GC 罚得越狠。**

所以：**任何"多分配换少计算"的优化，评估前必须先把 GC 排除掉**，否则你测到的是 GC 的账，不是你的账。

#### 教训 3："空间换时间"不是无条件成立的，要看空间进了哪个数据结构

同一轮里两条改动都是花内存，结果完全相反：per-word 计数常驻（多占 2~3 GB）**快 1.42×**；让堆无限增长（多占 1.3 GB）**慢 2.6×**。

区别在于：dict 是 **O(1)** 查找，多占内存不影响单次操作的成本；堆是 **O(log n)**，而 n 就是堆长度。**给对数级的数据结构塞空间是自伤。**

#### 教训 4：每改一条就要重新 profile，优化清单会被上一条优化作废

"heap key 缓存"这条是照着第 10 条**之前**的 profile 定的（那时 `_neg` 被调用了 4080 万次）。而第 10 条减少了 touched pair、连带减少了 push，heap 早就不是热点了，实测收益 0。

#### 教训 5：微基准和整体跑可能给出相反的结论

第 10 条的微基准是**每个词快 3.5×**，整体却慢 27%——差异全在 GC 这种全局效应上。**微基准只能解释局部，不能拍板。**

#### 关于 profile 和验证

profile 用 `cProfile.run(..., 'prof')` 加 `pstats.Stats('prof').sort_stats('tottime')`。主要看 **tottime**（函数自身耗时，找瓶颈看它）和 **ncalls**（几百万次的就是热点）。

实战效果：profile 直接指出 `max` 占 7.3 s、`rank` 占 6.6 s（被调用了 **1 亿次**），加起来几乎是全部时间，直接指向"用堆替代每轮全扫"；后来又指出 667 万次 `Counter` 构造，指向了邻域增量。**先 profile 再优化，别猜。**

**怎么验证优化没改坏结果**（计数漂移这类 bug 静态看不出来，唯一可靠的办法是对拍）：

1. **差分测试**：写一个每轮全量重算的 brute-force 版本，逐条比对 merges 和 vocab。语料要**专门造刁钻的**——大量 pair 同频的 tie 语料（测 tie-break）、`aaaa` 这种重叠串（测贪心从左到右 + 重叠记账）、中文和带音标的拉丁字母（测多字节）、随机串。
2. **不变量断言**：每步 merge 之后从 `vocab_ids` 从零重算真值，校验 `pair_counts` 没有漂移、`pair_to_words` 和真值相等、**每个存活的 pair 都有一条携带当前计数的堆条目**（最后这条是懒删除正确性的命根子）。
3. **官方测试**。

那个"建索引"行是倒推出来的，值得说一句：我给分块、预分词、merge loop 都埋了计时，唯独把 `_build_indexes`（从频率表建起 §2.4 那五个数据结构）漏了，结果三段相加只有 255 s，和总耗时差了 40 秒。**在 OWT 上这一步的耗时和整个预分词是同一个量级**（40 s 对 41 s）——给 660 万个词各建一个 dict，这个代价本来就不该被当成"顺手做的准备工作"。教训很直白：**分阶段计时要覆盖所有阶段，否则最先被忽略的那个阶段就是你最不了解的那个。**

**怎么读这组数**：OpenWebText 的 4.363 只比 TinyStories 的 4.071 高 7%——**词表大了 3.2 倍，只换来这么点压缩率**。原因有两层：① 边际收益递减，BPE 先合并的都是最高频的模式，后面那 2.2 万个格子吃的都是长尾；② OpenWebText 的长尾里有相当比例是乱码和分隔线（见下），这些 token 覆盖的文本占比极低，对整体压缩率几乎没有贡献。

**词表翻倍不等于压缩率翻倍**——这是选 vocab_size 时要记住的。

顺带一个实用技巧：这个压缩率是**免费**得来的，而且**可以当作 `encode` 的现成验收标准**。写完 `encode` 后在训练语料上跑一遍，字节/token 应该和这个数很接近，对不上就是 `encode` 有 bug。不用另写 brute force。

它为什么是免费的？因为 merge loop 结束时，每个词的 id 序列就是"依次施加 merge 1..N 之后的结果"，而 `Tokenizer.encode` 做的也正是依次施加 merge 1..N。**训练结束时整个语料已经被编码过一遍了**，只需要在建索引时额外记下每个词的原始字节数（一个 int）。注意要用出现次数加权：频率表里 `the` 只存一份，但语料里它出现了上百万次。

#### 「最长 token 合理吗」——答案是不合理

OpenWebText 最长的 10 个 token **一个真词都没有**：

```
 64B  'ÃÂÃÂÃÂÃÂÃÂÃÂÃÂÃÂÃÂÃÂÃÂÃÂÃÂÃÂÃÂÃÂ'
 64B  '----------------------------------------------------------------'
 48B  '————————————————'
 32B  '________________________________'   '================================'
 32B  '................................'   '********************************'
```

那个 64 字节的是 `b'\xc3\x83\xc3\x82'` 重复 16 次，也就是 **double-encoded UTF-8 mojibake**（重复编码乱码）：一段 UTF-8 字节被误当成 latin-1 解码、再按 UTF-8 编码回去，每错一轮就多一层 `ÃÂ`。

举个例子，不换行空格 U+00A0 的 UTF-8 是 `\xc2\xa0`，误读成 latin-1 得到 `'Â '`，再编码成 UTF-8 就是 `\xc3\x82\xc2\xa0`。64 字节说明同一段文本在爬取管线里被**错误转码了很多轮**。

对照 TinyStories 最长的 10 个，全是规规矩矩的英文词：` accomplishment` / ` disappointment` / ` responsibility` / ` uncomfortable` / ` compassionate`……

**结论**：TinyStories 的最长 token **合理**——GPT-4 生成的干净儿童故事，最长 token 自然就是最长的常用词。OpenWebText 的最长 token **不合理**——它反映的是网页语料的编码损坏和排版分隔线，不是语言结构。

要强调的是：**算法没错，是数据脏**。这些字节序列确实高频，BPE 忠实地把它们学了下来。

这引出一个更值得追问的问题：**词表里到底有多少格子被垃圾占掉了？** 这直接吃掉压缩率，也吃掉 leaderboard 上宝贵的 token 预算。真实的预训练管线会先做数据清洗（去重、编码修复、过滤），这正是后面数据那个 assignment 的主题。

#### 序列化：为什么选 JSON + latin-1

落盘要存 `vocab.json` 和 `merges.json`。测试完全不碰加载函数，格式随便选，但有几个决定值得记一笔。

**首先，bytes 塞不进文本格式。** 实测 `vocab_size=300` 的词表里，**128/300 个 token 不是合法 UTF-8**（多字节字符的续接字节，单独拿出来就是非法的），直接 `b.decode("utf-8")` 会崩。三种解法：

| 方案 | 谁在用 | 做法 |
|---|---|---|
| byte → unicode 映射 | GPT-2 的 `vocab.json` / `merges.txt` | 把 256 个字节各映射到一个**可打印**字符（空格→`Ġ`、换行→`Ċ`）。这个 trick 是为了迁就 `merges.txt` 用空格分隔两个 token 的文本格式——不映射的话，token 本身是空格就产生歧义了 |
| **latin-1**（我选的） | — | 字节 0–255 一一映射到码点 U+0000–U+00FF，所以 `b.decode("latin-1").encode("latin-1") == b` 对**任意**字节串成立。merges 我存成 JSON 数组而不是空格分隔，所以不需要 GPT-2 那套 trick |
| base64 | tiktoken / Llama 3 | 最保险，代价是不可读 |

**有三层容易搞混**，以 id=195 为例：token 是 1 个字节（值 195）→ JSON 文本里是 1 个字符（码点 195，也就是 `'Ã'`）→ **磁盘上是 2 个字节**（`C3 83`，因为文件本身按 UTF-8 写）。所以所有 ≥128 的字节在磁盘上都膨胀一倍。

### 2.9 Tokenizer 的 encode / decode

训练产出的是 vocab 和 merges，这一节讲怎么拿它们去编码新文本：构造函数要预建哪几张表、encode 为什么必须分三段、以及流式版本 `encode_iterable` 那三条一碰就错的不变量。

测试结果是 24 passed、1 xfailed（那个 xfail 是测试自己标的，`encode` 不要求省内存）。

**但绿灯不等于证明。** 有个测试用装饰器把内存限制到 1 MB，可它在 `finally` 里就把限制还原了，而被装饰的函数是**生成器函数**——调用它只创建生成器、不执行，等真正迭代时限制早就撤了（实测：普通函数里 rlimit=14MB 生效，生成器迭代时是"无限制"）。

所以那个 PASSED 的证明力比看起来弱得多。真正的依据是**结构本身**（用 `yield` + 缓冲区只留未结算的尾巴）和我自建的对拍。**测试测的是它写下的那个条件，不一定是你以为的那个条件。**

#### 构造函数要建四张表

传进来的 `vocab` 和 `merges` 都答不了 encode 要问的问题：

| 表 | 类型 | 为什么需要 |
|---|---|---|
| `inverse_vocab` | `dict[bytes, int]` | `vocab` 方向反了；合并操作的是 bytes，输出要 ID |
| `merge_rank` | `dict[pair, int]` | 在 list 里查"排第几"是 O(n)；rank 就是它在 `merges` 里的下标 |
| `cached_word_ids` | `dict[str, list[int]]` | pre-token 记忆化。key 用 `str`，命中时能省一次 `.encode()` |
| `special_split_pat` | 编译好的正则 | 依赖 `self.special_tokens`，不能放模块级 |

两个坑：特殊 token 要追加进 vocab，并且**必须同步更新 `inverse_vocab`**；另外 `special_tokens` 这个参数即使 vocab 里已经全有也得传——`vocab` 只是 `id → bytes`，**它没有标记谁是特殊的**。

#### encode 分三段

① 用 `special_split_pat` 切开并保留分隔符，特殊 token 直接查表；② 普通段过 GPT-2 正则；③ 每个 pre-token 单独做合并。

第①步**必须独立，不能把特殊 token 塞进主正则当成一个 or 分支**。这是被 tiktoken 当裁判实测出来的：`'x <|endoftext|> y'` 合进主正则会得到 `['x', ' <|', 'endoftext', '|>', ' y']`——特殊 token 被切碎了。

原因是正则交替是逐位置尝试的：扫到 `<` 前面那个**空格**时，special 分支不匹配，而 ` ?[^\s\p{L}\p{N}]+` 这一支会贪心地吃掉 `' <|'`。**加个 or 分支救不了。**

切分正则有三个要点：`re.escape`、外层加捕获组（`re.split` 才会保留分隔符）、**按长度降序排列**（因为交替是从左到右优先，不是最长匹配）。

#### 合并单个 pre-token

做法是：拆成单字节 → 循环 { 挑 `merge_rank` 最小的相邻对，合并它的所有出现 } → 挑不到就退出。

这和"从头遍历所有 merge 规则"**完全等价**（实测 277 个 pre-token 零差异），但**快 119 倍**。

等价的依据是：训练时新 token 的 id 等于当时的词表长度，所以任何用到 `X` 的 merge，它的 rank 必然大于造出 `X` 的那条；而合并之后新冒出来的对只可能包含 `X`，所以都在前方。

成本对比：遍历法固定要跑 5 万次，挑最小法最多跑「词长−1」次，实际约 **3 次**（加权平均 pre-token 只有 4.22 字节）。

**这里不要用堆。** 候选只有约 3 个，且每轮只取一次最小值，实测 `min()` 在 3~2000 各种规模下都比 `heapify + pop` 快两倍多。对照训练那边堆赢了 9.8×——**同一个优化，规模不同结论相反**，又一次印证了 §2.7 教训 1。

#### encode_iterable 的三条不变量

要求是 5 MB 文件在 1 MB 内存里跑完，且必须和整体 `encode` 逐 token 相同。

| # | 危险 | 守法 |
|---|---|---|
| 1 | 特殊 token 横跨切点，split 只看到半截 | 结算上限设为 `len(buf) − (最长特殊token长度 − 1)`；如果仍落在某个特殊 token 匹配内部，再退到它的起点 |
| 2 | 最后一个正则匹配可能还没吃完（`\s+(?!\S)` 要看后一个字符） | **扣住最后一个匹配**不结算。只扣最后一个文本段——被特殊 token 夹住的段是硬边界 |
| 3 | **吐已经算好的 token，不能拿结算前缀重新跑正则** | 最短反例是 `'\n\n!!'`：整体切是 `['\n','\n','!!']`，但单独对 `'\n\n'` 跑 findall 时，前瞻在字符串末尾成功，得到 `['\n\n']`。**我在这栽了两次** |

实现上用 `itertools.chain(iterable, [None])` 加一个哨兵、延迟一拍，才能知道当前块是不是最后一块。

有个直觉上的做法行不通：「只在遇到特殊 token 时才结算」——因为 roundtrip 测试**没有传特殊 token**，没有刷新点，缓冲区会一路涨满整个文件。

已知局限：一个巨大的连续空白串整体是一个匹配，会全堆在缓冲区里。

#### decode

`b"".join(...).decode("utf-8", errors="replace")`。**必须先拼接再一次性解码**——merge 可能落在多字节字符的中间，逐个 token 解码会各自失败，变成两个 `�`。

**验证手段**：官方测试（含一批和 tiktoken 逐 token 对比的用例）+ 自建对拍器（1011 个刁钻用例 × 3 种特殊 token 配置 × 5 种切法，包括 chunk=1 和逐行）。上面那三条不变量是被反例逐个逼出来的，**每错一次就往语料里加一个用例**。

### 2.10 实验和数据落盘

#### 压缩率（字节/token，越大越好）

| 样本 | 用哪个 tokenizer | 字节 | token 数 | 字节/token |
|---|---|---|---|---|
| TinyStories 10 篇 | TinyStories (10k) | 7,633 | 1,861 | 4.102 |
| OpenWebText 10 篇 | OpenWebText (32k) | 60,084 | 13,586 | **4.422** |
| OpenWebText 10 篇 | **TinyStories (10k)** ← 交叉 | 60,084 | **17,952** | **3.347** |

只有后两行可比（同一份 OpenWebText 样本），第一行是另一份样本，只能横向看比值。

另外注意样本量差很多：10 篇儿童故事才 **7.6 KB**，10 篇网页有 **60 KB**。小样本的压缩率方差大，能和全量数字对上有运气成分——真要下结论应该看下面全量落盘的 4.116 / 4.371（口径见本节末尾：这两个数含 `<|endoftext|>`，§2.8 表里的 4.071 / 4.363 不含）。

**结论：用错 tokenizer，压缩率掉 24.3%、token 数多 32.1%。** TinyStories 的词表学自 GPT-4 生成的儿童故事，完全没有网页文本的词汇（URL、技术术语、非英文、排版符号），所以只能把 OpenWebText 切得更碎。

**这条有真实代价**：leaderboard 是固定 45 分钟的算力预算，token 效率低 32% 大致等于模型少看 32% 的文本；推理时 context window 也会更快耗尽。

顺带一提，这和"多语言不公平"是同一个机制——小语种被切碎，本质就是拿一个没覆盖这类文本的词表去编码。

#### 吞吐（单进程）

作业里拿 The Pile（825 GB）当尺度参照物，不是真的去跑，而是算一笔账：*这个 tokenizer 拿到真实规模的语料上要多久？* 一个慢 100 倍的实现（比如 `encode` 遍历全部 merge），同样这笔账就是 90 天，预处理直接变成工程阻塞。

| | 单进程 MB/s | 缓存命中率 | 处理 Pile 825 GB |
|---|---|---|---|
| TinyStories | **20.7** | 99.75%（每 401 次出现才真算 1 次） | 11.1 小时 |
| OpenWebText | **10.6** | 96.93%（每 32.5 次） | 21.5 小时 |

**别拿单进程除以 32 去估并行。** 实测 32 进程是 **187.2 MB/s**，加速比只有 **17.6×** 而不是 32×（效率 55%，损耗在 IO、pickle 回传、父进程拼接、负载不均）。所以 Pile 的实际估算是 **1.2 小时**，不是除以 32 得到的 0.67 小时。

**吞吐由缓存命中率决定，不由词表大小决定。** 同样 20 MB 的文本，OpenWebText 有 13.5 万个不同的 pre-token（TinyStories 才 1.3 万），真正需要做合并计算的次数多 10 倍。直觉容易归因于"词表大 3 倍所以慢"，实际原因是**语料多样性**。

#### 落盘产物（32 进程）

| split | 语料 | 耗时 | token 数 | 字节/token | 文件大小 |
|---|---|---|---|---|---|
| tinystories_train | 2.23 GB | 8.5 s (261 MB/s) | 5.41 亿 | 4.116 | 1.08 GB |
| tinystories_valid | 0.02 GB | 0.2 s | 546 万 | 4.117 | 0.01 GB |
| **owt_train** | **11.92 GB** | **63.7 s (187 MB/s)** | **27.27 亿** | 4.371 | **5.45 GB** |
| owt_valid | 0.29 GB | 2.5 s | 6640 万 | 4.367 | 0.13 GB |

**为什么存成 uint16**：范围 0–65535，装得下 32000 和 10000。换成 uint32 文件直接大一倍（5.45 → 10.9 GB），而训练时是用 `np.memmap` 随机采样的，**文件越小页缓存命中越好**。

前提条件是 `vocab_size ≤ 65536`，落盘时应该加断言。像 Llama 3（128k）、Qwen（15 万）那种词表就必须用 uint32。

**并行怎么做的**：按特殊 token 把文件切成「进程数 × 4」块，各个 worker 编码自己那块，父进程按块序拼接。

- **正确性**：边界落在特殊 token 的起点，而它是硬边界，pre-token 和 merge 都不会跨越，所以分块编码严格等于整体编码。实测验证过：valid 上 546 万个 token 与整体 `encode` 逐个相同，decode 回原文一字不差。
- **worker 回传 `np.uint16` 数组而不是 `list[int]`**：pickle 的是 2 字节/token 的连续 buffer，而不是几千万个 Python int 对象。
- **tokenizer 建在模块级**：Linux 上多进程走 fork，全局对象通过 copy-on-write 免费继承；而且 worker 跨任务复用同一个对象，缓存能累积（块数取 ×4 就是为了摊薄冷启动）。

最后一点值得单独说：**同一个压缩率有三条独立路径能算出来**——训练期从频率表的内部数据算出 4.071、采样 10 篇文档跑 `encode` 算出 4.102、全量落盘之后用 token 总数除字节总数算出 4.116。三条路径共用的代码几乎为零，能落在同一个小区间里，就是**免费的正确性交叉验证**。

但 4.071 和 4.116 之间那 1.1% 的差不该被当成"约等于"糊过去，它有确定的来源：**训练期的统计不包含 `<|endoftext|>`**（特殊 token 不进频率表，见 §2.1），而落盘时它是实打实的 token。TinyStories 有约 273 万篇文档，也就是 273 万个分隔符，每个在原文里占 13 个字节：

$$\frac{2.23\times10^9 - 273\text{万}\times13}{5.41\times10^8 - 273\text{万}} = 4.077$$

和 4.071 对上了。**两条路算出来的数不一样时，先别急着说"差不多"——把差额也解释掉，才算真的对上了。** 这一次差额里藏的是"特殊 token 算不算进压缩率"这个口径问题，而口径问题正是最容易在后面引出错误结论的东西。

方法论上这比数字本身值钱：**任何时候一个量能用两条路算，就该都算一遍。**

### 2.11 延伸：分词的代价

> 这一节和作业实现无关，是顺带梳理的背景。

#### 三种主流分词算法

| | **BPE** | **WordPiece** | **Unigram LM** |
|---|---|---|---|
| 代表模型 | GPT 系、Llama 3、Qwen | BERT | SentencePiece：Llama 1/2、Gemma |
| 训练时选谁 | 频率最高的对 `count(AB)` | 似然提升最大，实践上约等于 `count(AB)/(count(A)·count(B))` | 反向操作：从大词表剪枝，去掉损失最小的 piece |
| **推理时怎么切** | **重放 merge 序列**（有序） | **词表内最长前缀匹配**（trie） | **Viterbi 求全局最可能的切分** |
| 交付物 | vocab + **merges** | **只要 vocab** | vocab + 每个 piece 的分数 |
| 贪心吗 | 是 | 是 | 否，全局最优 |
| 未登录词 | byte-level 下不存在 | 需要 `[UNK]` | 需要回退 |

**为什么 WordPiece 能贪心而 BPE 不能？** 因为两者把"编码"定义成了不同的东西：

- BPE 的定义是「**复现训练时发生过的那串操作**」，所以必然依赖顺序，必然要带着 merges 走。
- WordPiece 的定义是「**在词表里取最长**」，只依赖词表这个集合，与训练时怎么得到它无关。

这是设计取舍，不是谁更聪明。

**所以不能把 BPE 的 encode 改写成 trie 贪心。** 反例：merges 只有 `rank0: (b,c)→bc` 和 `rank1: (a,b)→ab`，编码 `"abc"`——BPE 挑 rank 最小的 `(b,c)`，得到 `[a, bc]`；trie 最长前缀得到 `[ab, c]`。**结果不同。** 不是那个算法不好，是它和你训出来的这套 merges 不配套。

#### 分词不是 Transformer 的缺陷，但有一条真实的因果链

分词发生在模型之外。Transformer 拿到的就是一串整数 ID，它不知道也不关心这些 ID 怎么来的。换成 RNN / LSTM / Mamba，问题一模一样。所以这不是 Transformer 架构的缺陷。

但有一条因果链值得记住：

> attention 是 $O(n^2)$，embedding 和最后的 softmax 是 $O(\text{vocab})$，所以分词是一道**压缩工序**，把序列长度压下来好让 $O(n^2)$ 付得起。

**它本身不产生任何语义价值。** 如果 attention 是免费的，直接喂字节就行——这正是下面那批工作的出发点。

#### 分词制造的真问题

| 问题 | 表现 |
|---|---|
| **算术差** | `12345` 的切法不稳定，学不到位值关系。GPT-4 限制数字长度就是为此打的补丁 |
| **字符级失明** | "strawberry 里有几个 r"——模型没见过字符，只见过几个 token ID |
| **多语言不公平** | 小语种被切得稀碎，同一句话花几倍 token，又贵又差 |
| **提示词边界效应** | 末尾多一个空格就换一套 token，行为跟着变（前导空格吸附） |
| **glitch token** | `SolidGoldMagikarp` 那一类：在词表里但训练语料几乎没出现，embedding 那一行从没被更新过，模型碰到就发疯 |
| **词表格子被垃圾占** | OpenWebText 词表里最长的 10 个 token 全是乱码和分隔线 |

**但最要命的一条不是"问题"而是"约束"**：**encode 必须和训练时完全一致。**

模型学的是「ID 47 后面常跟 ID 892」这种统计规律。训练时用 BPE 的 rank 顺序切、推理时改用贪心切，同一句话会变成一串不同的 ID，分布一偏模型立刻退化。这就是为什么测试里有一堆要求逐 token 对上 tiktoken 的用例——**tokenizer 不是"差不多就行"的组件，它是模型的一部分。**

#### 去 tokenizer 化的尝试

思路都是「把压缩这一步交给模型自己学，而不是外挂一个固定词表」。SSM 和线性注意力让长序列变便宜之后，这条路更有希望了。

| 工作 | 一句话 |
|---|---|
| **CANINE**（2021, Google） | 字符级编码器，下采样后再进 Transformer |
| **ByT5**（2021, Google） | 直接吃 UTF-8 字节的 T5，无词表 |
| **Charformer**（2021） | 学习式的子词切分，端到端可微 |
| **MegaByte**（2023, Meta） | 固定大小 patch + 局部/全局两级 Transformer，让字节级序列可扩展 |
| **Byte Latent Transformer**（2024, Meta） | 按**熵**动态划分 patch——信息量大的地方切细，平淡处切粗 |

读这批工作时要盯的共同问题：① 序列变长后算力怎么摊（这是分词存在的唯一理由）；② 去掉词表后，前面那张表里的问题解决了几条、又新增了什么；③ 和固定词表相比，同算力下的实际质量。

### 2.12 §2 小结

BPE 部分的 34 分全部拿下。产出的四个 `.npy` 文件就是后面训练时用 `np.memmap` 读的输入。

**要记住 tokenizer 速度和 LM 训练速度无关**：训练读的是已经落盘的 memmap 数组，tokenizer 不在那个循环里。真正影响训练的是它的**输出**——`vocab_size`（决定 embedding 和 LM head 的参数量、以及 softmax 开销）和**压缩率**（决定同样 token 预算下模型能看到多少文本，对 45 分钟的 leaderboard 是实打实的杠杆）。

所有优化都保持了 merges 逐条相同，也就是没有改变输出，所以没有影响训练。

最后一个小技巧：**数据探查用命令行比写 Python 快**。`grep -c/-oF`、`wc -l/-c`、`stat -c %s` 就够了。实测 TinyStories valid 有 27630 个 `<|endoftext|>`、22.5 MB；train 2.23 GB，倒推约 273 万篇文档，平均约 816 字节一篇。

### 3.1 整体地图

端到端的形状流：

| 阶段 | 输出形状 | 备注 |
|---|---|---|
| 输入 | `(batch, seq)` | 整数 token ID，来自 §2.10 落盘的 `.npy` |
| Token Embedding | `(batch, seq, d_model)` | 查表 |
| Transformer Block × num_layers | `(batch, seq, d_model)` | **进出同形状** |
| 最后一个 RMSNorm | `(batch, seq, d_model)` | pre-norm 架构特有 |
| LM head（Linear） | `(batch, seq, vocab_size)` | **logits，不是概率** |

两个骨架级的理解：

1. **`d_model` 是一条从头贯到尾的总线**，叫做残差流（residual stream）。中间那些 block 谁也不改变它的宽度，每个 block 只是往这条总线上"加"东西。
2. **block 进出同形状，所以能无脑堆叠**。这不是巧合，而是设计约束——正因如此 `num_layers` 才能当成一个自由超参。

pre-norm block 里两个子层是同一个模式：

$$y = x + \text{Sublayer}(\text{RMSNorm}(x))$$

子层一是带 RoPE 的因果多头自注意力，子层二是 SwiGLU 前馈网络。也就是**先 norm、再主操作、最后残差**。注意残差加回去的是 `x` 而不是 `RMSNorm(x)`——**这正是"残差流保持干净"的含义**。

有三个问题值得先想清楚：

**为什么 pre-norm 最后还要补一个 RMSNorm？** post-norm 里每个子层出口都归一化过，输出天然有界；pre-norm 把 norm 挪到了入口，残差流上的量层层累加就没人约束了，LM head 拿到的东西尺度会失控。所以必须在最后补一次。后面消融实验里 `pre_norm_ablation` 测的就是这个。

**位置信息在哪一步进入模型？** 对着架构图找一遍会发现，**embedding 之后没有任何位置编码**。位置信息只在每一层 attention 内部通过 RoPE 注入，而且只作用于 Q 和 K。这和 GPT-2 不同（GPT-2 是可学习的绝对位置 embedding，直接加在 token embedding 上），所以本模型只有**一张** embedding 表。

**模型返回 logits 还是概率？** 是 logits。作业文档自己有点不一致——开头说返回 "normalized probability distribution"、架构图顶上也画着 Softmax，但具体那道题说的是 "unnormalized distribution over the vocabulary (the logits)"。以后者为准。理由：cross-entropy 需要在内部做 log-softmax 才能数值稳定；生成时的 temperature / top-p 也要在 logits 上介入。

**可学习参数清单**（做资源估算时要用）：

| 组件 | 形状 | 个数 |
|---|---|---|
| token embedding | `(vocab_size, d_model)` | 1 |
| 每个 Block：注意力四个投影 + 前馈三个矩阵 + 两个 RMSNorm 的 gain | — | 9 × num_layers |
| 最后的 RMSNorm | `(d_model,)` | 1 |
| LM head | `(vocab_size, d_model)` | 1 |

两个容易漏的点：**RoPE 没有参数**（它的 cos/sin 是 buffer 不是 Parameter）；**本作业不做 weight tying**，LM head 和 token embedding 是两个独立的矩阵，所以 `vocab_size × d_model` 要算两次。

最后，构造参数里的 **`context_length` 只有一个用途——决定 RoPE 预计算 buffer 的长度**。它不出现在任何参数矩阵的形状里，这也是这套架构理论上能外推到更长序列的原因（效果另说）。

### 3.2 张量代数：einops 和内存序

作业文档花了整整两页讲 einsum 记号，不是凑字数。到多头注意力那一步，你要同时管 batch、seq、head、d_k 四个维度，用 `view` + `transpose` 拼很容易写出"跑得通但数值错"的代码。

**核心思想**：轴从"位置"变成"名字"——声明输入和输出各个轴叫什么，中间的 view/transpose/permute 交给库去推。所以文档里说 "documentation is implementation"，不可能出现"注释写着 `(b,h,s,d)` 但代码其实是 `(b,s,h,d)`"这种漂移。

三个 op：`rearrange`（纯搬运，元素数不变）、`reduce`（聚合）、`einsum`（收缩）。常用动作：

| 动作 | pattern |
|---|---|
| 换序 | `"a b c -> a c b"` |
| 合并轴 | `"a b c -> a (b c)"` |
| 拆分轴 | `"a (b c) -> a b c", b=4`（必须给出其中一个大小；不整除直接报错，等于免费的形状断言） |
| 加一个长度 1 的轴 | `"a b -> a 1 b"` |
| **任意批维** | `"... a b -> ... b a"` |

einsum 的判定只有两条规则：**同名的轴对齐配对相乘**；**左边有、右边没有的轴，沿它求和消去**。

有两个坑要记住。

**第一个是 `(a b)` 的顺序语义**：左边的 `a` 是慢变轴、右边的 `b` 是快变轴（合并后索引等于 `a*len(b)+b`，和 row-major 内存序是同一条规则）。**合并和拆分只有 `(a b)` 对 `(a b)` 才互逆。** 拆分时顺序写反的话，形状完全正确、代码照样跑、但元素被洗牌了，数值全错。到多头注意力拆 head 时，这就是决定成败的一行。

**第二个是 API 陷阱**：`einops.einsum(t1, t2, "pat")` 是张量在前，而 `torch.einsum("pat", t1, t2)` 是 pattern 在前、且只能用单字母轴名。建议全程只用 einops 版。

#### 行/列向量与 row-major 到底在说什么

作业文档里有一节讲这个，初读容易晕。精髓是：

数学习惯用列向量（$y = Wx$），这种写法批量化时 batch 只能放**后面**。但 PyTorch 是 row-major，batch 必须放**前面**——因为这样每个样本的特征在内存里是连续的一段，取一个样本等于顺序读一段内存，缓存友好；反过来存成 `(d_in, batch)` 就被打散成跳读了。

batch 在前就只能用行向量式 $y = xW^\top$，于是**数学和代码之间永远差一个转置**。

但要注意：**两种约定对 $W$ 的存储形状没有分歧，都是 $(d_{out}, d_{in})$**。分歧只在于 $x$ 从哪一侧乘进来。

而且——**用 einsum 就对这一节免疫**。写 `"... d_in, d_out d_in -> ... d_out"`，轴名一标，根本不存在"该不该转置"这个问题。

### 3.3 命名约定：模块树和 state_dict

这一条看起来琐碎，但它决定了后面九道题好不好写。

`state_dict` 的 key 是**属性名沿模块树拼接**出来的。所以属性名写错一个字母，整条路径就废了。课程提供的测试适配器文档里列出了参考实现的完整命名，开工前照着定名，后面每个适配器都只需要一行 `load_state_dict`：

| 层级 | 属性名 |
|---|---|
| LM | `token_embeddings` / `layers`（必须是 `nn.ModuleList`）/ `ln_final` / `lm_head` |
| Block | `attn` / `ln1` / `ln2` / `ffn` |
| 注意力内部 | `q_proj` `k_proj` `v_proj` `output_proj` |
| 前馈内部 | `w1` `w2` `w3` |
| 叶子参数 | `weight` |

拼出来的 key 形如 `layers.3.attn.q_proj.weight`、`ln_final.weight`。

注意 `layers` 必须用 `nn.ModuleList`。普通 Python list 里的子模块**不会被注册**，参数进不了 `state_dict`，优化器也看不见。

**`load_state_dict` 是原地拷贝**，等价于 `param.data.copy_()`。这意味着参数的 device 和 dtype **不会改变**，传进来的张量会被自动转换。建议保持 `strict=True`：key 或形状对不上就报错，**这是免费的命名校验和形状校验**。

三个坑：

1. 有些适配器给的是**裸 Tensor** 而不是字典，要自己包成一个单键字典（叶子模块没有路径前缀，key 就是 `weight`）；而 block 和 LM 那两个适配器给的**本身就是字典**，key 已经是全路径，可以直接传。
2. **device 和 dtype 要在构造时就对齐**，而且要取自权重张量（不是输入激活）。device 不一致的话 forward 会报错（**响的**）；dtype 不一致的话会**静默转换精度**（**哑的，更麻烦**）。
3. **persistent buffer 也会进 `state_dict`**。所以 RoPE 的 cos/sin 如果按默认方式注册，会多出参考实现没有的 key，`strict=True` 直接失败。**这才是作业要求 `persistent=False` 的真实原因**，不只是省磁盘。

调试技巧：key 对不上时，把两边的 key 集合做**对称差**，一眼看出谁多谁少。

还有一条设计原则：**适配器只做胶水**。里面出现的每一点逻辑，都说明模块本该提供而没提供。发现自己在适配器里写形状变换或默认值填充，就是模块接口设计有问题。

### 3.4 参数初始化

作业给了一组够用的初始化，细节留到后面的 assignment：

| 参数 | 分布 | 截断 |
|---|---|---|
| Linear 权重 | $\mathcal{N}(0,\ \sigma^2=\frac{2}{d_{in}+d_{out}})$，也就是 Xavier/Glorot | $[-3\sigma, 3\sigma]$ |
| Embedding | $\mathcal{N}(0,\ \sigma^2=1)$ | $[-3, 3]$ |
| RMSNorm 的 gain | 全 1（恒等变换） | — |

**Xavier 的分母是怎么来的**：前向传播希望激活方差逐层不变，这要求 $\sigma^2 \sim 1/d_{in}$；反向传播希望梯度方差不变，这要求 $\sigma^2 \sim 1/d_{out}$。两者一般不可兼得，取调和平均就得到了这个式子。

数值上感受一下：GPT-2 XL 的 $d_{model}=1600$，注意力那几个方阵的 $\sigma \approx 0.025$。而 GPT-2 论文里用的是固定 0.02——**同一个数量级**，不是巧合。

**Embedding 为什么不套 Xavier**：Xavier 的推导前提是"输出等于 $d_{in}$ 项的加权和"，靠求和的方差累积来定标度。但 embedding 是**取一行**，那个累积效应根本不存在，所以推导不适用，直接取单位方差。

**gain 如果顺手写成 0**：前向输出恒为 0、梯度也断了，loss 会卡在 $\ln(\text{vocab\_size})$ 一动不动。

**最大的坑**：`torch.nn.init.trunc_normal_` 的 `a`/`b` 参数是**绝对边界值**，默认是 `±2.0`。如果写 `std=0.02` 又不传 a/b，实际截断发生在 $\pm 100\sigma$，**等于完全没截断**。a/b 必须跟着算出来的 $\sigma$ 走。

另外三个值得知道的点：

- **截断不等于 clamp**。`randn().clamp()` 会把两条尾巴压成 $\pm 3\sigma$ 处的两个**点质量**，分布形状就变了；而 `trunc_normal_` 是逆 CDF 采样，直接从截断分布里抽。截断也不是理论洁癖：$3\sigma$ 外的概率是 0.27%，GPT-2 XL 的某个矩阵有 686 万个元素，**必然出现约 1.8 万个离群值**。
- **`torch.empty` + 就地初始化是 PyTorch 官方 idiom**（`nn.Linear.reset_parameters` 就这么写）。`empty` 只分配内存不填值，紧接着被逐元素全覆盖，省掉了一次注定要被覆盖的填充。
- **实测 `std()` 会比名义 $\sigma$ 低约 1.3%**，因为截断砍掉两条尾巴必然让方差缩水，而 PyTorch 不做补偿性 rescale。看到 0.987σ 是**正确行为，别当 bug 去查**，更不要后处理去凑。

最后是一条方法论上的提醒：**初始化这一块 pytest 完全测不到。**

测试都是加载给定的权重再比数值，你写的 `trunc_normal_` 根本不会被执行。$\sigma$ 写错、gain 写成 0、忘了截断，**测试照样全绿**。账要到真正训练时才结（loss 不降或者前几百步炸掉），那时已经隔了十几个组件，极难回溯。更麻烦的是作业文档自己说 "pre-norm 对初始化异常鲁棒"——意味着你连一个明确的失败信号都不会有。

所以要自己加断言：检查 `weight.std()` 是否接近理论 $\sigma$（允许低 1.3%）、`weight.abs().max()` 是否不超过 $3\sigma$。30 秒的事，能省掉后面一个下午。这是 §2.9 那条"绿灯不等于证明"的延续。

### 3.5 Linear

第一个要自己写的模块，只值 1 分，但我在上面踩了五个坑，其中两个测试完全抓不到——这一节记的主要是那五个坑，以及它们暴露出的一条通用原则：**用契约构造模块，不要用数据构造模块。**

先列要求：不带 bias（跟随现代 LLM 的做法）；参数存 $W$ 而不是 $W^\top$，形状 `(d_out, d_in)`；属性名叫 `weight`；必须包在 `nn.Parameter` 里；必须支持任意批维；禁用 `nn.Linear` 和 `F.linear`。

我在这道 1 分的题上踩了五个坑，前两个**测试完全抓不到**：

| # | 坑 | 后果 |
|---|---|---|
| 1 | 参数没包进 `nn.Parameter`，只是个普通 tensor | 不进 `state_dict`、优化器看不见、`.to()` 搬不走、`load_state_dict` 无效。这四件事后面全是刚需 |
| 2 | `std` 硬编码成 0.02，且不传 `a`/`b` | 分布和截断双错，测试全绿 |
| 3 | einsum pattern 里批维写死成 `b` | 喂三维输入直接报错 |
| 4 | 属性名叫 `W`、类名小写 | 对不上参考 state_dict，后面两道大题要手工搬十几个张量。**这条有连锁后果，越晚改越贵** |
| 5 | 适配器里用 `weights.shape` 反推维度 | 见下 |

第 5 条值得展开。适配器的签名同时给了 `d_in`/`d_out`（**声明的契约**）和 `weights`（**实际的数据**）。用 `weights.shape` 去构造，模块形状就完全由数据定义了，于是 `load_state_dict` 的形状检查变成自己和自己比，**永远不可能报错**。而用 `d_in`/`d_out` 构造，它才真的在比对契约和数据，权重转置之类的错误会当场抛出 `size mismatch`，一眼定位。

这其实就是 §2.10 那条方法论的微型版：**任何时候一个量能用两条路算，就该都算一遍。**

### 3.6 Embedding

这一节讲怎么不借助 `nn.Embedding`、只用张量的高级索引（advanced indexing，即用整数张量当下标）实现查表，以及为什么这个看起来离散的操作是可微的。

核心实现只有一行 `self.weight[x]`，但它做的事值得用一个小到能手算的例子看清楚。取 `vocab_size=4`、`d_model=3`，权重表就是这么一张 4×3 的表：

| token id | 这一行的向量 |
|---|---|
| 0 | `[0.1, 0.2, 0.3]` |
| 1 | `[1.0, 1.1, 1.2]` |
| 2 | `[2.0, 2.1, 2.2]` |
| 3 | `[3.0, 3.1, 3.2]` |

喂进一个形状 `(2, 2)` 的 id 张量 `[[2, 0], [1, 3]]`，`weight[x]` 得到的是形状 `(2, 2, 3)` 的结果：`[[[2.0,2.1,2.2], [0.1,0.2,0.3]], [[1.0,1.1,1.2], [3.0,3.1,3.2]]]`。

规律一眼就出来了：**PyTorch 保持 `x` 的骨架不动，把里面每个整数替换成 `weight` 里对应的整行**，于是输出形状就是 `x.shape + (d_model,)`。这既解释了为什么代码能短到一行，也解释了为什么它天然支持任意批维——`x` 是几维，输出就比它多一维，实现里不需要写任何形状处理。

**为什么查表是可微的**，我一开始想不通：按下标挑一行，这不是个离散操作吗？

关键是查表在数学上严格等于 **one-hot 向量乘以权重矩阵**。上面那个 id=2，等价于用 `[0,0,1,0]` 去乘那张 4×3 的表，结果正是第 2 行。既然是矩阵乘法，当然可微；只不过 one-hot 里除了一个 1 全是 0（真实词表下是五万分之一），实现上没必要真的去乘，直接按地址取行就行。反向传播执行的是 `scatter-add`：收到的梯度按行号累加回权重表——**同一个 token 在一个 batch 里出现几次，它那一行就被加几次梯度**，而没出现过的行梯度为零。这就是 §1.5 说的"罕见 token 的那一行几乎没被更新过"的机制层面。

两个和别处联动的点。一是 **embedding 的初始化不套 Xavier**，理由在 §3.4：Xavier 的推导前提是"输出是 $d_{in}$ 项的加权和"，而这里是取一行，累积效应不存在。二是**下标张量必须是 `int64`**，`uint16` 之类的窄整型 PyTorch 的索引算子不认——这个坑在 §5.1 的 dataloader 里真的踩到了，报错信息指向的正是这一层。

### 3.7 RMSNorm

RMSNorm（Root Mean Square Layer Normalization）是在 LayerNorm 的基础上去掉了减去均值的步骤，只保留了基于 RMS 的缩放操作，最后乘以可学习的参数 $g_i$：

$$\text{RMSNorm}(a_i) = \frac{a_i}{\text{RMS}(a)} g_i, \qquad \text{RMS}(a) = \sqrt{\frac{1}{d_{model}}\sum_{i=1}^{d_{model}} a_i^2 + \varepsilon}$$

去掉减均值这一步的好处是少一趟归约、少一次遍历，而实践上效果不比 LayerNorm 差——Llama 系列用的就是它。gain 是 `d_model` 个可学习参数，初始化为全 1（见 §3.4），所以刚开始这一层只做归一化、不额外缩放。

注意 $\varepsilon$ 的位置：它加在**根号里面、均值上面**，不是加在开方之后的分母上。有些实现是后者，数值上差别很小，但既然测试要和参考实现逐个数比对，就按作业写的来。默认值 `1e-5`。

#### 坑一：必须先 upcast 到 fp32

作业文档在这里直接给了代码骨架，要求先把输入转成 `torch.float32`，算完再转回原来的 dtype。理由是**平方那一步会溢出**。

具体一点：fp16 能表示的最大值约 65504，所以只要某个激活值的绝对值超过 256，$a_i^2$ 就直接变成 `inf`，接下来求和、开方、相除全是 NaN。bf16 的动态范围和 fp32 一样宽、不会溢出，但它只有 8 位尾数，几百上千个数累加起来精度损失很可观。两种情况都要靠升精度解决。

这是整份作业里**第一次出现"为了数值稳定而临时提高精度"这个模式**，后面还会见到：softmax 要减最大值、cross-entropy 要用 log-sum-exp 而不是先 softmax 再取对数。共同点都是——**中间量的动态范围比输入输出大得多，所以要在中间那一段额外小心。**

一个容易忽略的细节：算完一定要转回**输入的** dtype 再返回。如果直接返回 fp32，这个 tensor 会沿着残差流一路把后面所有层都拖成 fp32，混合精度训练就白做了。

#### 坑二：为什么必须加 `keepdim=True`

计算均方根的代码如下：
`rms = torch.sqrt(torch.mean(x ** 2, dim=-1, keepdim=True) + self.eps)`

结论先说：**保留那一维是为了下一步的除法能触发广播**。

归约操作（reduction，指 `mean`、`sum`、`max` 这类把一整维压成一个数的运算）默认会把被归约的那一维直接消掉。输入 `[2, 10, 512]` 在 `dim=-1` 上求平均，不加 `keepdim` 得到的是 `[2, 10]`——512 那一维没了。而广播是从右往左对齐的，`[2, 10, 512]` 和 `[2, 10]` 最右边对上的是 512 和 10，既不相等也没有一个是 1，直接抛 `RuntimeError: The size of tensor a (512) must match the size of tensor b (10)`。

加上 `keepdim=True` 之后形状是 `[2, 10, 1]`，最右边对上的是 512 和 1，广播就把那个 1 复制 512 份，于是同一个 RMS 标量被用到这个位置的全部 512 个特征上——这正是我们要的语义。

这个坑后面还会遇到两次：softmax 减最大值（§3.10）和 attention 的 mask（§3.12）都是同一个模式。**凡是"归约出一个统计量、再拿它去缩放原张量"的写法，都需要 `keepdim`。**

### 3.8 SwiGLU 前馈网络：命名绑定与数学对齐

这一节讲三件事：门控前馈网络在算什么，三个矩阵的名字怎么和公式对上（这里有个会让 `load_state_dict` 直接报错的坑），以及 $d_{ff}$ 那个 $\frac83$ 是从哪来的。

传统前馈网络是"升维 → 激活 → 降维"两个矩阵，现代大模型（Llama 3、Qwen 2.5 等）普遍改用带门控的 SwiGLU：

$$\text{FFN}(x) = \text{SwiGLU}(x, W_1, W_2, W_3) = W_2\big(\text{SiLU}(W_1 x) \odot W_3 x\big)$$

其中 $\odot$ 是逐元素乘法，SiLU（也叫 Swish）是

$$\text{SiLU}(x) = x \cdot \sigma(x) = \frac{x}{1 + e^{-x}}$$

#### 门控在做什么

关键是升维之后**兵分两路**：$W_1 x$ 过 SiLU 当作"门"，$W_3 x$ 不过激活当作"值"，两者逐元素相乘。门的每一个分量是一个接近 0 或接近 1 的系数，决定值那一路对应的通道**放行多少**。相比之下经典 FFN 的 ReLU 是一刀切——要么原样通过要么归零，而且是否通过只由这个通道自己决定。门控让"通不通过"由另一条独立的线性投影来判断。

SiLU 相对 ReLU 的差别是它平滑、且在负半轴留了一点非零值（最小值约 $-0.278$，在 $x \approx -1.28$ 处），所以不会像 ReLU 那样彻底切断梯度。

至于门控为什么有效——**没有理论解释**。提出 SwiGLU 的 Shazeer 在论文里自己写的是："We offer no explanation as to why these architectures seem to work; we attribute their success, as all else, to divine benevolence."（我们无法解释这些架构为什么有效，只能像归因其他一切那样，归因于神的恩典。）handout 引这句话是有意的：**这是一个纯经验的选择，不要给它编一套原理。** 和 §3.12 那条"别用 roofline 解释多头"是同一个毛病的两个方向——一个是编错了原理，一个是本来就没有原理。

#### 命名绑定：`w2` 不是"第二个用到的矩阵"

这是这道题唯一一个会真正咬人的地方。按数据流的顺序读代码，三个矩阵的使用次序是"门分支 → 值分支 → 降维"，很自然会想把它们叫 `w1`、`w2`、`w3`。但 handout 的公式里：

| 名字 | 形状 | 在公式里的角色 |
|---|---|---|
| $W_1$ | $d_{ff} \times d_{model}$ | 升维，结果过 SiLU，**门** |
| $W_3$ | $d_{ff} \times d_{model}$ | 升维，不过激活，**值** |
| $W_2$ | $d_{model} \times d_{ff}$ | **降维**，最后那一步 |

**$W_2$ 是降维矩阵，不是第二个被用到的矩阵。** 按数据流顺序命名的话，`w2` 和 `w3` 正好互换，而参考实现的 `state_dict` 用的是公式里这套名字。

好消息是这个错误是**响的**：$W_2$ 和 $W_1/W_3$ 的形状互为转置，`load_state_dict(strict=True)` 会当场抛 size mismatch。只有在 $d_{ff} = d_{model}$ 的退化情形下才会静默——而 $d_{ff} = \frac83 d_{model}$ 永远不等于 $d_{model}$，所以这条路是安全的。这正是 §3.3 说的"保持 `strict=True` 就是免费的命名校验和形状校验"。

#### $d_{ff}$ 取 $\frac83 d_{model}$ 并对齐到 64

实现里就一行：

```python
d_ff = round(8 / 3 * d_model / 64) * 64
```

$\frac83$ 的来历在 §3.14 算过：经典 FFN 是两个矩阵、$d_{ff} = 4d$，参数量 $8d^2$；SwiGLU 是三个矩阵，要维持同样的 $8d^2$ 就得让 $3 \cdot d \cdot d_{ff} = 8d^2$，解出 $d_{ff} = \frac83 d$。**多加一个矩阵却不让参数量涨，这样和旧模型比才公平。**

对齐到 64 的倍数纯粹是硬件考虑（矩阵乘的 tile 尺寸）。值得一提的是上面这一行用的是四舍五入而不是向上取整，它精确复现了 §3.14 那张表里 GPT-2 四个尺寸的 $d_{ff}$——包括 medium 向上舍到 2752、large 向下舍到 3392 这两个方向不一致的情形。**看到"向上舍一个、向下舍一个"不要以为是 handout 写错了，那就是 round 的行为。**

#### 实现上的小事

三个矩阵直接复用 §3.5 写的 `Linear`（不是裸 `nn.Parameter`），这样 device/dtype 处理和 `state_dict` 路径全都自动对上，属性名就是 `w1` / `w2` / `w3`，拼出来的 key 形如 `layers.0.ffn.w1.weight`。

SiLU 写成独立的 `nn.Module` 而不是内联表达式，是为了后面 handout 的 `swiglu_ablation`（对比 SwiGLU 和不带门控的 SiLU 前馈网络）能直接复用。另外 handout 明确说这里可以用 `torch.sigmoid`。理由是照定义手写 `1 / (1 + torch.exp(-x))` 在 $x$ 很负时中间量 $e^{-x}$ 会溢出：fp32 下 $x < -88$、fp16 下 $x < -11$ 就到顶了。实测 fp16 下的 $x = -11.5$：手写版给出 `0.0`，而 `torch.sigmoid` 给出 $1.013\times10^{-5}$，也就是正确值。`torch.sigmoid` 在负半轴改用等价的 $e^{x}/(1+e^{x})$，指数的自变量始终为负，永远不会溢出。**又一次"输入输出都温和、只有中间量越界"**，和 §3.7、§3.10 是同一个家族。

`pytest tests/test_model.py -k "swiglu or silu"` → **2 passed**。

### 3.9 RoPE：用旋转编码相对位置

RoPE 的核心是将绝对位置信息转化为特征在复数平面上的旋转角度，使得 Query 和 Key 的内积能自然体现它们的相对位置。

**核心数学公式：**

对于位置 $i$ 上的向量，把相邻两维看成一对 2D 向量，旋转一个正比于 $i$ 的角度：

$$R^i_k = \begin{pmatrix} \cos\theta_{i,k} & -\sin\theta_{i,k} \\ \sin\theta_{i,k} & \cos\theta_{i,k}\end{pmatrix}, \qquad \theta_{i,k} = \frac{i}{\Theta^{(2k-2)/d}}$$

（注：$i$ 是序列中的位置索引，$k$ 是维度对的索引，$\Theta$ 通常默认 10000）。

利用旋转矩阵的角度可加性，内积结果只与两者的相对距离相关，优雅地消去了绝对位置：
$$\langle R_i q,\ R_j k \rangle = q^\top R_{j-i}\, k$$

1. **打表预计算，并且必须 `register_buffer(..., persistent=False)`**

   不要构造完整的 $d \times d$ 旋转矩阵，在 `__init__` 里算一张形状 `(max_seq_len, d_k/2)` 的 `cos` / `sin` 表就够了。挂载方式是 `self.register_buffer("cos_cached", cos_tensor, persistent=False)`，两个部分各解决一个问题。

   **`register_buffer` 解决设备搬迁**：写成普通属性 `self.cos_cached = ...`，它只是个 Python 属性，`model.to('cuda')` 不会带上它，forward 时报 `Expected all tensors to be on the same device`。注册成 buffer，PyTorch 才知道它属于这个模型。

   **`persistent=False` 解决 `state_dict` 对账**：注册的 buffer 默认会进 `state_dict`（这个默认是为 BatchNorm 的均值方差这类真状态设计的）。但 cos/sin 是由构造参数唯一决定的常数，参考实现不会存它们。于是测试里 `load_state_dict(reference_weights, strict=True)` 时，你的模型要 `cos_cached`、给的字典里没有，直接 `RuntimeError: Missing key(s) in state_dict: "cos_cached", "sin_cached"`。

   > 注意报的是 **Missing** 而不是 Unexpected，这两个方向很容易记反：**Missing 是"你的模型要、字典里没有"，Unexpected 是"字典里有、你的模型不认识"**。

   所以 `persistent=False` 的含义是"跟着模型搬家，但不算资产"——享受设备自动同步，同时不参与 `state_dict` 的对账。这和 §3.3 坑 3 是同一条：**由形状唯一决定的常量不该进 `state_dict`。**

2. **相邻配对**：本作业的数学定义要求**相邻配对** `(0,1), (2,3), (4,5)...`，不是某些开源模型用的"前半段配后半段"。两种配法都自洽，但和参考实现不一致就逐个数对不上。

3. **旋转用 flip 取反，不用显式切片**

   做 2D 旋转最简洁、也是主流开源实现采用的写法，是利用"旋转 $\theta$ = 原向量缩放 + 正交向量缩放"这个分解：

   $$(x\cos\theta - y\sin\theta,\ \ x\sin\theta + y\cos\theta) = \cos\theta\,(x, y) + \sin\theta\,(-y, x)$$

   而 $(-y, x)$ 正是原向量转 90° 的结果，用 `x_pairs.flip(-1) * [-1, 1]` 一步就能造出来。于是整个旋转就是 `x_pairs * cos + x_rot90 * sin`，不需要把两个分量切出来分别算，也省掉了 `torch.stack`。最后用 `rearrange(..., '... k xy -> ... (k xy)')` 拍回原形状。
4. **下标约定：讲义和代码用了两套起点**

   这是我在这道题上耗掉时间最多的地方，而且它不是数学问题，纯粹是记号问题。

   讲义的 $k$ **从 1 开始**（$k \in \{1,\dots,d/2\}$），所以指数写作 $(2k-2)/d$。但代码里生成这串指数最自然的写法是从 0 开始数，指数就变成了 $2k/d$。

   **两者数值完全一样**：讲义 $k=1$ 时指数为 0，代码第一个元素也是 0；讲义 $k=2$ 时是 $2/d$，代码第二个也是 $2/d$。令 $k' = k-1$ 即可互相转换。

   但如果注释里不写清楚用的是哪一套，过两天回头看就会怀疑自己写错了公式。**解决办法不是在每行注释里重复解释，而是在类的开头声明一次**：

   ```
   下标约定（全类统一，均 0-indexed）：
     i   位置          0 .. max_seq_len-1
     k   维度对编号     0 .. d_k/2-1     讲义用 1..d_k/2，讲义的 (2k-2) 即此处的 2k
     c   对内分量       0 或 1           一对 (x, y) 的两个坐标

   角度定义：theta[i, k] = i / Theta ** (2k / d_k)
   ```

   声明之后，逐行注释就能直接写成 `inv_freq[k] = ...`、`freqs[i, k] = ...` 这种带下标的形式。**把二维表的两个轴写进注释，比写一个孤零零的标量公式清楚得多**——读者一眼就知道哪个轴是位置、哪个轴是频率。

   还有一条容易忽略的：**einops 的轴名必须和这套术语一致**。如果同一个长度为 $d_k/2$ 的轴，在查表那两行叫 `half_k`、在拆分那行叫 `n`，einops 的自文档化价值就打了对折。顺带一个命名建议：那个长度为 2 的轴与其叫 `c`，不如叫 `xy`——它字面上就是被旋转的二维向量的两个坐标，`"... (k xy) -> ... k xy"` 几乎不需要注释。

   这件事让我修正了对 §3.2 那句 "documentation is implementation" 的理解：**它不是"用了 einops 就自动获得"的，而是要把轴名当作一套术语来维护**——统一起点、统一命名、在一个地方声明。工具让这件事变得可能，纪律还得自己上。

5. **精度：哪一步必须 fp32，哪一步可以降**

   这里必须把两件事分开看，它们的要求完全不同：

   | | 精度要求 | 为什么 |
   |---|---|---|
   | **算角度表**（`arange` × `inv_freq`，取 cos/sin） | **必须 fp32** | 见下 |
   | **应用旋转**（乘 cos、乘 sin、加减） | bf16 完全没问题 | 就是几次乘加，动态范围很小 |

   角度表必须 fp32 的理由比"防止溢出"更硬：**bf16 只有 8 位有效精度，能精确表示的整数上限是 256。** 也就是说位置索引超过 256 之后就开始丢值，位置 1000 和 1001 可能变成同一个数，位置编码直接废掉。（fp16 好一点，上限 2048，但对 32K 上下文照样不够。）

   这也是 HuggingFace 的实现把 `inv_freq` 固定注册成 fp32、并在这段专门禁用 autocast 的原因。

   而旋转那一步在 bf16 下做乘加毫无问题。所以正确的做法是：**表用 fp32 存，用的时候把 cos/sin 降到输入的 dtype，全程不要把 `x` 升上去**——方向反了，内存带宽的开销差一倍。

   还有一个连带的坑：如果模块里除了 cos/sin 还有别的常量 buffer（比如 flip 写法需要的符号向量），**三者的 dtype 处理必须一致**。我一开始让符号向量跟着构造参数走、又忘了在 forward 里转换，结果 bf16 输入会被静默提升成 fp32 返回——测试跑的是 fp32，两边碰巧一致，照样绿。又一次「绿灯 ≠ 证明」。

   **复数写法为什么被锁死在 fp32**：PyTorch 的复数 dtype 只有 `complex32`（fp16 分量，beta，很多算子未实现）、`complex64`、`complex128`——**没有任何一个以 bf16 为分量**。`view_as_complex` 遇到 bf16 直接抛错，而且它还要求最后一维正好是 2 且内存连续，前面做过 `rearrange` 的话可能要额外拷贝一次。这是硬约束，不是"支持得不够好"的程度问题，也是复数写法在工业界不被采用的第一原因。

   **fp8 是另一回事**：现在的 fp8 训练方案里，fp8 只用在**矩阵乘法的输入**上（线性层、$QK^\top$、$\text{attn}\cdot V$），RMSNorm、RoPE、softmax、残差相加全都跑在 bf16 或 fp32。原因是逐元素运算是 memory-bound，瓶颈在带宽不在算力，用 fp8 没有好处，而且它们恰恰是数值最敏感的地方。

   顺带纠正一个容易望文生义的说法：**RoPE 用不到 Tensor Core**。它是纯逐元素运算，Tensor Core 是矩阵乘法单元，任何 dtype 下都轮不到它。升精度的真实代价只有一条——内存带宽翻倍。

   最后：**这份作业里怎么写都能跑过**，因为测试是 fp32 的。上面这些是到真机上训练才会咬人的东西。这和 §2.7 教训 1「测量规模决定结论」是同一个主题——**同一个模块，玩具规模和生产规模的最优解不一样**。


### 3.10 Softmax：为什么要先减最大值

softmax 把一串分数变成一个概率分布：

$$\text{softmax}(v)_i = \frac{\exp(v_i)}{\sum_{j} \exp(v_j)}$$

直接按这个式子写会炸。问题出在 $\exp$ 上——**它的输出动态范围远大于输入**，而浮点数的上限是有限的：

| dtype | 能表示的最大值 | $\exp(x)$ 溢出的阈值 |
|---|---|---|
| fp32 / bf16 | ≈ $3.4 \times 10^{38}$ | $x > 88.7$ |
| fp16 | 65504 | $x > 11.1$ |

注意力分数是 $q \cdot k / \sqrt{d_k}$，正常训练时大多在个位数到几十，但**训练早期或初始化不好时冲到 88 以上完全可能**；fp16 下 11 这个阈值更是随手就能突破。一旦 $\exp$ 溢出成 `inf`，分子分母都是 `inf`，相除得到 `NaN`，整个前向就毁了。

**解法：先把每个元素减去这一维的最大值。**

这么做不改变结果，因为 softmax 有**平移不变性**——给所有输入同时加一个常数 $c$，分子分母会同时乘上 $e^c$，约掉了：

$$\frac{\exp(v_i - c)}{\sum_j \exp(v_j - c)} = \frac{e^{-c}\exp(v_i)}{e^{-c}\sum_j \exp(v_j)} = \text{softmax}(v)_i$$

取 $c = \max_j v_j$ 之后有两个好处：

- **最大项恰好变成 $\exp(0) = 1$**，其余都 $\le 1$，**上溢彻底不可能发生**。
- **分母至少是 1**（因为最大项贡献了 1），不会出现"分母下溢成 0"导致的除零。

至于下溢——那些远小于最大值的项 $\exp(\text{很负的数})$ 会变成 0。**这是安全的**：它们本来的概率就接近 0，舍入成 0 不影响结果。

#### 实现上的两个点

**减的必须是"做 softmax 的那一维"的最大值，而且要 `keepdim=True`。** 这和 RMSNorm 那个坑（§3.7）是同一件事：归约会消掉一维，不保留就没法广播回去。**同一个模式在这一章出现了第二次**，后面 attention 的 mask 还会再遇到。

**警惕一整行全是 $-\infty$ 的情况。** 如果某一行的所有位置都被 mask 掉了，那这一行的最大值是 $-\infty$，$-\infty - (-\infty) = \text{NaN}$，softmax 直接产出一整行 NaN。

因果掩码不会触发这个（第 $i$ 行至少能看到自己），但**带 padding 的批处理会**——一个全是 padding 的位置就是这样。这份作业里不会碰到，但它是真实训练里非常经典的一个 NaN 来源，值得先知道。

#### 这是一个反复出现的模式

到这里，"为了数值稳定而在中间步骤额外小心"已经是第三次出现了：

| 位置 | 危险的中间量 | 手段 |
|---|---|---|
| RMSNorm（§3.7） | $a_i^2$ 会溢出低精度 | 先升到 fp32 再算 |
| **softmax（这里）** | $\exp(v_i)$ 会溢出 | 先减去最大值 |
| cross-entropy（§4.1） | 先 softmax 再取 log，两次误差叠加 | 合成一个 log-sum-exp 一步算完 |

共同点是：**输入和输出都很温和，只有中间量的动态范围爆炸。** 所以看到 $\exp$、平方、除法这类会放大动态范围的运算时，就该条件反射地问一句"中间量会不会越界"。

顺带一提，`torch.softmax` 内部就是这么做的——自己实现一遍的价值在于知道它为什么这么做。

### 3.11 Scaled Dot-Product Attention

这一节写的是注意力的**纯计算引擎**：给定 Q、K、V 和一个 mask，按公式算出结果，不管位置编码、不管有几个头。这层的接口设计直接决定了下一节的多头能不能一行不改地复用它，所以除了公式本身，"它不该管什么"和"它该管什么"一样重要。

$$\text{Attention}(Q,K,V)=\text{softmax}\!\left(\frac{QK^\top}{\sqrt{d_k}}+\text{Mask}\right)V$$

形状是 `q: ... queries d_k`、`k: ... keys d_k`、`v: ... keys d_v`，输出 `... queries d_v`。这里用 `einsum` 而不是 `@`，因为前面那个 `...` 里可能只有 batch、也可能还塞了 heads（§3.12 就会多塞一维进来），而 `einsum` 按轴名对齐，根本不需要关心到底有几个前导维度。

#### 三个概念问题

**① softmax 沿哪个维度？——`dim=-1`，也就是 keys。**

打分矩阵是 `[..., queries, keys]`：**行 = 一个 query 对所有 key 的打分**。
"注意力"的本质是分配权重：固定一个 query，它分给所有候选 key 的权重之和必须是 1，所以要沿**列**（也就是最后一维）归一化。
沿 queries 归一化没有意义——那会变成"所有 query 对同一个 key 的竞争"，不是 attention 的语义。

**② mask 为什么必须是 $-\infty$，不能相乘。**

直觉上"把不该看的位置乘 0"是错的：

$$\text{softmax 之前置 } 0 \;\Longrightarrow\; e^{0}=1$$

被乘成 0 的位置在 softmax 里得到的是 $e^0=1$，**不但没被屏蔽，反而拿到了不小的权重**——比那些真实得分为负的位置还高。要让 softmax 输出 0，必须在**进 softmax 之前**把它变成 $-\infty$（$e^{-\infty}=0$），用 `masked_fill`。

> ⚠️ mask 的布尔约定要**去测试里核对**：`True` 是"保留"还是"屏蔽"，两种约定都有人用，弄反了整个注意力就翻过来了。这属于"契约不在类型里、只在文档/测试里"的一类坑。

**③ RoPE 不在这一层。**

这个函数是**纯计算引擎**：给我 Q、K、V 和 mask，我按公式算。至于 Q、K 有没有加绝对位置编码、有没有做 RoPE 旋转、有没有 ALiBi 偏置——它一概不问。

RoPE（§3.9）是在 **MultiHeadAttention 内部、投影和切头之后、调用本函数之前**，**只对 Q 和 K** 施加的。保持这层的纯粹性，换位置编码方案时这个函数一行都不用改。

#### 踩过的四个坑

| # | 写法 | 问题 |
|---|---|---|
| 1 | `/ Tensor.sqrt(v.dim[-1])` | `.dim` 是**方法**、返回维度**个数**不是大小，要 `.shape[-1]`；`Tensor.sqrt` 吃张量不吃 int，标量用 `math.sqrt`。另外公式里是 $\sqrt{d_k}$，该取 `q.shape[-1]`——虽然通常 $d_k=d_v$，但取 v 是**恰好对而不是真的对** |
| 2 | `maskQK = mask * QK` | 见上面 ②，$e^0=1$ |
| 3 | 没判断 `mask is None` | 推理时不传 mask，`None * QK` 直接 `TypeError` |
| 4 | 算了 `maskQK` 却把 `QK` 传进 softmax | **算了没用**。这类 bug 最阴——不报错，结果只是"看起来差不多"，得靠测试或对拍才发现 |

第 1 和第 4 条有个共同教训：**"恰好对"和"真的对"要分开**。`v.shape[-1]` 在 $d_k=d_v$ 时给出正确的数，但理由是错的；哪天用了 $d_k \neq d_v$ 的变体（比如 MQA/GQA 里 V 的维度不同）就会静默出错。

#### 这一层的接口设计值得单独记

`scaled_dot_product_attention` 的形状签名全用 `...` 泛化前导维度，带来一个后面直接兑现的好处：**MultiHeadAttention 把 heads 切出来当成一个额外的前导维度之后，可以原样调用它，一行都不用改**——`heads` 被自动当作 batch 处理。

这是"**让底层组件对上层的组织方式无知**"的一个具体例子，和 §2 里那个模块级预编译的 GPT-2 正则能同时被 BPE 训练和 `encode` 复用是同一种性质：**接口只承诺自己那一层的语义，不假设调用方怎么组织数据。**

### 3.12 Multi-Head Self-Attention：公式与形状

#### 为什么要从单头变成多头

**一个 head 只能表达一种关注方式。** 因为它的输出是 V 的加权平均，而 softmax 强制权重和为 1，所以**注意力是零和的**——多看一个地方，必然少看另一个。

但一个 token 常常需要**同时**获取性质完全不同的信息。例如

> The keys that I lost **were** on the table.

`were` 既需要 `keys`（主谓一致，决定用 were 不是 was），又需要 `table`（语义）。两者毫无关系，却共用同一份 1.0 预算：

| 权重分配 | 输出 | |
|---|---|---|
| 全给位置1 | `[1.0, 0, 0, 0]` | 语义丢了 |
| 全给位置3 | `[0, 0, 1.0, 0]` | 语法丢了 |
| 各 0.5 | `[0.5, 0, 0.5, 0]` | **两个都只剩一半，都糊了** |

这就是 Vaswani 原文那句 **"With a single attention head, averaging inhibits this."**

**修法是并排做 $h$ 次，每次有自己独立的 1.0 预算**，最后拼接起来，于是两种信息都能拿到满强度。

**但朴素做法要 $h$ 倍参数和计算**，于是让每个头只在 $d_k=d_{\text{model}}/h$ 维里工作，$h \times d_{\text{model}}/h = d_{\text{model}}$，总量回到原来。

> **逻辑顺序别搞反**：想要的是「$h$ 套互不竞争的注意力分布」（表达力）；**切分只是把成本压回单头水平的手段**，不是目的。所以 `rearrange('... seq (h d) -> ... h seq d')` 做的是「把 $d_{\text{model}}$ 个提取器分成 $h$ 组」，不是「把 token 拆开」。

#### 三处常见的误说法

| 常见说法 | 实际 |
|---|---|
| "把词向量切成 8 份分给各头" | **没有切词向量**。每个头都完整看到全部 $d_{\text{model}}$ 维，切的是 $W_Q$ 的**输出维度**（行分组）。切输入会让每个头对 $1-1/h$ 的特征全瞎（实测验证过） |
| "参数量和计算量完全一样" | 参数量和**矩阵乘** FLOPs 一样；但**打分矩阵大 $h$ 倍**（$d_{\text{model}}$=512/seq=1024 时实测 104 万 vs 838 万个元素）⇒ softmax 计算量和激活显存都是 $h$ 倍。**矩阵乘免费，softmax 和中间张量不免费** |
| "Head 1 管语法、Head 2 管语义" | 头**没有被指派角色**，大部分是多义的（polysemantic）。可解释性研究确实找到过功能明确的头（induction head、previous-token head），但那是**训练涌现，不是设计**。准确说法：**结构允许分工，训练可能产生分工** |

> ⚠️ **别用 roofline 解释"为什么多头"**。参数量和矩阵乘 FLOPs 完全相同、而多头在打分矩阵上更吃内存——一个在 compute 和 memory 上都不更优的设计，不可能是被它们驱动的。
> **判据**：先比两个方案的 FLOPs 和访存量。差很多 → 用 roofline 解释（**MQA/GQA** 是纯 KV-cache 带宽驱动、**FlashAttention** 的前提就是 attention 是 memory-bound）；几乎不差 → 它买的一定是表达力或优化性质（多头、残差、norm 的位置）。

#### 那 compute / memory 的考量在哪？——在 MQA / GQA

推理（自回归解码）时每生成一个 token 都要把之前所有的 K、V 从显存读一遍，这是**彻底的 memory-bound**：GPU 算得快，卡在等数据。缓存大小

$$\text{KV cache}=2\cdot L\cdot \text{seq}\cdot (h_{kv}\cdot d_k)\cdot B$$

实测（$d_{\text{model}}$=4096、seq=8192、32 层、fp16）：

| 方案 | Q 头 | KV 头 | KV cache |
|---|---|---|---|
| 单头（$d_k$=4096） | 1 | 1 | **4.29 GB** |
| MHA 32 头 | 32 | 32 | **4.29 GB** ← 和单头**完全一样** |
| GQA 32/8（Llama 3） | 32 | 8 | 1.07 GB |
| MQA 32/1 | 32 | 1 | 0.13 GB |

这张表里最该注意的是第二行：**多头不增加 KV cache 一个字节。** 标准多头里 $h\cdot d_k=d_{\text{model}}$，头数在式子里被彻底消掉了，所以 32 头和单头的缓存大小完全一样。

真正砍掉它的是 MQA / GQA，做法是让 $h_{kv}\cdot d_k < d_{\text{model}}$，也就是**让 K/V 的总宽度比 $d_{\text{model}}$ 还窄**。这是对"单头和多头共同基线"的偏离，不是在修多头的毛病。这又一次印证了上面那条判据：**两个方案的某项指标完全相同时，别拿这项指标去解释它们的差异。**

另一处常见误说法是"多头把大矩阵切碎，对 GPU 不友好"。实际上 Q/K/V 投影仍然是三次完整的 $d_{\text{model}}\times d_{\text{model}}$ 大矩阵乘（GEMM，即通用矩阵乘法，GPU 上效率最高的那种操作；handout 明确要求 "a total of three matrix multiplies"），切头发生在投影之后，是纯 reshape、零计算。真正被拆成一批小矩阵乘的只有 $QK^\top$ 和 $AV$ 两处，而 `h` 在那里提供的是**并行度**而不是碎片。$d_k$ 之所以普遍守在 64 或 128，真实理由是 **tile 效率**——GPU 的矩阵乘按固定大小的块（tile）调度，$d_k$ 太小时单个 tile 填不满，算力就浪费了。这和"避免切碎"是两回事。

#### handout 的三条式子（§3.4.5）

$$\text{MultiHead}(Q,K,V)=\text{Concat}(\text{head}_1,\dots,\text{head}_h)$$
$$\text{head}_i=\text{Attention}(Q_i,K_i,V_i)$$
$$\text{MultiHeadSelfAttention}(x)=W_O\,\text{MultiHead}(W_Q x,\;W_K x,\;W_V x)$$

其中 $Q_i,K_i,V_i$ 是把 $Q,K,V$ 沿 embedding 维切出的第 $i$ 片，$\text{Attention}$ 就是 §3.11 那个引擎。

| 参数 | 形状 | 说明 |
|---|---|---|
| $W_Q,\;W_K$ | $\mathbb{R}^{h d_k \times d_{\text{model}}}$ | |
| $W_V$ | $\mathbb{R}^{h d_v \times d_{\text{model}}}$ | |
| $W_O$ | $\mathbb{R}^{d_{\text{model}} \times h d_v}$ | |

作业里取 $d_k=d_v=\dfrac{d_{\text{model}}}{h}$，所以 $h d_k = h d_v = d_{\text{model}}$，**四个投影矩阵都是方阵** $d_{\text{model}}\times d_{\text{model}}$。

> 注意 $d_k=d_v=d_{\text{model}}/h$ 是**这个作业的取值**，不是定义。MQA / GQA 这类变体里 K、V 的头数比 Q 少，$h d_v \neq d_{\text{model}}$，那时上面那张形状表才显出必要性。这也是 §3.11 坑 1 说的"恰好对 vs 真的对"。

#### 关键理解一：为什么只需要三次矩阵乘，而不是 $3h$ 次

式 (13) 字面读是"每个头各做一次小投影"，但 $W_Q \in \mathbb{R}^{h d_k \times d_{\text{model}}}$ 本来就是**一整块**。把它的**输出维度**切成 $h$ 段、每段 $d_k$，得到的正是各头的投影矩阵。所以

$$\underbrace{x W_Q^\top}_{\text{一次大 GEMM}} \;\to\; [\dots,\text{seq},\,h d_k] \;\xrightarrow{\text{reshape}}\; [\dots,h,\text{seq},d_k]$$

和"做 $h$ 次小投影再堆起来"**在数学上完全相同**，但一次大矩阵乘远快于 $h$ 次小的。handout 明确要求"a total of three matrix multiplies"（Q、K、V 各一次），脚注还留了个 stretch goal：三个拼成一个更大的矩阵，只做一次。

**切头是纯粹的 reshape，不是计算。** 参数量、FLOPs 都和单头一样——多头改变的只是"这些维度如何分组做 softmax"。

#### 关键理解二：heads 维度必须放在 seq 前面

$$[\dots,\ \text{seq},\ (h\ d_k)] \;\longrightarrow\; [\dots,\ h,\ \text{seq},\ d_k]$$

因为 §3.11 的引擎把**最后两维**当作 `queries × d_k` 来算，前面的 `...` 一律视为 batch。heads 放到 `...` 里，就自动获得"每个头独立做 attention"的语义——**引擎一行都不用改**。

放成 `[..., seq, h, d_k]` 则会让引擎把 `h` 当成 queries、`d_k` 当成特征，算出来的东西毫无意义且**不报错**。

#### 关键理解三：Concat + $W_O$ ≡ 各头结果分别投影后求和

$\text{Concat}$ 得到 $[\dots,\text{seq},h d_v]$，再乘 $W_O \in \mathbb{R}^{d_{\text{model}}\times h d_v}$。把 $W_O$ 沿**输入维度**切成 $h$ 段 $W_O^{(i)}$，则

$$W_O\,\text{Concat}(\text{head}_1,\dots,\text{head}_h)=\sum_{i=1}^{h} W_O^{(i)}\,\text{head}_i$$

也就是说，各头的信息是在 $W_O$ 这一步**相加融合**的，而不是简单地并排放着。这也解释了 $W_O$ 为什么不能省：没有它，各头的输出就只是拼在一起、从头到尾没有交互过。

#### 完整形状流

| 步 | 操作 | 形状 |
|---|---|---|
| 0 | 输入 $x$ | `... seq d_model` |
| 1 | 三次投影 | 各 `... seq d_model`（即 `... seq (h d_k)`） |
| 2 | 切头 `... seq (h d) -> ... h seq d` | `... h seq d_k` |
| 3 | **RoPE 只作用于 Q、K** | 不变 |
| 4 | 因果 mask + §3.11 引擎 | `... h seq d_v` |
| 5 | 合头 `... h seq d -> ... seq (h d)` | `... seq d_model` |
| 6 | $W_O$ | `... seq d_model` |

#### 两条 handout 明写的约束

**① 因果 mask**：位置 $i$ 只能看 $j \le i$。用 `torch.triu` 或广播的下标比较造出来，然后**直接交给 §3.11 的引擎**——它已经支持 mask，不要在这里另写一套屏蔽逻辑。
mask 形状是 `seq × seq`，要能广播到 `... h seq seq`（heads 之间共用同一个 mask）。

**② RoPE 只给 Q、K，不给 V**，而且 **head 维度当作 batch 处理**——每个头施加的是**完全相同**的旋转。
理由：RoPE 编码的是**位置**，位置是 token 的属性，与"第几个头"无关。V 不参与打分（打分只由 $QK^\top$ 决定），所以旋转 V 没有意义。

> 为什么"旋转 Q 和 K"能编码**相对**位置：RoPE 让 $\langle R_m q,\ R_n k\rangle$ 只依赖 $m-n$（§3.9）。而 attention 的打分正是 $q\cdot k$ ⇒ 位置信息以相对形式进入打分，V 完全不受影响。

#### 因果 mask 建在哪：`__init__` 还是 forward

三种做法在生产里都跑过，所以问题不是"哪个对"，而是"什么决定了选哪个"：

| 做法 | 代表 | 建的次数 |
|---|---|---|
| `__init__` 预建 buffer，forward 切片 | GPT-2（`register_buffer("bias", tril(...))`，用时 `[:,:,:T,:T]`） | 一次 |
| forward 现造 | Llama 参考实现，每次 `full + triu` | 每步每层 |
| **根本不物化** | FlashAttention / `F.scaled_dot_product_attention(is_causal=True)` | 从不 |

**判据只有一条：mask 依赖形状，还是依赖数据？**

纯因果 mask 只依赖 `seq_len` 这一个整数，是完全静态的，所以可以预建；而 padding、sliding window、packed sequence 这几种 mask 依赖当前这一批数据长什么样，只能在 runtime 造。

而真实模型几乎总要把两者相与，所以 Llama 走 runtime **不是因为预建不好，是因为它的 mask 本来就不是纯静态的**。

**预建的代价在层数上**（bool，$O(L^2)$；对比 RoPE 表的 $O(L\,d_k)$）：

| $L$ | 单个 mask | ×32 层 | RoPE 表（$d_k{=}128$） |
|---|---|---|---|
| 256 | 64 KB | 2 MB | 32 KB |
| 8192 | 64 MiB | **2 GiB** | 4 MB |

mask 是 $L$ 的平方、RoPE 表是线性，所以序列一长，两者的代价就完全不是一个量级。**结论是：要预建也该在模型级共享一份，而不是每层各存一份。**

两条延伸：

- **GPT-2 的 `attn.bias` 最初忘了 `persistent=False`**，那个下三角矩阵被写进了 checkpoint，HF 至今要在 `_keys_to_ignore_on_load_missing` 里过滤。呼应 §3.3 坑 3——**由形状唯一决定的常量不该进 state_dict**。
- **显式 mask 张量和 FlashAttention 互斥。** FlashAttention 的全部意义是永不物化 $S\times S$ 的打分矩阵；你递给它一个 $S\times S$ 的 mask，就把 $O(S^2)$ 显存搬了回来。所以现代接口把因果性表达成一个 **flag**，让 kernel 在分块循环里用下标比较跳过。

**本作业的选择**：§3.11 的引擎只接受物化的张量，第三条路关掉了。而 forward 里 `x.shape[-2]` 唾手可得 ⇒ **不需要从 `__init__` 传 `max_seq_len` 进来**——非 RoPE 那条适配器恰好也不传它。

> 教训：差点把一个 forward 里本来就有的信息，改成从构造函数传入。**信息在哪一层可得，就在哪一层取**；往上提会凭空制造一个"那条路径没有这个参数"的问题。

#### mask 的两种约定：布尔 vs 加性浮点

PyTorch 的 SDPA 两种都支持，**而它们的"保留"值正好相反**：

| | 布尔 | 加性浮点 |
|---|---|---|
| 写法 | `masked_fill(~mask, -inf)` | `scores + mask` |
| **保留** | `True` | **`0.0`** |
| 代表 | nanoGPT、PyTorch 默认 | HF Transformers 传统实现 |

**最阴的坑**：`mask == False` 对浮点张量的含义是 `mask == 0.0`。所以一个标准加性 mask 传进来，会被**完全反向**解读——该保留的全屏蔽、该屏蔽的全放行，**且不报错**。用 `~mask` 代替 `mask == False`，float 会直接抛异常。

另外三条：

- **HF 用 `torch.finfo(dtype).min` 而不是 `-inf`**（`-inf` 参与算术易出 NaN）。但它自己有坑：因果 mask + padding mask 都用 `finfo.min`，**相加会溢出成 `-inf`**。
- **mask 必须加在 `/√d_k` 之后**，否则连 mask 值一起被除。用 `finfo.min` 时除完仍极负，所以"看起来对"——又一个"恰好对"。
- **整行全屏蔽 → NaN**：`x_max = -inf`，`x - x_max = -inf - (-inf) = nan`。纯因果不会触发（对角线保底），**一旦叠加 padding mask 就会**。

**布尔是加性的特例**（bias 只取 0 或 $-\infty$）。加性能表达布尔表达不了的东西——**ALiBi** 的距离斜坡、**T5 的相对位置偏置**，这些是"部分抑制"而非"完全屏蔽"。业界的分化由此而来：只做因果就用布尔（或干脆不物化），要注入位置偏置就用加性。

#### 一次静态扫描：六个静默失败

MHA 写完后做的一次通读，抓到六个**测试不一定能拦住**的问题。列在这里不是为了记结论，是为了记**它们的共同结构**。

| # | 症状 | 机制 | 为什么哑 |
|---|---|---|---|
| 1 | RoPE 完全没生效 | 调用点 `mha(x, token_positions)` 把位置传进了 `mask` 形参 | 形参默认值让漏传合法；Int 张量进 `mask == False` 变成"屏蔽 key 0 那一列"，形状全合法 |
| 2 | **因果性泄漏** | `if mask is None: mask = causal` —— 一传外部 mask 因果性就没了 | 表现是 **loss 掉得异常漂亮**，会去怀疑 lr / 数据 / 初始化 |
| 3 | RoPE 静默跳过 | `if rope is not None and token_positions is not None` | 触发点在**下一道题**：`run_transformer_block` 的签名里没有 `token_positions`，但它要求用 RoPE |
| 4 | RoPE 旋转错位 | positions 无 head 维，右对齐时 batch 撞上 $h$ | 测试传 `[1, seq]` 才侥幸对；conftest 里 `batch = heads = 4`，传 `[batch, seq]` 会**静默算错而不是报错** |
| 5 | `*` 当逻辑与用 | bool 上结果正确，但对非 bool 静默做算术 | `&` 会直接抛类型错误 |
| 6 | RMSNorm gain 未初始化 | `torch.empty` 后没有 `ones_` | 测试一律 `load_state_dict` 覆盖它 ⇒ 全绿；从零训练第一步 NaN |

**六个里有五个的共同结构：降级路径不出声。** "参数没传就用默认"、"没有 mask 就用因果"、"没有位置就跳过 RoPE"——每一条单独看都像是贴心的容错，合起来就是一张让错误安静穿过的网。

四条可直接复用的做法：

1. **把隐含契约变成运行时断言。** 注解写了 `Bool` 但 `mask == False` 接受任何 dtype，类型系统拦不住——本作业用的 jaxtyping 只是把形状和 dtype 写进类型注解，默认并不做运行时检查。**一条 dtype 断言能让 #1 在第一次调用就崩，而不是变成一个跑得通的错数。**
2. **用运算符的类型约束代替记忆。** `&` 不接受 float、`~` 不接受 float ⇒ 选它们等于免费拿到 #5 和加性 mask 反转的防护。这比"记住要检查 dtype"可靠。
3. **缺省值应该是"补全"，不是"跳过"。** #3 的正解是位置缺省时按 `arange(seq_len)` 生成——但要知道**这只在一次喂完整序列时成立**；增量解码（KV cache）时第一个 token 的位置是 `past_len` 而不是 0，HF 就是从 `past_key_values_length` 算的。**默认值是假设，不是恒等式。**
4. **约束写在制造它的那一层。** #4 的断言该放在 MHA 而不是 RoPE：`[batch, seq]` 的 positions 对 RoPE 本身完全安全（`run_rope` 直接调用时四维对四维），**是 MHA 塞进 head 维之后才产生的风险**。写进 RoPE 会平白削弱一个更通用的组件。

最后一条对照，说明为什么值得给 mask 和 positions 补断言：

> 同一次改名（`o_proj → output_proj`、`scale → weight`），漏改适配器会让 `load_state_dict(strict=True)` **立刻抛异常并列出 missing / unexpected 的 key**；而上面六个是"跑得通但算错"。**同样是不匹配，一个有 strict 检查、一个没有，调试成本差两个数量级。**

**这六条现在的状态**：全部改掉了，而且改法基本都是按上面那四条来的——

| # | 现在是什么样 |
|---|---|
| 1 | 调用点一律用关键字传参 `mha(x, mask=..., token_positions=...)`，位置传错不可能发生 |
| 2 | 因果性改成**相与**而不是替换：`mask = mask & causal_mask`，外部再传什么都不会让因果性消失 |
| 3 | 改成断言：`assert token_positions is not None`（RoPE 启用时），从"静默跳过"变成"立刻报错" |
| 4 | positions 由 `TransformerLM` 统一按 `arange(seq_len)` 生成并逐层透传，不再由各层自己猜 |
| 5 | 逻辑与一律用 `&` |
| 6 | RMSNorm 的 gain 显式 `ones_` 初始化 |

第 2 条的改法值得单独看：原来是 `if mask is None: mask = causal`，现在是 `mask = mask & causal_mask`。**同样一行代码的位置，从"二选一"变成"叠加"，最高危的那个故障模式就从可能变成了不可能。**

### 3.13 Transformer Block 与完整 LM

到这里所有零件都齐了，这一节是组装：把两个子层拼成 block、把 $L$ 个 block 加上 embedding 和 lm_head 拼成完整模型。组装本身没什么算法，但**这一章最隐蔽的两个错误恰好都在这里**——一个是残差加错了对象（形状完全正确、不报错），一个是把 softmax 算进了模型（也不报错，只是训练变慢）。另外还记了一次重构的账：它省掉了 $L$ 次重复，同时开了一条安全性倒退，最后是怎么两全的。

#### 两条式子，和一个形状看不出来的错

handout 只给了第一个子层（式 15），第二个完全对称：

$$y = x + \text{MHA}(\text{RMSNorm}(x)) \qquad z = y + \text{FFN}(\text{RMSNorm}(y))$$

**`+` 号左边是原始的 $x$，不是 $\text{RMSNorm}(x)$。** 这是 pre-norm 最常见的实现错误，两种写法**形状完全一样、不报错**：

```
x + attn(ln1(x))          ✓
ln1(x) + attn(ln1(x))     ✗
```

"pre-norm" 的含义是 **norm 在分支内部，残差通路上什么都没有**。那条从第一层直通最后一层的加法链——**残差流（residual stream）**——全程是裸的。

#### 为什么 pre-norm 必须补一个 `ln_final`

handout 只写了要求（"additionally **requires** ... layer normalization after the final Transformer block"），没写理由。理由就是上一段：

**pre-norm** 是 $x_{l+1} = x_l + f(\text{norm}(x_l))$，残差流本身从未被归一化过，$L$ 层不断往上加，尺度随深度一路增长。这样 `lm_head` 拿到的输入尺度取决于模型有多少层，**所以必须在出口补一次归一化**。

**post-norm** 是 $x_{l+1} = \text{norm}(x_l + f(x_l))$，每层出口都被重新缩放了一遍，尺度天然有界，不需要补。

同一个性质还解释了另外两件事：pre-norm **不需要 learning-rate warmup**、能堆到几十上百层——因为从 loss 到任意一层的梯度通路上**没有 norm**，只有恒等加法。§3.4 里"pre-norm 对初始化异常鲁棒"是同一件事的第三种说法。

#### 输出必须是 logits，不是概率

Figure 1 里画了 softmax，但那画的是**模型**；这个 `nn.Module` 的返回值边界**故意划在 softmax 之前**。handout 文字说了三次 unnormalized / logits。

三个理由，第一个有具体数字：

**① `log(softmax(x))` 和 `log_softmax(x)` 数学相同、数值差很远。**
交出 logits，cross-entropy 就能走 $z_i-\max-\log\sum_j e^{z_j-\max}$ 这条路，**那些极小的概率从头到尾没有被物化过**；交出概率，下游就只能 `log(p)`，而这时 $p$ 已经被 `exp` 压过一轮了。

> fp16 的最小正规数是 $2^{-14}=6.1\times10^{-5}$。**GPT-2 词表 50257，均匀分布下每个 token 是 $2.0\times10^{-5}$——已经落进 subnormal 区。** 训练初期模型就接近均匀，这不是极端情况。再低（$<6\times10^{-8}$）直接归零，$\log 0=-\infty$，梯度全 NaN。

**② 双重 softmax 是一个会静默训练的错误。** 若模型返回概率而下游用 `F.cross_entropy`（内部自带 `log_softmax`），得到 $\text{softmax}(\text{softmax}(z))$——不报错、不 NaN、loss 还会降，只是降得很慢。

**③ 采样需要 logits。** 温度采样是 $\text{softmax}(z/T)$。从概率反推数学上可行（$p^{1/T}$ 再归一化即得），但**数值上已经损失**：下溢成 0 的 token 无论 $T$ 多大都回不来。

佐证：HF 的 `...ForCausalLM` 返回的字段就叫 `logits`；PyTorch 的 `nn.CrossEntropyLoss` 文档第一句是 "between input **logits** and target"，**它压根没有接受概率的版本**。

> 附带一条：§3.10 实现的 `softmax` 在这一层**用不上**，它的用处在生成时的采样。**"实现了一个组件"不等于"这一层要用它"。**

#### 端到端测试只告诉你"错了"，不告诉你"错在哪"

| 测试 | 失败时的信息量 |
|---|---|
| `test_embedding` 等单元测试 | **就是这个模块错了** |
| `test_transformer_lm` | 整条链某处不对（4 层 + 7 种组件） |

所以**排查顺序应该沿着"已经通过的单元测试"向"没被单独测过的部分"收敛**。到 LM 这一步，没被单独测过的只剩组装逻辑本身：子层顺序、`ln_final`、`lm_head`。

端到端的容差也被放宽了：`atol=1e-4, rtol=1e-2`，而单元测试是 `1e-5`。**误差在层间累积是正常的**，不是谁写错了。

`test_transformer_lm_truncated_input` 单独值得看：它把输入截掉一半、`context_length` 仍传完整值，测的正是 **`seq_len < context_length` 时对不对**。因为 mask 按 `x.shape[-2]` 现造、位置按 `arange(seq_len)` 生成，这道测试是**免费过的**。若当初选了"`__init__` 按 `max_seq_len` 预建 mask"，这里就必须记得切片。

#### 一次重构：把 mask 和 positions 提到顶层

`mask` 和 `token_positions` **只依赖 `seq_len`**，对整个模型是同一份，却原本被放在最内层的 MHA 里算，于是 $L$ 层要重复 $L$ 遍。改法是把构造上提到 `TransformerLM.forward`，然后逐层透传。

方向是对的（HF / Llama 就是这么做的），但**代价必须记清楚**：

| | 消除的 | 制造的 |
|---|---|---|
| 重复 | $L$ 次**运行时**执行 | **4 份源码副本**（3 个适配器 + LM） |
| 安全性 | — | **MHA 不再自带因果性** |

第二行是重点。重构刚做完时，MHA 的 `mask` 仍然是 `= None` 的可选参数，而 `mask=None` 时注意力走的是**全双向**。也就是说，**§3.12 花力气消灭的最高危故障模式（因果性泄漏）被换了个形式放回来了**——它不再是"传了 mask 就失去因果性"，而变成了"不传 mask 就没有因果性"。故障还是同一个，触发条件从"多做一件事"变成了"少做一件事"，而后者更容易发生。

**两全的改法，也是最后采用的**：把 MHA 和 TransformerBlock 的 `mask` 都变成**必填参数**（去掉默认值），只有最外层的 `TransformerLM.forward` 保留 `mask=None`——因为它自己就能造出因果 mask，缺省是"补全"而不是"跳过"。这样顶层构建一次的收益保留了，静默路径也关掉了：忘了传是当场 `TypeError`，不是一个跑得通的信息泄漏。

**规模判据**（§2.7 教训 1 的复现）：

| 配置 | 每次前向的 mask 分配 |
|---|---|
| $L{=}4$、seq$=256$（本作业） | $4\times 64$ KB —— **收益无法测量** |
| $L{=}32$、seq$=8192$ | $32\times 64$ MiB = **2 GiB 分配 churn** |

也就是说，这是一个**在当前规模上收益为零、但在生产规模上确实重要**的优化。做它没错，但要清楚**它此刻不是被测量证实的**，纯粹是照着未来的规模提前布局。

最后留一条尾巴：适配器里现在有三处复制的 `tril`。按 §3.3 记的那条原则——**"适配器里出现的每一点逻辑，都说明模块本该提供而没提供"**——这正是"MHA 不再自带因果性"的代价在别处显形。把 mask 变必填之后，安全性的窟窿补上了，但**这三份重复仍然在**，它们是这次重构没有还清的债。原则先于结论：测试全绿并没有推翻这一条。

#### 一条工作方式上的记录

这一节的多数结论来自**先跑测试、再读代码**，而不是采信任何一方的报告。实际发生过的偏差：

- 另一个 AI 报告 "5 passed"（那是 `-k "multihead or transformer"` 的子集），全量是 13 passed
- 同一份报告称重构后的结构"无懈可击"，而它引入的正是上面那条因果性倒退
- 更早还有两处硬错误：称"多头带来沉重 KV cache"（实测单头与 32 头**同为 4.29 GB**，§3.12）、称多头把大矩阵"切碎"（投影仍是三次完整大 GEMM）

**绿灯 + 自信的措辞 ≠ 正确。** 这和 §2.9 记的"绿灯不等于证明"是同一条，只是这次的绿灯来自别人。

### 3.14 资源盘点：参数量与 FLOPs（handout transformer_accounting）

这一节是 handout 的一道 5 分书面题，要求把 GPT-2 XL 尺寸的模型从头数一遍：**(a)** 参数量和 fp32 权重占多少显存、**(b)** 一次 forward 要多少 FLOPs、**(c)** 哪个组件最贵、**(d)** 换成 small / medium / large 三个尺寸这个占比怎么变、**(e)** 把上下文从 1024 拉到 16384 又怎么变。下面按这五问的顺序走，小标题里的 (a)–(e) 就是它们。

一句话预告结论：**最贵的不是注意力，是 FFN**；而且**"算多少 FLOPs"和"要跑多久"是两本不同的账**，后面会各算一遍。

#### 两条法则

```
① 矩阵乘：A(m×n) @ B(n×p)  =>  2*m*n*p  FLOPs
   (每个输出元素是一次长度 n 的点积 = n 乘 + n 加)

② 由 ① 推出的捷径：
   x[T,d_in] @ W[d_in,d_out] = 2*T*(d_in*d_out) = 2 * token数 * 参数量

   物理意义：每个 token 过一遍这个矩阵，每个参数被用一次(1乘+1加)
   => 数完参数量就等于数完了 FLOPs，不必重新列矩阵
```

符号：`V` 词表、`d` d_model、`d_ff`、`L` 层数、`T` 序列长度（= 一次 forward 里的 token 数）。

> `T` 和 `d` 是**正交的两个方向**：`T` 是"有多少个 token"，`d` 是"每个 token 多宽"。整张表里只有 `Q@K^T` 和 `scores@V` 让 `T` 出现两次——**那是 $T^2$ 的唯一来源**。

#### (a) 参数量与显存

配置（GPT-2 XL 尺寸，本作业架构）：`V=50,257  T=1,024  L=48  d=1,600  h=25  d_ff=4,288`

| 组件 | 符号 | 参数量 | fp32 显存 | 占比 |
|---|---|---|---|---|
| token_embeddings | `V*d` | 80,411,200 | 321.6 MB | 4.90% |
| q/k/v/output_proj | `4*d^2` ×L | 491,520,000 | 1,966.1 MB | 29.96% |
| w1/w2/w3 | `3*d*d_ff` ×L | 987,955,200 | 3,951.8 MB | 60.22% |
| ln1/ln2 | `2*d` ×L | 153,600 | 0.6 MB | 0.01% |
| ln_final | `d` | 1,600 | 0.006 MB | ~0% |
| lm_head | `d*V` | 80,411,200 | 321.6 MB | 4.90% |
| **总计** | | **1,640,452,800** | **6,561.8 MB** | 100% |

```
N_params = 1.64 B          fp32 权重 = 6,561.8 MB  (6.56 GB)
```

> **这只是加载权重。** 训练还要 梯度(1×) + AdamW 的 m、v(2×) = **4× ≈ 26,247 MB**，而且**还没算激活值**。§4 会用到。

```
每层 = 8*T*d^2 + 4*T^2*d + 6*T*d*d_ff   = 0.070 TFLOPs
×48                                      = 3.352 TFLOPs
lm_head = 2*T*d*V                        = 0.165 TFLOPs
总计                                      = 3.517 TFLOPs
```

**`token_embeddings` 不在表里** —— `self.weight[x]` 是查表（gather），**0 FLOPs**。
于是有一个不对称：**参数量里 `V*d` 要算两份（embedding 表和 lm_head 各一份），FLOPs 里只算一份**（只有 lm_head 真的做了矩阵乘）。这个不对称在 (d) 里是关键。

#### 化简成一行（(c)(d)(e) 全靠它）

```
N_params ≈  2*V*d  +  12*L*d^2

FLOPs    ≈  2*T*( V*d + 12*L*d^2 )  +  4*L*T^2*d
            \____________________/     \_________/
             A 类 激活×权重             B 类 激活×激活
             有参数,  线性于 T           无参数,  平方于 T
```

对照精确值：3.185 + 0.322 = 3.507 TFLOPs vs 3.517 TFLOPs，差 0.3%（因为 `d_ff=4288` 不是精确的 `(8/3)*1600=4266.7`）。

#### 三个值得单独记的结构

**① `8/3` 是从哪来的**

```
经典 FFN (ReLU, 2 矩阵, d_ff=4d) :  d*4d + 4d*d    = 8*d^2
SwiGLU   (3 矩阵, d_ff=(8/3)d)   :  3*d*(8/3)d     = 8*d^2
```

**完全相等。** SwiGLU 比经典 FFN 多一个矩阵，把系数从 `4` 降到 `8/3` 正是为了让参数量持平——这样和旧模型比才公平。handout 那句 "nearest multiple of 64 to (8/3)·1600" 就是这么来的。

于是每层 `4*d^2`(attn) + `8*d^2`(ffn) = **`12*d^2`**，**这个 `12*L*d^2` 对用不用 SwiGLU 都成立**，值得背下来。

**② FFN 的参数和算力都是注意力投影的两倍**

`8d^2` vs `4d^2`，2:1。这个比例贯穿整张表。（经典 Transformer 是 `12d^2` vs `4d^2` = 3:1。）

**③ 头数在 `Q@K^T` 里被消掉**

```
单头   :  2*T^2*d_k
h 个头 :  h * 2*T^2*d_k = 2*T^2*(h*d_k) = 2*T^2*d
```

因为 `h*d_k = d_model` 恒成立。**和 §3.12 里 KV cache 与头数无关是同一个原因**——凡是"每头一份、再加起来"的量，都和 `h` 无关。

#### 四大块的占比（GPT-2 XL, T=1024）

| 块 | 符号 | TFLOPs | 占比 |
|---|---|---|---|
| **FFN** | `2*T*8*L*d^2` | **2.023** | **57.5%** |
| Attention 投影 (QKVO) | `2*T*4*L*d^2` | 1.007 | 28.6% |
| Attention 打分 (QK^T, AV) | `4*L*T^2*d` | 0.322 | 9.2% |
| lm_head | `2*T*d*V` | 0.165 | 4.7% |

**(c) 的答案在这张表里，而且它是反直觉的**：最贵的是 **FFN（57.5%）**，不是注意力。而"真正的注意力计算"（那两次激活×激活）**只占 9.2%**——在 `T=1024` 这个长度上，Transformer 主要是一台矩阵乘机器，注意力只是配角。

> 这也解释了为什么 MoE（mixture of experts，把一个大 FFN 换成许多个小 FFN、每个 token 只激活其中几个）首先动的是 FFN 而不是注意力：那里才是 FLOPs 的大头。

#### Arithmetic intensity：FLOPs 占比 ≠ 时间占比

上面那张表**只回答了"算多少"，没回答"要多久"**。两者不等价，因为 GPU 可能卡在搬数据上而不是算数上。

```
Arithmetic Intensity (AI) = FLOPs / 从 HBM 搬运的字节数   [FLOP/byte]

Roofline:  AI > 机器平衡点  =>  compute-bound  (算力吃满，搬运不是瓶颈)
           AI < 机器平衡点  =>  memory-bound   (算力闲着等数据)

机器平衡点 = 峰值算力 / 显存带宽
  A100 :  312 TFLOP/s (bf16) / 2.03 TB/s  ≈ 154 FLOP/byte
  H100 :  989 TFLOP/s (bf16) / 3.35 TB/s  ≈ 295 FLOP/byte
```

把表里三类操作各自算一遍（bf16，2 字节/元素；假设每个张量只过一次 HBM）：

| 操作 | FLOPs | HBM 字节 | AI 公式 | AI @ XL, T=1024 | A100 判定 |
|---|---|---|---|---|---|
| 投影 `x@W` | `2Td^2` | `2(2Td + d^2)` | `Td/(2T+d)` | **449** | compute-bound |
| FFN `x@W1` | `2Td·d_ff` | `2(Td + d·d_ff + T·d_ff)` | `Td·d_ff/(Td+d·d_ff+T·d_ff)` | **545** | compute-bound |
| 打分 `Q@K^T` | `2T^2 d` | `2(2Td + hT^2)` | `Td/(2d + hT)` | **57** | **memory-bound** |

**结论和 FLOPs 表正好相反的地方：**

- FLOPs 上，注意力打分只占 **9.2%**，看着无关紧要
- AI 上，它是**唯一一个掉到平衡点以下的**（57 < 154），也就是**唯一一个在等数据而不是在算**的部分

合起来的结论是：**它占用的墙钟时间远远超过那 9.2%。** 这就是 FlashAttention 存在的定量理由——它不减少 FLOPs（一个都不减），它减少的是**那个 `[h,T,T]` 中间张量在 HBM（显存）和芯片之间的往返次数**。

原因在字节数那一列：`Q@K^T` 要写出的 scores 是 `h*T^2 = 25 × 1024² = 2621 万`个元素，而它读进去的 Q 只有 `T*d = 164 万`——**输出比输入大 16 倍**。这正是 §3.12 那条"打分矩阵是 h 倍大"的代价，在 roofline 上的显形。

> 上表还**低估**了问题：朴素实现要把 scores 写出去、读回来做 softmax、再写出去、再读进来做 `@V`，是 4 趟 HBM 往返，实际 AI 比 57 还低。FlashAttention 把这些合并在 SRAM 里做，一趟都不写。

**同一个 T=1024 的矩阵，换个场景就翻转：**

```
训练 / prefill (T=1024) :  AI = Td/(2T+d) = 449   => compute-bound   (prefill = 生成第一个 token 前把整段提示词一次性过一遍)
推理 decode  (T=1)      :  AI = 1·d/(2+d) ≈ 1.0   => 极度 memory-bound
```

**同一份权重、同一个 kernel，只因为一次处理的 token 数从 1024 变成 1，就从算力受限变成带宽受限。** 这是自回归生成慢的根本原因，也是推理必须攒 batch、以及 KV cache（§3.12）成为核心瓶颈的原因。

> **和 §3.12 那条 roofline 判据的对照**：那里说"两个方案 FLOPs/参数量完全相同时，compute/memory 的论证无法区分它们"——那是**误用**（单头 vs 多头）。这里是**正用**：FFN 和注意力打分的 FLOPs 不同、AI 也不同，roofline 确实能区分。
> **同一个工具，区别在于被比较的两者在相关量上是否真的有差异。**

#### (d) 四个尺寸横向对比（`T=1024` 固定）

`d_ff` = nearest multiple of 64 to `(8/3)d`，注意 medium 向上舍、large 向下舍：

| 模型 | L | d | h | (8/3)d | d_ff | 参数量 | fp32 |
|---|---|---|---|---|---|---|---|
| small | 12 | 768 | 12 | 2048.0 | 2048 | 162.1 M | 648.6 MB |
| medium | 24 | 1024 | 16 | 2730.7 | 2752 | 406.5 M | 1,626.2 MB |
| large | 36 | 1280 | 20 | 3413.3 | 3392 | 833.6 M | 3,334.4 MB |
| XL | 48 | 1600 | 25 | 4266.7 | 4288 | 1,640.5 M | 6,561.8 MB |

一次 forward 的 FLOPs 与四块占比：

| 模型 | 总 TFLOPs | attn 投影 | attn 打分 | FFN | lm_head |
|---|---|---|---|---|---|
| small | 0.292 | 0.058 (19.9%) | 0.039 (**13.3%**) | 0.116 (39.8%) | 0.079 (**27.1%**) |
| medium | 0.830 | 0.206 (24.8%) | 0.103 (12.4%) | 0.416 (50.0%) | 0.105 (12.7%) |
| large | 1.769 | 0.483 (27.3%) | 0.193 (10.9%) | 0.960 (54.3%) | 0.132 (7.4%) |
| XL | 3.517 | 1.007 (28.6%) | 0.322 (**9.2%**) | 2.023 (**57.5%**) | 0.165 (**4.7%**) |

**四条趋势，全部由次方决定**（`T` 固定，看对 `d` 的次方）：

```
attn 投影 :  8*T*d^2 * L    -> d 的 2 次方        占比 涨   19.9% -> 28.6%
FFN       :  6*T*d*d_ff * L -> d 的 2 次方        占比 涨   39.8% -> 57.5%
attn 打分 :  4*T^2*d * L    -> d 的 1 次方        占比 跌   13.3% ->  9.2%
lm_head   :  2*T*d*V        -> d 的 1 次方, 无 L  占比 崩   27.1% ->  4.7%
```

- **`lm_head` 塌得最狠（÷5.8）**：分子只有 `V*d`，而 `V=50,257` 是**固定**的，只随 `d` 线性增长；分母的主体 `12*L*d^2` 却是 `L` 和 `d^2` 一起涨。小模型里输出层是四分之一的算力，到 XL 只剩二十分之一。
- **`attn 打分` 缓跌**：它只有 `d` 的一次方，追不上 `d^2` 的两项。

一句话概括这张表：**模型越大，Transformer 越是"一台大矩阵乘机器"**，输出层和注意力打分都在被稀释。

**一个与 `L` 无关的不变量**（这条比上面四行更有用）：

```
打分 / 投影 = 4*L*T^2*d / (8*L*T*d^2) = T / (2*d)

small  : 1024/1536 = 0.667   实测 13.25/19.88 = 0.667  ✓
XL     : 1024/3200 = 0.320   实测  9.16/28.62 = 0.320  ✓
```

**层数完全约掉了。** 注意力打分相对于其余部分的分量，**唯一的自变量是 `T/d`**，和模型有多少层无关。

#### (e) XL 把上下文拉到 16,384

`T: 1024 → 16,384` 是 ×16。但两类项吃到的倍数不同：

| 块 | 关于 T | 倍数 | T=1024 | **T=16,384** |
|---|---|---|---|---|
| attn 投影 | `∝T` | ×16 | 1.007 (28.6%) | 16.106 (12.1%) |
| FFN | `∝T` | ×16 | 2.023 (57.5%) | 32.373 (24.2%) |
| lm_head | `∝T` | ×16 | 0.165 (4.7%) | 2.635 (2.0%) |
| **attn 打分** | **`∝T^2`** | **×256** | 0.322 (9.2%) | **82.463 (61.7%)** |
| **总计** | | **×38.0** | **3.517** | **133.578** |

```
总 FLOPs:  3.517 -> 133.578 TFLOPs   =  ×37.98    (不是 ×16)
attn 打分占比:  9.2%  ->  61.7%      =  从配角变成主角
```

用不变量核对：`T/(2d) = 16384/3200 = 5.12`，而 `61.7% / 12.1% = 5.12` ✓

**交叉点**（线性项 = 平方项）：

```
2*T*(V*d + 12*L*d^2) = 4*L*T^2*d
=>  T* = V/(2L) + 6*d  ≈  6 * d_model     (V/(2L) 通常很小)

GPT-2 XL    d=1600  =>  T* ≈ 10,100
Llama-3-8B  d=4096  =>  T* ≈ 26,600
```

也就是说，**上下文长度超过大约 `6·d_model` 时，注意力的平方项就压过了整个模型的其余部分**。Llama-3 用 8K 训练还稳稳待在线性区；同一份权重跑 128K 就深在平方区了。**同一个模型，只因为上下文长度不同，瓶颈就换了部件。**

> `T*` 里**没有 `L`**——线性项的 `12*L*d^2` 和平方项的 `4*L*T^2*d` 都带 `L`，约掉了。这和上面那个 `T/(2d)` 不变量是同一件事。

**再看一眼 arithmetic intensity**（上一节的公式）：

```
Q@K^T 的 AI = T*d/(2*d + h*T)

T=1024   : 1,638,400 / 28,800  = 56.9  FLOP/byte
T=16384  : 26,214,400 / 412,800 = 63.5  FLOP/byte
T->inf   : -> d/h = d_k = 64
```

**AI 略微上升，但渐近到 `d_k = 64` 就封顶了**，永远追不上 A100 的平衡点 154。

所以长上下文是**双重打击**：注意力打分既吃掉了 61.7% 的 FLOPs（(e) 的结论），又**始终是唯一 memory-bound 的部分**（arithmetic intensity 那节的结论）。**这两条是彼此独立的论证，合起来才是 FlashAttention 的完整动机。**

### 3.15 阶段性小结

**§3 全部完成**：Linear、Embedding、RMSNorm、SwiGLU、RoPE、Softmax、SDPA、MultiHeadSelfAttention、TransformerBlock、TransformerLM。`pytest tests/test_model.py` 13 passed。
**下一步**：§4 cross-entropy 与 AdamW。

从这些小题里提炼出的方法论，后面继续用：

1. **命名先行。** 模块树的属性名必须和参考实现的 state_dict 对齐。这是一个成本单调递增的决定：现在改是零成本，越晚改越贵。
2. **让错误尽早、尽响地暴露。** 用契约（签名给的维度）而不是数据（`weights.shape`）去构造模块；保持 `strict=True`；device 和 dtype 在构造时对齐。**响的错误比哑的错误便宜一个数量级。**
3. **测试覆盖不到的地方要自己兜**：初始化、device/dtype 一致性、数学不变量。这是 §2.9"绿灯不等于证明"在这一章的延续。
4. **形状断言优先于打印。** 断言让 bug 在产生的地方就炸，而不是三层之后。
5. **toy 尺寸手算。** 抽象规则看不懂的时候，造一个小到能手算的例子跑一遍（§3.6 那张 4×3 的表就是这么来的），比看十遍解释管用。
6. **"恰好对"不是"真的对"。** 已经出现三次：`v.shape[-1]` 在 $d_k=d_v$ 时对（§3.11 坑 1）、RoPE 的 positions 在测试传 `[1,seq]` 时对（§3.12）、`finfo.min` 被 $\sqrt{d_k}$ 除完仍够负。**理由错的代码会在假设变化时静默失效**，而不是报错。
7. **分层要守住**：底层组件只承诺自己那层的语义，不假设调用方怎么组织数据（RoPE 不进 SDPA、`...` 泛化前导维度让 MHA 免费复用）。反过来，**约束也要写在制造它的那一层**——head 维引起的广播风险属于 MHA，不属于 RoPE。
8. **警惕"贴心的容错"。** `if x is None: 跳过` 这类降级路径，单看都像健壮性，合起来是一张让错误安静穿过的网（§3.12 那六个静默失败里占了五个）。**缺省应该是"补全"而不是"跳过"**，补不出来就报错。
9. **让运算符替你检查类型。** `&` / `~` 不接受 float，`*` / `== False` 接受——选前者等于免费拿到一层防护，比"记得检查 dtype"可靠。
10. **优化把责任往上移时，要同时把契约收紧。** 把 mask 提到顶层构建（§3.13）省掉了 $L$ 次重复，但只要下层参数仍是可选的，就等于开了一条静默路径。**责任上移 ⇒ 下层的参数必须变必填**，否则收益是真的、倒退也是真的。
11. **绿灯不等于正确，别人的绿灯尤其。** 报告可能只跑了子集、可能对自己引入的倒退无感。**先跑全量测试、再读代码**，然后才轮到看结论。
12. **FLOPs 占比不等于时间占比。** 数完 FLOPs 只答了"算多少"，要答"要多久"必须再算一次 arithmetic intensity（§3.14）。注意力打分在 FLOPs 上只占 9.2%，在 roofline 上却是唯一 memory-bound 的部分——**优化目标应该由后者决定，不是前者。**

## 4. 训练：损失与优化器

对应 handout §4，四个小问题：cross-entropy、AdamW、学习率调度、梯度裁剪。这一章造的是"怎么改参数"的那套零件；把它们和 §3 的模型接起来跑的那部分（数据加载、checkpoint、训练循环）属于 handout §5，放在本笔记 §5。

**和前两章相比战场又变了一次。** §2 的失败模式是算法逻辑，§3 是形状和 dtype，§4 则是**数值范围和状态管理**：损失要在 $\exp$ 和 $\log$ 之间走得稳，优化器要在不多分配一份显存的前提下把四个张量原地更新对。这一章的坑几乎都不报错——loss 平平地不降、训练曲线莫名停滞几千步——所以推导要比前两章更往前站一步：**先算清楚每个量的范围和寿命，再写代码。**

### 4.1 Cross-Entropy Loss

#### 一次前向产出 $m$ 个训练信号

模型在每个位置 $i$ 吐出 logits $o_i \in \mathbb{R}^V$，$\text{softmax}(o_i)$ 就是它对"第 $i+1$ 个 token 是谁"的分布。handout 强调的那句括号注很关键：

> a single forward pass yields $p_\theta(x_{i+1}\mid x_{1:i})$ for **all** $i=1,\dots,m$

**这是因果 mask 的回报。** 位置 $i$ 看不见 $i+1$ 之后，所以每个位置都是一道合法的"预测下一个"。没有因果 mask，位置 $i$ 直接能看到答案，这 $m$ 道题**全部作废**——这就是 §3.12 那条因果性泄漏为什么是最高危故障：它不会崩，只会让 loss 掉得异常漂亮。

#### 推导一：从极大似然到 NLL

目标是让训练语料在模型眼里概率最大：

$$\max_\theta \ \prod_{i=1}^{m} p_\theta(x_{i+1}\mid x_{1:i})$$

连乘上万项极小的数必然下溢，所以取 $\log$ 把连乘变连加；而优化器只会最小化，所以再取负：

$$\min_\theta \ \sum_{i=1}^{m} -\log p_\theta(x_{i+1}\mid x_{1:i})$$

对整个数据集平均，就是 handout 式 (16)：

$$\ell(\theta;D)=\frac{1}{|D|\,m}\sum_{x\in D}\sum_{i=1}^{m} -\log p_\theta(x_{i+1}\mid x_{1:i})$$

> **交叉熵在这里不是"被挑中的损失函数设计"，它就是极大似然本身。**

#### 推导二：$p_\theta$ 到底是什么——softmax 是模型的**定义**

推导一给出的是 $-\log p_\theta(x_{i+1}\mid x_{1:i})$。但**模型的 forward 根本不输出 $p$，它输出的是 logits** $o_i\in\mathbb{R}^V$（§3.13：必须返回未归一化的 logits）。

两者的关系是**模型的定义**，不是推导出来的结论——handout 式 (17)：

$$p_\theta(x_{i+1}\mid x_{1:i}) \;:=\; \text{softmax}(o_i)[x_{i+1}] \;=\; \frac{\exp\big(o_i[x_{i+1}]\big)}{\sum_{a=1}^{V}\exp\big(o_i[a]\big)}$$

三样东西要分清：

| 记号 | 是什么 | 性质 |
|---|---|---|
| $o_i \in \mathbb{R}^V$ | forward 的原始输出 | **任意实数**，可正可负、和不为 1，**没有概率含义** |
| $\text{softmax}(o_i)$ | 归一化后的向量 | 每项 $>0$、和为 $1$，**是一个合法分布** |
| $[\,k\,]$ | 取第 $k$ 个分量 | handout 脚注 6：$o_i[k]$ = 向量 $o_i$ 的第 $k$ 个元素 |

所以 $\text{softmax}(o_i)[x_{i+1}]$ 读作：**"模型分给真实答案那个 token 的概率"**。

代回推导一：

$$\ell_i \;=\; -\log p_\theta(x_{i+1}\mid x_{1:i}) \;=\; -\log\ \text{softmax}(o_i)\big[x_{i+1}\big]$$

单个位置上简记 $o := o_i$、$t := x_{i+1}$（target 下标），就得到推导四的起点：

$$\ell \;=\; -\log\ \text{softmax}(o)[t]$$

**为什么偏偏用 softmax 做这座桥**（把实数向量变成分布的方法不止一种）：

1. **$\exp$ 严格为正**，所以分母恒大于 0、每一项也恒大于 0，外面那个 $\log$ 永远有定义
2. **配上 $-\log$ 后梯度化简成"预测减真实"**（见下面梯度一节）——这是 exp 族独有的
3. **平移不变**：$\text{softmax}(o+c\mathbf{1})=\text{softmax}(o)$

> 第 3 条不只是个漂亮性质——**它就是推导四里"减最大值"合法的根本原因**。给所有 logit 减去同一个 $M$，模型定义的那个分布**一个字都没变**，所以那不是近似、不是 trick，是恒等变形。

#### 推导三：为什么叫 "cross-entropy"

信息论定义（真实分布 $p$、模型分布 $q$）：

$$H(p,q)=-\sum_{a=1}^{V} p(a)\log q(a)$$

而语言模型在每个位置**只观测到一个 token** $t=x_{i+1}$，所以真实分布是 one-hot（handout 脚注 7 称之为 Dirac delta）：

$$p(a)=\mathbb{1}[a=t] \quad\Longrightarrow\quad H(p,q)=-\log q(t)$$

**整个求和塌成一项。** 所以"交叉熵"和"负对数似然"在这里是同一个东西，只是来自两个思想传统，名字用了信息论那个。

#### 推导四：数值稳定形式（这是要实现的）

起点是推导二的结果（$o$ 是这个位置的 logits，$t$ 是正确类别下标）：

$$\ell = -\log\ \text{softmax}(o)[t] = -\log \frac{\exp(o[t])}{\sum_{a=1}^{V}\exp(o[a])}$$

**第一步——$\log$ 和 $\exp$ 相消**（handout 的 "cancel out log and exp"）：

$$\ell = -\underbrace{\log \exp(o[t])}_{=\ o[t]} + \log\sum_{a=1}^{V}\exp(o[a]) \;=\; -o[t] + \log\sum_{a=1}^{V}\exp(o[a])$$

到这一步，**式子里再也没有 softmax 了，一个概率都不用算出来**。这正是 §3.13 说"必须交出 logits"的兑现点。

**第二步——减最大值**。令 $M=\max_a o[a]$，把 $e^M$ 提出来：

$$\log\sum_a \exp(o[a]) = \log\Big(e^{M}\sum_a e^{o[a]-M}\Big) = M + \log\sum_a \exp(o[a]-M)$$

**最终形式：**

$$\boxed{\ \ell = \big(M - o[t]\big) + \log\sum_{a=1}^{V}\exp\big(o[a]-M\big)\ }$$

#### 怎么读这个式子：两项各自在说什么

**先看 $t$ 出现在哪** —— 整个式子里**只有一处**：$o[t]$。$M$ 和那个求和都只用到完整的 logit 向量，与 $t$ 无关。

> 这就是为什么代码里 `targets` **只在 gather 那一步出现**：整数下标对损失的全部影响，都压缩在 $o[t]$ 这一个标量里。

$$\ell \;=\; \underbrace{\big(M - o[t]\big)}_{\text{正确答案比首选差多少}} \;+\; \underbrace{\log\sum_{a}\exp\big(o[a]-M\big)}_{\text{模型整体有多不确定}}$$

| 项 | 取值范围 | 含义 | 依赖 $t$？ |
|---|---|---|---|
| $M-o[t]$ | $[0,\ \infty)$ | $=0$ 表示模型的最高分**就是**正确答案；越大表示正确答案落后首选越多 | **是** |
| $\log\sum_a e^{o[a]-M}$ | $[0,\ \ln V]$ | $\to 0$ 表示某个 logit 遥遥领先（极度自信）；$=\ln V$ 表示所有 logit 相等（完全不确定） | **否** |

第二项范围的两端：所有 logit 相等 $\Rightarrow \sum = V \Rightarrow \log = \ln V$；单个 logit 独大 $\Rightarrow \sum \to 1 \Rightarrow \log \to 0$。

#### 尺度参照与 perplexity

loss 的单位是 **nats/token**，读作"模型平均每个 token 有多惊讶"。

$$\text{perplexity}=\exp\Big(\frac{1}{m}\sum_{i=1}^{m}\ell_i\Big)$$

含义：**模型实际上在多少个等可能选项之间做选择。**

| 情形 | loss (nats) | perplexity |
|---|---|---|
| 均匀瞎猜（$V=10{,}000$） | $\ln V = 9.21$ | 10,000 |
| TinyStories 训练好的小模型 | ~1.4–1.5 | ~4.1–4.5 |
| 完全确定且正确 | 0 | 1 |

> **$\ln(\text{vocab\_size})$ 是一个要认识的数字。** loss 卡在 9.21 一动不动 = 模型输出恒定、什么都没学到（§3.4 记过 gain 初始化成 0 就会这样）。看到这个数直接怀疑前向被切断，而不是去调 lr。

### 4.2 优化器：从 SGD 到 AdamW

对应 handout §4.2–§4.3。SGD 的完整代码 handout 直接给了，没有实现任务；要写的是 AdamW。

#### 谱系：先看全貌

| 年份 | 方法 | 解决了什么 | 留下什么 |
|---|---|---|---|
| 1951 | **SGD** | — | 单一全局 lr；病态曲率 |
| 1964 | **Momentum** (Polyak) | 梯度噪声与来回震荡 | 尺度问题没动 ⇒ 日后成为 Adam 的 $m$ |
| 2011 | **AdaGrad** (Duchi) | 逐参数尺度，稀疏特征受益 | 分母**无限累加** ⇒ lr 单调趋 0，深网络提前停 |
| 2012 | **RMSProp** (Hinton，**从未正式发表**，出自 Coursera 讲义) | 把累加换成滑动平均 ⇒ 窗口有限、lr 可恢复 | 没有动量 ⇒ 日后成为 Adam 的 $v$ |
| 2015 | **Adam** (Kingma & Ba) | 动量 + RMSProp + **偏差修正** | weight decay 与自适应耦合 |
| 2019 | **AdamW** (Loshchilov & Hutter) | 解耦 weight decay | 至今仍是默认 |
| 2024 | **Muon** (Keller Jordan et al.) | 逐元素预条件 → **矩阵级**谱范数最速下降 | 见本节末尾 |

> **Adam 不是什么精妙设计，是两条独立修补路线的并集**：动量治噪声、AdaGrad/RMSProp 治尺度。它唯一新增的东西是偏差修正——那是两者合并之后才必须处理的问题。

#### 符号表（后面所有公式都用这套）

| 符号 | 是什么 | 形状 | 显存 |
|---|---|---|---|
| $\theta$ | 参数本身（比如某个权重矩阵） | $[d_\text{out}, d_\text{in}]$ | **1×，常驻** |
| $g$ | 梯度 $\partial L/\partial\theta$ | 和 $\theta$ 一样 | **1×**，反向时分配 |
| $m$ | $g$ 的滑动平均 —— 一阶矩 | 和 $\theta$ 一样 | **1×，常驻** |
| $v$ | $g^2$ 的滑动平均 —— 二阶矩 | 和 $\theta$ 一样 | **1×，常驻** |
| $\alpha$ | 学习率 | 标量 | 0 |
| $\beta_1,\beta_2$ | 两个滑动平均的衰减率 | 标量，如 $0.9$ / $0.999$ | 0 |
| $\varepsilon$ | 防除零 | 标量，$10^{-8}$ | 0 |
| $\lambda$ | weight decay 系数 | 标量 | 0 |
| $t$ | 步数，从 1 开始 | 整数 | 0 |

所有运算都是逐元素的：$m$、$v$ 是和参数一样大的张量，每个参数元素都有自己的一份 $m$ 和 $v$。

**最后那列是这一节的一条暗线。** 优化器的每一样"状态"都要真金白银地占显存，而且单位是"一整份模型参数"。$\theta$、$g$、$m$、$v$ 四份加起来就是 §3.14 里那个 4×——GPT-2 XL 的权重只有 6.5 GB，可训练它需要 26 GB，激活值还没算。后面每引入一个新张量，我都会标出它值多少显存。

#### 起点：SGD 和它的两个毛病

$$\theta \leftarrow \theta - \alpha\,g$$

**毛病 ①：一个全局学习率服务所有参数。**

随便挑两个权重，梯度量级差得极远（罕见 token 的 embedding 几乎收不到信号，而 norm 的 gain 被每个样本推）：

| | 典型值 | 典型梯度 |
|---|---|---|
| $w_1$：embedding 某一行的元素 | $0.02$ | $10^{-6}$ |
| $w_2$：RMSNorm 的 gain | $1.0$ | $10^{-2}$ |

取 $\alpha=0.1$：

```
w1 移动  0.1 × 1e-6 = 1e-7      相对自身 0.02  ->  动了 0.0005%   基本冻住
w2 移动  0.1 × 1e-2 = 1e-3      相对自身 1.0   ->  动了 0.1%      正常
```

**同一个 $\alpha$，实际效果差 10000 倍。** 调大让 $w_1$ 动起来，$w_2$ 就炸；调小让 $w_2$ 稳住，$w_1$ 永远不学。

**毛病 ②：梯度是有噪的，而且损失面病态。** mini-batch 的 $g$ 只是真实梯度的一个带噪估计；再加上损失面常常一个方向陡、一个方向平（ravine），$\alpha$ 必须小到能容忍陡方向，于是平方向爬得极慢。

这两个毛病催生了**两条独立的修补路线**——毛病 ② 走出了动量，毛病 ① 走出了 AdaGrad / RMSProp。Adam 就是两条路线的合流。

> **"Transformer 用 SGD 训不好"是稳健的经验事实**，毛病 ① 是最直接的解释（embedding、attention、norm 的梯度尺度差几个数量级）。但机制上仍在争论——一派归因于语言数据重尾分布使罕见 token 梯度极小，一派归因于损失面各方向曲率高度不均。**别把任何单一解释当定论。**

#### 修补一：动量 —— 治毛病 ②

$$m \leftarrow \beta_1 m + (1-\beta_1)\,g$$

不用当前这一个 $g$，而是用最近若干步 $g$ 的平均。来回震荡的分量在平均中互相抵消，方向一致的分量不断叠加，于是噪声被抑制、有效方向被加强。

这就是 Adam 的 $m$。但要真看懂它，得先把这个递推式打开，见下一节。

**显存代价：$m$ 是常驻状态，$+1\times$。** 注意左边的 $m$ 和右边的 $m$ 是同一块内存——这个式子可以完全原地执行，不需要额外的临时张量。但这块内存从第一步分配之后就再也不能释放，因为下一步还要用。**"有状态"和"占显存"在这里是同一件事。**

#### 工具：滑动平均（EMA）到底在算什么

$m$ 和 $v$ 用的是同一个机制，讲一次就够。

**把递推式展开**（记 $\beta=\beta_1$，$m_0=0$）：

$$
\begin{aligned}
m_1 &= \beta\cdot 0 + (1-\beta)g_1 = (1-\beta)\,g_1\\
m_2 &= \beta m_1 + (1-\beta)g_2 = \beta(1-\beta)\,g_1 + (1-\beta)\,g_2\\
m_3 &= \beta m_2 + (1-\beta)g_3 = \beta^2(1-\beta)\,g_1 + \beta(1-\beta)\,g_2 + (1-\beta)\,g_3
\end{aligned}
$$

通项：

$$\boxed{\ m_t = (1-\beta)\sum_{i=1}^{t}\beta^{\,t-i}\,g_i\ }$$

换句话说，**它是过去所有梯度的加权和，权重按 $\beta$ 的幂指数衰减**——越老的梯度权重越小。

**权重具体是多少**（$\beta=0.9$）：

| 这是第几新的梯度 | 权重 |
|---|---|
| 最新 $g_t$ | $0.1$ |
| 上一步 | $0.9\times 0.1 = 0.09$ |
| 再上一步 | $0.81\times 0.1 = 0.081$ |
| 10 步前 | $0.0387$ |
| 30 步前 | $0.0042$ |

**几十步之前的梯度基本没影响了。** 这就是"滑动平均"：一个不断前滑的、指数加权的窗口。

**有效窗口长度 $\approx 1/(1-\beta)$。** 权重是指数衰减的、没有硬边界（老样本权重永远不严格为 0），所以"窗口"需要一个定义。三种定义**指向同一个数**：

**① 平均年龄**（$j$ = 这个梯度有多老）：

$$\mathbb{E}[j] = \sum_{j=0}^{\infty} j\,(1-\beta)\beta^{\,j} = \frac{\beta}{1-\beta}$$

$\beta=0.9 \Rightarrow 9$ 步，$\beta=0.999 \Rightarrow 999$ 步。

**② 时间常数：走 $\frac{1}{1-\beta}$ 步恰好覆盖 63.2% 的权重。**

最近 $t$ 步的累计权重是 $1-\beta^{\,t}$。代入 $t=\frac{1}{1-\beta}$：

| $\beta$ | 最近 $\frac{1}{1-\beta}$ 步 | 覆盖率 |
|---|---|---|
| 0.9 | 10 | 65.1% |
| 0.99 | 100 | 63.4% |
| 0.999 | 1000 | **63.2%** |

因为 $\beta\to1$ 时 $\beta^{1/(1-\beta)}\to e^{-1}$，覆盖率 $\to 1-1/e = 63.2\%$。**和 RC 电路的时间常数 $\tau$ 是同一个常数、同一个道理。**

**③ 覆盖率表**（倍数与 $\beta$ 无关）：

| 想覆盖 | 需要最近多少步 |
|---|---|
| 50% | $0.69 \times \frac{1}{1-\beta}$ |
| **63.2%** | $\mathbf{1.00 \times \frac{1}{1-\beta}}$ |
| 90% | $2.30 \times \frac{1}{1-\beta}$ |
| 99% | $4.61 \times \frac{1}{1-\beta}$ |

于是 **$\beta_2=0.999$ 就有了具体含义**：$v$ 的信息 63% 来自最近 1000 步、90% 来自 2300 步、**99% 来自 4600 步**。它记的不是"这一步梯度多大"，是"这个参数最近几千步以来梯度一般多大"。

**这也解释了为什么 $\beta_2$ 要比 $\beta_1$ 大得多。** $m$ 估的是"方向"，要跟得上损失面的变化，所以**窗口短，约 10 步**；$v$ 估的是"典型幅度"，本质是个统计量、要稳，所以**窗口长，约 1000 步**。两者差 100 倍。

**权重之和不是 1**（这一条后面要用）：

$$(1-\beta)\sum_{i=1}^{t}\beta^{\,t-i} = (1-\beta)\cdot\frac{1-\beta^{\,t}}{1-\beta} = 1-\beta^{\,t}$$

#### 修补二：自适应尺度 —— 治毛病 ①

思路：**拿梯度除以「这个参数自己梯度的典型大小」**。

```
w1 :  梯度 1e-6  ÷  典型量级 1e-6   ->  约 1
w2 :  梯度 1e-2  ÷  典型量级 1e-2   ->  约 1
```

**两个都移动 $\alpha$。** 剩下的问题只是"典型大小"怎么估。

**AdaGrad（2011）**：用历史梯度平方的**累加**。

$$G \leftarrow G + g^2, \qquad \theta \leftarrow \theta - \alpha\,\frac{g}{\sqrt G}$$

它在稀疏特征上效果显著，但 $G$ 只增不减，有效学习率 $\alpha/\sqrt G$ 因此单调趋于 0，深度网络还没收敛就先停了。

**RMSProp（2012）**：把累加换成上一节那个 EMA。

$$v \leftarrow \beta_2 v + (1-\beta_2)\,g^2$$

窗口有限（约 $1/(1-\beta_2)$ 步），梯度变小时分母也跟着降，学习率能恢复，AdaGrad 的死穴就此解决。

$\sqrt v$ 就是最近这些梯度的均方根，也就是"这个参数的梯度一般有多大"，不看方向。

**显存代价：又是常驻的 $+1\times$。** 值得注意的是 AdaGrad 的 $G$ 和 RMSProp 的 $v$ 占的显存**一模一样**——从累加换成滑动平均，改的只是遗忘速度，不省一个字节。这条路线从诞生起就是拿一份完整的模型参数换来的。

#### Adam = 两者相加

$$m \leftarrow 0,\qquad v \leftarrow 0\qquad(\text{与 }\theta\text{ 同形状})$$

对 $t=1,2,3,\dots$：

$$
\begin{aligned}
g &\leftarrow \partial L/\partial\theta &&\text{当前 batch 的梯度}\\[3pt]
m &\leftarrow \beta_1 m + (1-\beta_1)\,g &&\text{修补一：方向}\\[3pt]
v &\leftarrow \beta_2 v + (1-\beta_2)\,g^2 &&\text{修补二：幅度}^2\\[3pt]
\hat m &\leftarrow m/(1-\beta_1^{\,t}),\qquad \hat v \leftarrow v/(1-\beta_2^{\,t}) &&\text{偏差修正（下下节）}\\[3pt]
\theta &\leftarrow \theta - \alpha\,\frac{\hat m}{\sqrt{\hat v}+\varepsilon} &&\text{更新}
\end{aligned}
$$

| 行 | 在算什么 | 显存 |
|---|---|---|
| $g$ | 这一个 batch 说"往哪走" | 1×，反向时分配 |
| $m$ | 最近约 $1/(1-\beta_1)=10$ 步的梯度平均，去噪后的方向 | 1×，常驻 |
| $v$ | 最近约 $1/(1-\beta_2)=1000$ 步的梯度平方平均，$\sqrt v$ 是梯度的典型幅度 | 1×，常驻 |
| $\hat m,\hat v$ | 把 EMA 的权重归一化 | **各 1×，临时** ← 见下 |
| 更新 | $\hat m/\sqrt{\hat v}$ = 方向 ÷ 典型幅度 | 临时 |

> **这是 Adam，还不是 AdamW。** weight decay 是后面那一节加的第六行。

**把显存账算一下**：$\theta$、$g$、$m$、$v$ 四份常驻，这就是 §3.14 那个 4×。但如果照字面实现，第四行的 $\hat m$ 和 $\hat v$ 还会各分配一份新张量——**峰值瞬间变成 6×**。GPT-2 XL 就是 26 GB 变 39 GB，而这两份张量用完就扔。

**这不是小事，它直接影响你能开多大的 batch。** 后面 handout 那个 $\alpha_t$ 写法存在的理由就是消掉这 2×。

#### $\hat m / \sqrt{\hat v}$：整个算法的关键就是这一个比值

**它是纯数字（无量纲）。** 无量纲 = 同类相除、单位抵消：

$$5\,\text{米} \div 2\,\text{米} = 2.5\ (\text{纯数}), \qquad 5\,\text{米} \div 2\,\text{秒} = 2.5\ \text{米/秒}\ (\text{有量纲})$$

$\hat m$ 是**梯度**的平均、$\sqrt{\hat v}$ 是**梯度平方**的平均开根 —— **两者都带梯度的单位**，相除 ⇒ 纯数字。这带来三个后果。

**后果一：它的取值大致在 $[-1,1]$，含义是信噪比。**

$$\text{梯度一直朝同一方向} \Rightarrow \hat m \approx \sqrt{\hat v} \Rightarrow \frac{\hat m}{\sqrt{\hat v}} \approx \pm 1 \quad\text{走满一步}$$
$$\text{梯度来回抖动} \Rightarrow \hat m \approx 0 \Rightarrow \frac{\hat m}{\sqrt{\hat v}} \approx 0 \quad\text{几乎不动}$$

**后果二：$\alpha$ 的含义变了，从此可迁移。**

梯度 $g$ 的单位是 $[\text{损失}]/[\text{参数}]$，所以在 SGD 里：

$$[\text{参数}] = [\alpha]\cdot\frac{[\text{损失}]}{[\text{参数}]} \quad\Longrightarrow\quad [\alpha]_{\text{SGD}}=\frac{[\text{参数}]^2}{[\text{损失}]}$$

也就是说，**SGD 里的 $\alpha$ 是个换算系数**，取值同时取决于损失的尺度和参数的尺度。换一层、换模型大小、给 loss 乘个常数，都得重新调。

而 Adam 乘的是纯数字：

$$[\alpha]_{\text{Adam}} = [\text{参数}]$$

于是 **$\alpha$ 的单位变成了「参数」本身**，含义直接就是"每一步让参数移动多远"。这是它能跨层、跨模型规模迁移的原因，也是 scaling law 类实验的前提，还解释了为什么 `lr=1e-3` 能当一个放之四海皆准的起点。

**后果三：对损失缩放严格不变（可以验算）。**

把损失整体乘以常数 $c$，则 $g\to cg$。而 $m$ 对 $g$ 线性、$v$ 对 $g$ 二次：

$$m \to cm,\qquad v \to c^2 v,\qquad \sqrt v \to c\sqrt v \qquad\Longrightarrow\qquad \frac{m}{\sqrt v}\ \text{精确不变}$$

结论是：**Adam 对损失缩放完全免疫，而 SGD 必须把 $\alpha$ 除以 $c$ 才能等效。**

> 顺带解释 $\varepsilon$ 为什么必须极小：$\hat m/(\sqrt{\hat v}+\varepsilon)$ 里的 $\varepsilon$ **是有量纲的**，它破坏上面这个不变性。取 $10^{-8}$ 不是"随便一个小数"，是要让破坏可忽略。

#### 偏差修正的来历：权重和不是 1

回到 EMA 那节算过的那个和：$m_t$ 的权重之和是 $1-\beta^{\,t}$，**不是 1**。

所以 $m_t$ 是个加权**和**，不是加权**平均**。要变成平均，就得除以权重和：

$$\hat m_t = \frac{m_t}{1-\beta^{\,t}}$$

**这就是偏差修正的全部来历——不是额外补丁，就是"把权重归一化"。**

验一下 $t=1$：

```
m₁  = 0.1 × g₁            窗口里只有一个样本，权重和 = 0.1
m̂₁  = 0.1·g₁ / 0.1 = g₁   除掉之后正好是 g₁ 本身
```

$t\to\infty$ 时 $\beta^t\to 0$，权重和 $\to 1$，修正因子 $\to 1$，**自动失效**。

**不修正会怎样**（$\beta=(0.9,\,0.999)$）：

$$\frac{m_1}{\sqrt{v_1}} = \frac{(1-\beta_1)g}{\sqrt{(1-\beta_2)}\,|g|} = \frac{0.1}{\sqrt{0.001}} = 3.16$$

也就是说，**不修正的话第一步会大 3.16 倍**。两个 EMA 都被拽向 0，但 $v$ 多开了一次根号，**两者收缩的程度不一样**，所以不会自动抵消——这正是那个"两条路线合并之后才必须处理"的问题。

#### handout 的等价写法：把两个修正合并进学习率

$$\alpha\cdot\frac{m/(1-\beta_1^t)}{\sqrt{v/(1-\beta_2^t)}} = \underbrace{\alpha\frac{\sqrt{1-\beta_2^t}}{1-\beta_1^t}}_{\displaystyle \alpha_t}\cdot\frac{m}{\sqrt v}$$

于是 handout 的 Algorithm 1 写成：先算 $\alpha_t$，然后直接用**未修正**的 $m$、$v$ 做 $\theta \leftarrow \theta - \alpha_t\,m/(\sqrt v+\varepsilon)$。

**这个变形的全部意义在显存上。** $\alpha_t$ 是个标量，算它不占任何显存；而 $\hat m$、$\hat v$ 是两份和参数同形状的张量。把修正从张量挪进标量，峰值就从 6× 回到了 4×——**对 GPT-2 XL 是省下 13 GB**。PyTorch 的官方实现也是这么做的。

（代价是 $\varepsilon$ 的位置略有不同：标准形式里它加在 $\sqrt{\hat v}$ 上，这里加在 $\sqrt{v}$ 上，两者差一个 $\sqrt{1-\beta_2^t}$ 的因子。数值上无关紧要，但这解释了为什么 `test_adamw` 允许"匹配参考实现**或** PyTorch 之一"。）

**$\alpha_t/\alpha$ 的实际形状是非单调的**：

| $t$ | 1 | 5 | **10** | 20 | 50 | 100 | 1000 | 5000 |
|---|---|---|---|---|---|---|---|---|
| $\beta_2=0.999$ | 0.316 | 0.173 | **0.153** | 0.160 | 0.222 | 0.309 | 0.795 | **0.997** |
| $\beta_2=0.95$ | **2.236** | — | 0.973 | — | — | 0.997 | 1.000 | 1.000 |

$\beta_2=0.999$ 时**先降后升**，$t\approx 10$ 触底（约 $0.15$），**要几千步才逼近 1**。

换句话说，**AdamW 自带一段隐式的低学习率启动期。**

这个长度不是巧合——**它就是 EMA 那节的窗口**：$\beta_2=0.999$ 的 $v$ 要几千步才积累够 99% 的权重（上面覆盖率表：$4.6\times\frac{1}{1-\beta_2}$），偏差修正因子自然也要那么久才归位。

而 $\beta_2=0.95$（窗口只有 20 步）形状完全不同：第一步是 $2.24$ 倍（**过冲**而非欠冲），十步内收敛到 1。这就是 LLaMA / GPT-3 用 $(0.9,\,0.95)$ 的一个具体理由——**别把几千步浪费在隐式 warmup 上**（真要 warmup 就用显式的，见 handout §4.4）。

#### AdamW 的 "W"：加上第六行

Adam 的算法里插入一行 weight decay，就是 AdamW：

$$\theta \leftarrow \theta - \alpha\lambda\theta \qquad\text{（在更新之前，独立于梯度通路）}$$

| | 做法 | 后果 |
|---|---|---|
| **Adam + L2** | $g \leftarrow g + \lambda\theta$，然后照常算 $m,v$ | 衰减项**也被 $\sqrt v$ 除**了 ⇒ 梯度历史大的参数拿到**更弱**的衰减 |
| **AdamW** | $\theta \leftarrow \theta - \alpha\lambda\theta$，**旁路** | 每个参数按**相同的相对速率**衰减 |

关键在于 $\lambda\theta$ **不进 $g$、不进 $m$、不进 $v$**。

Adam+L2 的问题不是"错"，而是**正则强度变成了梯度幅度的函数**，超参数 $\lambda$ 失去统一含义、没法调。

**显存代价：零。** 这一行是纯粹的原地缩放（$\theta \mathrel{*}= 1-\alpha\lambda$），不需要任何新张量，也不需要任何新状态。有意思的是，反而是那个"更省事"的 Adam+L2 写法要多一份临时张量来装 $g+\lambda\theta$——**解耦版本既更正确又更省显存。**

**为什么这在 SGD 上不是问题**：

$$\text{SGD}+\text{L2}:\quad \theta \leftarrow \theta - \alpha(g+\lambda\theta) = (1-\alpha\lambda)\theta - \alpha g$$

**恰好就是 weight decay。** 两者在 SGD 下**代数等价**，所以历史上没人区分这两个词——直到 Adam 出现，等价性被 $\sqrt v$ 打破。

> Loshchilov & Hutter 论文的论点值得单独记：当时所有人用 Adam+L2，并普遍观察到"**Adam 泛化不如 SGD**"。他们的主张是——**那个观察相当程度上是这个 bug 的假象**，解耦之后差距大幅缩小。
> 好例子：**一个被广泛接受的"经验结论"，根源可能只是实现细节。**

#### 大图景：优化器家族 = Hessian 近似的阶梯

前面说 Adam 治的是"每个参数该用多大的尺子"。这件事有个理论上的终点：牛顿法。

$$\theta \leftarrow \theta - H^{-1}g$$

它**对任意线性重参数化免疫**——量纲问题从根上不存在。但 $H$ 是 $d\times d$，GPT-2 XL 的 $d=1.64\times10^9$ ⇒ $2.7\times10^{18}$ 个数，不可能。

所以整个家族其实是**一道「用多少内存换多少 Hessian 精度」的阶梯**：

| 优化器 | 对 $H$ 的近似 | 额外内存 |
|---|---|---|
| SGD | $H\approx I$ —— "所有方向曲率相同" | 0 |
| SGD + momentum | 同上，但对 $g$ 去噪 | 1× |
| **Adam / AdamW** | $H\approx\operatorname{diag}(\sqrt v)$ —— **只保留对角线** | **2×** |
| Shampoo / SOAP | 分块 / Kronecker 近似 | 2–4× |
| 牛顿法 | $H$ 本身 | $d\times$ |

**Adam 的位置就是"只保留对角线"**：承认参数间有交互（$H$ 的非对角元），但选择忽略，换来 $d$ 个数而不是 $d^2$ 个。

> **为什么 $\sqrt v$ 能当曲率代理**：Fisher 信息矩阵 $F=\mathbb{E}[gg^\top]$ 的对角线就是 $\mathbb{E}[g^2]\approx v$，而对数似然损失下 $F\approx H$。
> 但注意是 $\sqrt v$ **不是 $v$**——真正的牛顿法要除 $H$，Adam 只除 $\sqrt H$。这个"半步牛顿"更保守也更稳，**没有干净的理论解释，是经验选择**。别把 Adam 说成"就是自然梯度"。

**那 2× 是要真金白银付的**：$m$ 和 $v$ 各一份和参数同形状的张量。这就是 §3.14 那个 "4×" 的来源——参数(1) + 梯度(1) + $m$(1) + $v$(1)。GPT-2 XL 的 6,562 MB 权重 ⇒ **26,247 MB 只是为了能训**，激活值还没算。`adamw_accounting` 那题就是把这笔账算清楚。

#### `learning_rate_tuning`（handout 1 分）

拿 handout 给的 toy loop 跑一跑：`weights = 5*randn(10,10)`，`loss = (weights**2).mean()`，用 handout 那个带 $1/\sqrt{t+1}$ 衰减的 SGD 跑 10 步。三个学习率的 loss（`manual_seed(0)`，初值都是 26.27）：

| 步 | lr = 1e1 | lr = 1e2 | lr = 1e3 |
|---|---|---|---|
| 0 | 26.27 | 26.27 | 26.27 |
| 1 | 16.81 | **26.27** | 9.48e3 |
| 2 | 12.39 | 4.51 | 1.64e6 |
| 3 | 9.70 | 0.108 | 1.82e8 |
| 4 | 7.85 | **1.1e-16** | 1.48e10 |
| 9 | 3.53 | 2.3e-23 | **2.44e18** |

三种典型行为一次看全：**lr=1e1 平稳但慢**（10 步只降到 3.53），**lr=1e2 快到离谱**（第 4 步就机器零），**lr=1e3 直接发散**。

这个玩具问题小到可以完全解析，值得算一下，因为它解释了表里两个看起来很怪的数。损失是 $\frac1{100}\sum w^2$，梯度是 $0.02\,w$，所以一步更新就是给每个元素乘同一个系数：

$$w \leftarrow w\,(1 - 0.02\,\alpha_t), \qquad \alpha_t = \frac{\alpha}{\sqrt{t+1}}$$

于是收敛条件是 $|1 - 0.02\alpha_t| < 1$，也就是 $\alpha_t < 100$。这正是"二次函数上梯度下降稳定当且仅当 $\alpha < 2/L$"这条通用结论（这里曲率 $L = 0.02$）。对着它看表：

- **lr=1e2 的第 1 步 loss 一个数字都没变**，不是我抄错了：$\alpha_0 = 100$ 恰好落在临界点上，系数是 $1-2 = -1$，**每个权重被整体翻了个符号，模长一点没变**。
- **lr=1e2 第 4 步的 `1.1e-16` 是真正的零**：$t=3$ 时 $\alpha_3 = 100/2 = 50$，系数正好是 $1-1 = 0$，一步把所有权重清零。这是这个玩具问题独有的巧合，不是什么优化上的胜利。
- **lr=1e3 要等到 $\alpha_t < 100$ 才可能收敛**，也就是 $\sqrt{t+1} > 10$、$t \ge 100$ 步之后。可它在第 10 步就已经涨到 $10^{18}$，等不到那一天。**$1/\sqrt{t}$ 的衰减救不了一个一开始就发散的学习率**——衰减是多项式的，发散是指数的。

最后一条是这道题真正想说的：**"最优学习率"贴着稳定边界**。1e2 比 1e1 好一百倍，而 1e3 直接炸掉，中间没有平滑过渡。真实训练里当然没有解析的临界值，但形状是一样的——这就是为什么 lr 要靠扫、而且扫出来的最好值往往就在发散的悬崖边上，也是为什么需要 warmup 和梯度裁剪（§4.3、§4.4）把早期那几步护住。

#### 延伸：Muon（2024）——换的不是预条件，是「距离」的定义

本作业不涉及，但它是 AdamW 出现以来最有说服力的挑战者，值得知道它在哪个维度上不一样。

**出发点**：Adam 的 $\operatorname{diag}(\sqrt v)$ 是**逐元素**的——它把一个 $[d_\text{out}, d_\text{in}]$ 的权重矩阵当成一袋互不相干的标量，**矩阵结构被完全丢掉**。Muon 认为更新量既然是矩阵，就该按矩阵的方式度量。

**算法**（只作用于 2D 参数）：

$$B \leftarrow \mu B + G \qquad\text{（动量，和 SGD 一样）}$$
$$O \leftarrow \operatorname{Orthogonalize}(B):\quad B = U\Sigma V^\top \ \Longrightarrow\ O = UV^\top$$
$$\theta \leftarrow \theta - \alpha\,O$$

**关键在第二步：把奇异值全部扔掉，只留方向。**

**为什么是这个**：在谱范数球内找与梯度内积最大的方向，

$$\arg\max_{\|\Delta\|_2 \le 1}\ \langle G,\ \Delta\rangle \;=\; UV^\top$$

也就是说，**Muon 是谱范数下的最速下降**，而 SGD 是 Frobenius（欧氏）范数下的最速下降。

> 所以它和 Adam / Shampoo 不在同一个轴上：**那些在改"对 $H$ 的近似"，Muon 在改"什么叫一步走得远"。**
> 后果是更新的所有奇异方向被拉平到同一量级——**没有哪几个方向能主导这一步**。

**工程上的三个细节**：

| | |
|---|---|
| 不做 SVD | 用 **Newton-Schulz 迭代**近似，约 5 步、每步几次矩阵乘，bf16 即可。系数是调出来的（约 $(3.4445,\ -4.7750,\ 2.0315)$），**不追求收敛到精确的 $UV^\top$**，只要把奇异值压进 1 附近就够 |
| 开销 | 相对模型的前向/反向可忽略 |
| **只用于 2D 隐层权重** | embedding、`lm_head`、所有 1D 参数（norm 的 gain）**仍用 AdamW** —— 那些地方"矩阵结构"的语义不成立 |

**显存**：只存动量 $B$，也就是 **1× 参数量**，而 AdamW 是 2×——因为它压根没有 $v$ 这个二阶矩。这是把整节那条暗线收尾的地方：**"换一种范数"这条路线不只是换了个更新方向，它顺带砍掉了一半的优化器状态。** 实际总量会略高于 1×，因为 embedding、`lm_head` 和 1D 参数还要配一套 AdamW。

**现状**：NanoGPT speedrun 的记录保持者；Moonshot 的 Kimi K2（2025，~1T 总参数的 MoE）用它做主训练器，并加了 **MuonClip**（对 attention 的 qk logit 做裁剪）抑制训练后期的数值爆炸。

> 但**还没到"默认"的地位**——大规模复现和消融仍在积累。记这一条主要是为了那个框架：**优化器可以在两个正交的方向上改进——更好的曲率近似，或者换一种范数。** AdaGrad→Adam 走的是前者，Muon 走的是后者。

### 4.2.1 AdamW 的实现

上一节讲清楚了每一行公式的来历，这一节讲怎么把它写成一个 PyTorch 优化器。这里的核心不是算法（算法已经在上面了），而是**一整套围绕"不要多分配显存"展开的工程约定**。

#### `torch.optim.Optimizer` 的两个方法

| 方法 | 职责 |
|---|---|
| `__init__(self, params, ...)` | 把超参打包成 `defaults` 字典，交给 `super().__init__(params, defaults)`。`params` 可能是**参数组**（不同部分用不同 lr），基类负责存 |
| `step(self, closure=None)` | 走 `self.param_groups` → `group["params"]`，读 `p.grad`，**原地**改 `p`。`closure` 是 API 要求，我们用不到但要收下 |

per-parameter 的状态放在 `self.state[p]`，这是个 `dict[Parameter, dict]`，$m$、$v$、$t$ 都存在里面。

**这个字典就是上一节那 2× 显存的实际所在**，有两件事值得知道。一是 PyTorch 的官方实现和我们一样**懒分配**——`state` 在第一次 `step()` 时才创建 $m$、$v$，所以模型刚建好时显存只有 1×，**要跑完第一步才看得到真实占用**。调试 OOM 时很容易被这一点骗到：以为装得下，第一步就炸。二是 `state_dict` 会把它们一起存进 checkpoint，所以**优化器的 checkpoint 比模型本身还大一倍**。

#### 五行公式对应五行代码

按 handout Algorithm 1 的顺序（$\alpha_t$ → weight decay → $m$ → $v$ → 更新），每一行都有对应的原地算子：

| 公式 | 算子 | 说明 |
|---|---|---|
| $\theta \leftarrow \theta-\alpha\lambda\theta$ | `p.mul_(1 - lr*weight_decay)` | 纯缩放，零额外显存 |
| $m \leftarrow \beta_1 m + (1-\beta_1)g$ | `m.mul_(beta1).add_(grad, alpha=1-beta1)` | 两步都在 $m$ 原地做 |
| $v \leftarrow \beta_2 v + (1-\beta_2)g^2$ | `v.mul_(beta2).addcmul_(grad, grad, value=1-beta2)` | `addcmul_` 把 $g^2$ 和累加**融合进一个 kernel**，$g^2$ 从不物化 |
| $\sqrt v + \varepsilon$ | `denom = v.sqrt().add_(eps)` | **唯一分配新张量的一行**，见下 |
| $\theta \leftarrow \theta-\alpha_t\frac{m}{\sqrt v+\varepsilon}$ | `p.addcdiv_(m, denom, value=-alpha_t)` | 除、乘、减融合成一个 kernel |

$\alpha_t$ 是标量，用 `math.sqrt` 在 CPU 上算就行，不要用 `torch.sqrt` 去造一个 0 维张量。

#### 为什么全用带下划线的原地算子

两个理由，第二个是致命的。

**理由一：显存。** 每写一个 `m = beta1 * m + (1-beta1) * grad` 这样的表达式，PyTorch 就分配一份和参数同形状的新张量。照公式逐行翻译，一步之内很容易堆出四五份临时张量——对 GPT-2 XL 就是每份 6.5 GB。`mul_`、`add_`、`addcmul_`、`addcdiv_` 存在的意义就是消掉它们。

顺带一提，`addcmul_` / `addcdiv_` 这种**融合算子**不只是省显存，它把两三个逐元素运算合并进一个 CUDA kernel，少读写几遍显存，也更快。

**理由二：写成 `p = p - ...` 等于没训练。** 那只是把局部变量 `p` 重新绑定到一个新张量上，模型里那块参数**一个 bit 都没变**。不报错、不崩溃、loss 平平地不降——这是本节最贵的一个坑。

#### 实测：唯一一处真实的临时分配

上面那张表里 `denom = v.sqrt().add_(eps)` 是唯一一行分配了新内存的。`.add_(eps)` 确实是原地的，但 **`v.sqrt()` 本身就已经造出了一份完整的 1× 张量**——原地的是后半句，不是整行。

所以"AdamW 的 step 零额外显存"这个说法**不准确**，准确的说法是：**峰值只多一份，而不是四五份**。PyTorch 官方实现也有这一份 `denom`，想彻底消掉得预分配一块 scratch buffer 复用，那已经是框架级的优化了。

#### `@torch.no_grad()` 不是优化，是必需

`step()` 上面那个装饰器不能省。没有它，`p.add_()` 会直接抛：

```
RuntimeError: a leaf Variable that requires grad is being used in an in-place operation
```

因为模型参数是 `requires_grad=True` 的**叶子节点**，autograd 不允许在追踪状态下原地修改它们——一旦改了，之前记录的计算图就对不上了。`no_grad` 把这段代码移出追踪范围，原地修改才合法。

顺带，这也解释了 `closure` 那几行为什么要 `with torch.enable_grad():` 包起来：closure 的职责是**重新算一次 loss**，那是需要建图的，得把 `no_grad` 临时反转回来。

#### 那前向传播为什么不能这么写

自然会问：既然原地这么好，为什么 §3.13 的 Transformer block 写的是 `x = x + self.attn(self.ln1(x))` 而不是 `x.add_(...)`？

常见的答复是"前向要留着算梯度，所以不能原地"——**这个说法太粗了**。实测三种情况：

| 写法 | 结果 |
|---|---|
| `nn.ReLU(inplace=True)` | **OK** |
| 对只做加法的中间量原地 `add_` | **OK** |
| 对已被保存用于 backward 的张量再原地改 | `RuntimeError` |

所以判据不是"哪个阶段"，而是：**某个已经被保存下来用于反向的张量，有没有被后续修改。**

这取决于具体算子保存了什么。加法的反向是 $\partial(a+b)/\partial a = 1$，**不需要任何输入值**；而 ReLU 的反向只需要**输出**的符号，原地版写的恰好就是输出——所以 PyTorch 才会给 ReLU、Dropout 提供 `inplace=True`。相反，乘法和矩阵乘的反向需要**两个输入**都保留，那些地方就动不得。

回到残差连接：`x = x + self.attn(self.ln1(x))` 之所以不能改成原地，不是因为那个加法，而是因为 **`ln1` 已经把 `x` 保存下来了**。你原地一改，`x` 的版本号变了，RMSNorm 的反向就会发现自己存的东西被人动过，当场报错。

优化器之所以能放开手脚，根本原因是**那里根本没有计算图**——前向反向都结束了，$g$ 已经拿到手，剩下的纯粹是按公式改数字。

#### 五个容易错的点

1. **$t$ 从 1 开始。** 若 $t=0$：$\alpha_0 = \alpha\sqrt{1-\beta_2^0}/(1-\beta_1^0) = \alpha\cdot 0/0$，**第一步就是 NaN**。handout 的 SGD 示例是 `t = state.get("t", 0)` 先用后加，AdamW 不能照抄——要先自增再用
2. **weight decay 用 $\alpha$，主更新用 $\alpha_t$。** 两行的学习率不是同一个
3. **$\sqrt v + \varepsilon$，不是 $\sqrt{v+\varepsilon}$。** $\varepsilon$ 加在开方之后
4. **`p.grad` 可能是 `None`**（这个参数这轮没被用到），必须 `continue` 跳过
5. **原地改 `p`**，别写成 `p = p - ...`

构造函数签名被测试钉死，和 `torch.optim.AdamW` 完全一致：

```python
opt_class(model.parameters(), lr=1e-3, weight_decay=0.01,
          betas=(0.9, 0.999), eps=1e-8)
```

注意 `betas` 是一个元组而不是两个独立参数，`weight_decay` 也不叫 `lambda`。测试的判定是"匹配参考实现**或** PyTorch AdamW 之一"（`atol=1e-4`），因为 weight decay 的施加位置有几种原理等价、浮点上略有差异的写法。

`pytest tests/test_optimizer.py -k adamw` → **PASSED**。

### 4.2.2 训练一步要多少显存和算力（`adamw_accounting`）

§3.14 只算了推理：加载权重 6,562 MB、一次前向 3.517 TFLOPs。这一节把训练那部分补齐——**训练的显存开销是推理的四倍起步，而且真正的大头往往不是权重。**

#### (a) 四笔账的代数式

符号：$V$ 词表、$T$ 上下文、$L$ 层数、$d$ = d_model、$h$ 头数、$B$ = batch_size。

**参数量**（§3.14 已推过）：

$$P = 2Vd + L\big(4d^2 + 3d\,d_{ff} + 2d\big) + d \;\approx\; 2Vd + 12Ld^2$$

由此三笔**与 batch 无关**的固定开销：

| | 大小 | 说明 |
|---|---|---|
| 参数 | $P$ | 常驻 |
| 梯度 | $P$ | 反向时分配 |
| 优化器状态 | $2P$ | $m$ 和 $v$（§4.2 那条暗线） |
| **小计** | $\mathbf{4P}$ | |

**激活值**则正比于 $B$。按 handout 指定的清单逐项数（每个 batch 元素）：

$$
\begin{aligned}
\text{每层} \;&=\; \underbrace{2BTd}_{\text{两个 RMSNorm}} + \underbrace{3BTd}_{QKV\ \text{投影}} + \underbrace{2BhT^2}_{QK^\top\ \text{和 softmax}} + \underbrace{BTd}_{\text{加权求和}} + \underbrace{BTd}_{\text{输出投影}} + \underbrace{4BTd_{ff} + BTd}_{\text{SwiGLU 五项}}\\[4pt]
&=\; 8BTd + 2BhT^2 + 4BTd_{ff}
\end{aligned}
$$

出口再加上最后的 RMSNorm、logits 和 cross-entropy：

$$A \;=\; L\big(8BTd + 2BhT^2 + 4BTd_{ff}\big) \;+\; BTd \;+\; 2BTV$$

代入 $d_{ff}=\tfrac83 d$，每层那部分是 $\big(\tfrac{56}{3}d + 2hT\big)BT$。

**总显存**（fp32，每个数 4 字节）：

$$\text{Mem} = 4\big(4P + A\big)\ \text{字节}$$

#### (b) 代入 GPT-2 XL

$V=50257,\ T=1024,\ L=48,\ d=1600,\ h=25,\ d_{ff}=4288$：

| | 大小 |
|---|---|
| 参数 | 6.56 GB |
| 梯度 | 6.56 GB |
| 优化器状态 $2P$ | 13.12 GB |
| **固定部分 $4P$** | **26.25 GB** |
| 激活值 | **16.37 GB × $B$** |

$$\boxed{\ \text{Mem} \;=\; 16.37\,B + 26.25\ \text{GB}\ }$$

$$80\ \text{GB} \Longrightarrow B \le 3.28 \Longrightarrow \textbf{最大 batch size} = \mathbf{3}$$

**单个 batch 元素就要 16.37 GB，比全部权重还多**——这是这道题最反直觉的结论。拆开看每一层的 83.1 M 个激活元素：

| 项 | 元素数 | 占比 |
|---|---|---|
| $2hT^2$（打分矩阵 + softmax） | **52.4 M** | **63%** |
| $4Td_{ff}$（SwiGLU 四个中间量） | 17.6 M | 21% |
| $8Td$（norm、投影、输出） | 13.1 M | 16% |

**注意力的 $T\times T$ 打分矩阵一项就吃掉了 63% 的激活显存**，而 §3.14 算过它只占 9.2% 的 FLOPs。这是同一个东西在两本账上的两副面孔：**算力上是配角，显存上是主角。**

FlashAttention 的动机在这里第三次出现，而且这次是最直接的：它不把那个 $[h,T,T]$ 的矩阵物化，**这 63% 直接消失**。前两次分别是 §3.14 的 arithmetic intensity（唯一 memory-bound 的部分）和长上下文下 FLOPs 占比涨到 61.7%。

#### (c) 一步 AdamW 的算力

$m$、$v$、$\theta$ 的更新全是**逐元素**运算，每个参数上大约十几次浮点操作（缩放、两次滑动平均、开方、除法、累加）：

$$\text{FLOPs}_{\text{step}} \;\approx\; 14P \;=\; 23.0\ \text{GFLOPs}$$

关键不是这个常数（它随实现在 10–20 之间浮动），而是**它正比于 $P$，与 $T$ 和 $B$ 都无关**。对比同一配置下前向 3.517 TFLOPs、加上反向共约 10.5 TFLOPs：

$$\frac{23.0\ \text{GFLOPs}}{10.5\ \text{TFLOPs}} = \mathbf{0.22\%}$$

**优化器的算力开销可以完全忽略**，它的代价全部体现在显存上。这个不对称值得记住：**AdamW 贵在 2× 的状态，不贵在计算。**

#### (d) 训练一个 GPT-2 XL 要多久

按 Kaplan / Hoffmann 的惯例，反向的 FLOPs 是前向的两倍，所以一步 = 3× 前向。

$$\text{总量} = 3 \times 3.517\ \text{TFLOPs} \times \underbrace{1024}_{\text{batch}} \times \underbrace{4\times10^5}_{\text{步}} = 4.31\ \text{ZFLOPs}$$

H100 的 TF32（NVIDIA 的 19 位浮点格式，用在 tensor core 的矩阵乘上）峰值是 495 TFLOP/s。实际训练不可能打满，按 50% 的 MFU（model FLOPs utilization，实际有效算力占峰值的比例，大模型训练里 40%–50% 已经算不错）来算：

$$\frac{4.31\times10^{21}}{495\times10^{12}\times 0.5} = 1.74\times10^{7}\ \text{秒} = \mathbf{4{,}836\ 小时} \approx \mathbf{202\ 天}$$

**单卡要跑大半年。** 这个数字本身就是答案——它解释了为什么大模型训练必然是多卡的：不是显存装不下（虽然也确实装不下，见 (b) 的 batch=3），而是**单卡的时间尺度根本不可接受**。要在两周内训完，需要约 15 张卡满负荷并行。

> 顺带看一眼 (b) 和 (d) 的矛盾：(d) 假设 batch size 是 1024，而 (b) 算出单卡最多放 3。**两者相差 341 倍**——这就是梯度累积和数据并行存在的全部理由。

### 4.3 学习率调度：warmup + 余弦退火

对应 handout §4.4，1 分。

#### 为什么学习率要随时间变

训练早期和晚期面对的是两个不同的问题。

早期模型离任何合理的解都很远，梯度方向在不同 batch 之间高度一致——这时候大步走是划算的，每一步都在往同一个方向推进。到了晚期模型已经落在某个极小值附近，真实梯度接近零，**此时 mini-batch 梯度里剩下的主要是噪声**。继续用大学习率的结果不是继续下降，而是在一个半径正比于 $\alpha$ 的"噪声球"里来回弹。把 $\alpha$ 降下来，这个球就跟着缩小。

所以衰减学习率不是"训练快结束了要温柔一点"这种玄学，它是在**换一个目标**：从"快速接近"换成"精确定位"。

#### 为什么开头还要先升上去（warmup）

这条不那么显然，因为直觉上开头就该大步走。

原因在 $v$ 上。§4.2 讲过 $v$ 是一个跨越约 $1/(1-\beta_2)$ 步的长期统计量，而**训练刚开始时它只积累了几个样本**，对"这个参数的梯度一般多大"的估计极不可靠。分母不可靠，$\hat m/\sqrt{\hat v}$ 这个比值就可能偏得离谱，做出的更新也就没有依据。等 $v$ 攒够样本再放开学习率，就是 warmup 在干的事。

这里有个容易混淆的地方值得说清：**AdamW 本身已经自带一段隐式 warmup**（§4.2 那张 $\alpha_t/\alpha$ 的非单调表：$0.316 \to 0.153 \to \dots \to 1$）。那是偏差修正造成的，和显式 warmup 是两回事，但作用方向相同。

两者的相对重要性取决于 $\beta_2$。用 $\beta_2=0.999$ 时隐式 warmup 长达几千步，显式的那段只是锦上添花；而 LLaMA / GPT-3 用的 $\beta_2=0.95$ 十步内就收敛到满学习率，**这时候几乎全靠显式 warmup 顶着**。所以"用小 $\beta_2$"和"配足够长的 warmup"通常成对出现。

#### 为什么是余弦

三段式的定义（$T_w$ 是 warmup 步数，$T_c$ 是退火结束步数）：

$$
\alpha_t=\begin{cases}
\dfrac{t}{T_w}\,\alpha_{\max} & t < T_w \\[10pt]
\alpha_{\min} + \dfrac12\Big(1+\cos\Big(\dfrac{t-T_w}{T_c-T_w}\pi\Big)\Big)\big(\alpha_{\max}-\alpha_{\min}\big) & T_w \le t \le T_c \\[10pt]
\alpha_{\min} & t > T_c
\end{cases}
$$

先验一下三段接得上：$t=T_w$ 时上面给 $\alpha_{\max}$，下面 $\cos 0=1$ 也给 $\alpha_{\min}+(\alpha_{\max}-\alpha_{\min})=\alpha_{\max}$，**连续**；$t=T_c$ 时 $\cos\pi=-1$，正好落到 $\alpha_{\min}$。中点 $t=\frac{T_w+T_c}{2}$ 处 $\cos\frac\pi2=0$，学习率恰好是 max 和 min 的中间值。

余弦相对线性衰减的好处是**导数在两端都为零**：刚进入退火时下降很慢（还能享受一段高学习率），接近尾声时也下降很慢（在低学习率上多停留一会儿做精细收敛），中间段降得最快。线性衰减在 $t=T_w$ 处有个导数跳变，阶梯衰减更是直接断崖。经验上余弦稳定好用，LLaMA、Chinchilla 都用它。

#### 一个实践上的陷阱：余弦把总步数写死了

$T_c$ 出现在公式里，意味着**整条曲线的形状取决于你打算训多少步**。这带来两个麻烦：训到一半想停，学习率还没退到 $\alpha_{\min}$，模型处在一个"没收好尾"的状态；训完了想接着训，学习率已经退到底了，续训等于用极小的学习率白跑。

这就是近年 WSD（warmup–stable–decay）类调度流行起来的原因——它中间保持恒定，只在最后一小段才衰减，于是**任何时刻的 checkpoint 都可以决定"就从这里开始收尾"**。本作业不涉及，但知道余弦的这个约束是从哪来的。

#### 实现

它就是一个**纯函数**，不是 `Optimizer` 的一部分：输入 $t$ 和四个超参，返回一个 float。训练循环里每步先算出 $\alpha_t$，再写进 `group['lr']`，然后才 `opt.step()`。

写的时候只有三个分支，直接照公式翻译即可。两个边界要自己验：

- $t=T_w$ 时两段是否给出同一个值（上面验过，是）
- $T_w=0$（不做 warmup）会不会除零。答案是不会——$t<0$ 不可能成立，第一个分支永远进不去，直接走余弦段

`pytest -k test_get_lr_cosine_schedule` → **PASSED**。

### 4.4 梯度裁剪

对应 handout §4.5，1 分。

#### 要解决的问题

训练中偶尔会撞上产生巨大梯度的 batch——可能是脏数据，可能是罕见的 token 组合，也可能只是损失面上一处真实的陡壁。一次这样的更新就可能把模型推到很难恢复的地方。

做法很简单：反向传播之后、优化器更新之前，把所有参数的梯度**看成一个大向量**，算它的 $\ell_2$ 范数。如果超过阈值 $M$，就整体乘以 $\dfrac{M}{\|g\|_2+\varepsilon}$ 缩回去；没超过就不动。

$\varepsilon$（取 $10^{-6}$，PyTorch 的默认值）在分母里，所以缩放之后的范数是 $\dfrac{M}{1+\varepsilon/\|g\|}$，**略小于 $M$ 而不是恰好等于**。handout 特意提了这一点。

**必须是全局范数，不能逐参数裁剪。** 因为所有梯度乘以同一个标量，总梯度的**方向完全不变**，只是步长变短；而逐参数各自裁剪会改变各层之间的相对大小，等于扭曲了下降方向。

#### 关键问题：Adam 已经按 $\sqrt v$ 归一化了，为什么还要裁

这是我一开始没想明白的地方——既然更新量 $\hat m/\sqrt{\hat v}$ 本来就被限制在 $[-1,1]$ 附近，一个 100 倍的梯度尖峰应该翻不起浪才对。

写个小模拟看看：梯度恒为 $1.0$，在第 500 步插入一个 $100$ 倍的尖峰，$\beta=(0.9,\,0.999)$，观察 $\hat m/\sqrt{\hat v}$（正常应为 $1.0$）：

| 相对尖峰的步数 | 不裁剪 | 裁剪到 1.0 |
|---|---|---|
| $-1$ | 1.000 | 1.000 |
| **$0$（尖峰当步）** | **2.12** | 1.000 |
| $+1$ | 1.93 | 1.000 |
| $+50$ | **0.217** | 1.000 |
| $+200$ | 0.241 | 1.000 |
| $+1000$ | 0.418 | 1.000 |
| $+2000$ | 0.636 | 1.000 |

结果和直觉相反：**尖峰当步只放大了 2.1 倍**，Adam 的自适应分母确实把 100 倍压了下去。真正的伤害在后面——那个 $100^2$ 的巨大值进了 $v$，**接下来两千步里这个参数的有效学习率被压到正常值的 20% ~ 60%，而且迟迟恢复不了**。

恢复的时间尺度不是巧合，它就是 §4.2 那个 EMA 窗口：$\beta_2=0.999$ 要 $4.6\times\frac{1}{1-\beta_2}\approx 4600$ 步才能把一个旧样本的权重衰减到 1% 以下。

所以梯度裁剪真正保护的不是"这一步"，而是**优化器的状态**。一次未经裁剪的尖峰会污染 $v$ 整整一个窗口的长度，表现出来就是训练曲线在某处莫名其妙地停滞几千步——而那时候尖峰早就过去了，很难回溯到原因。

> 这是本章第二次遇到"**伤害的持续时间等于 EMA 窗口**"这个模式。第一次是偏差修正（$\alpha_t$ 要几千步才归位），这次是尖峰污染。**只要一个量是 EMA，往里面塞进去的任何东西都会停留约 $\frac{1}{1-\beta}$ 步。**

典型的 $M$ 取 $1.0$。

#### 实现

三步：遍历所有参数把 $\|g\|_2^2$ 累加起来、开方、超过阈值就逐个 `mul_` 缩放。注意几点：

- **`p.grad` 可能是 `None`**，要跳过（和优化器里那条一样）
- **必须原地改 `p.grad`**（`mul_`），否则优化器读到的还是原来那份
- **调用时机是 backward 之后、`opt.step()` 之前**。放在 `step()` 之后等于没裁

有个性能上的点值得知道。我第一版是这么累加的：

```python
total_norm += p.grad.detach().pow(2).sum().item()
```

`.item()` 会把标量从 GPU 拷回 CPU，而这是一次**强制同步**——CPU 必须等 GPU 把前面排队的所有 kernel 跑完。一个 Transformer 有几百个参数张量，这就是每步几百次同步，足以让 GPU 大部分时间在空转。

PyTorch 官方的 `clip_grad_norm_` 的做法是把各个范数**堆成一个张量再一次性求范数**，全程留在设备上，最后只在真正需要判断的地方同步一次。`.pow(2)` 也会分配一份和梯度同样大的临时张量，用 `torch.linalg.vector_norm` 或者 `p.grad.norm()` 可以省掉。

本作业的规模下这些都无所谓，测试照样过。但**"每个参数一次 `.item()`"是个在真实训练里会实实在在拖慢速度的写法**，值得现在就知道。

`pytest -k test_gradient_clipping` → **PASSED**。

### 4.5 §4 小结

四个组件全部通过：cross-entropy、AdamW、余弦调度、梯度裁剪。

这一章反复出现的是同一件事——**很多量的寿命比你以为的长得多**，而 EMA 是它的载体：

1. **往 EMA 里塞进去的东西会停留约 $\frac{1}{1-\beta}$ 步。** 这一条以三种面貌出现过：偏差修正要几千步才归位（§4.2）、一次未裁剪的梯度尖峰污染 $v$ 整整一个窗口（§4.4）、以及 $\beta_2$ 的选择直接决定了显式 warmup 有多重要（§4.3）。**看到训练曲线在某处莫名停滞几千步，先回头找几千步之前发生了什么。**
2. **优化器贵在状态，不贵在计算。** AdamW 每步的算力只占前反向的 0.22%，但它常驻 2× 参数量的显存（§4.2.2）。所以那一整节的实现约定全都围绕"不要多分配一份张量"展开——`addcmul_` / `addcdiv_` 这些融合原地算子不是炫技，是把峰值从 6× 压回 4×。
3. **数值稳定的模式在这一章第三次出现**：cross-entropy 把 $\log\text{softmax}$ 合成一步（§4.1），共同点仍然是"输入输出都温和、只有中间量越界"，和 §3.7 的 RMSNorm 平方、§3.10 的 softmax 指数完全同构。
4. **测不出来的坑仍然是主要威胁。** `p = p - ...` 写成重新绑定而不是原地更新，不报错、loss 平平地不降；双重 softmax 同理。这是 §2.9"绿灯不等于证明"在本章的第三次复现。

## 5. 训练循环

对应 handout §5。前面四章造出了零件——分词器、模型、损失、优化器——这一章把它们接起来，还要补上三样支撑性的东西：数据加载、checkpoint、以及主训练脚本。

### 5.1 数据加载

这一节讲怎么把 §2.10 落盘的那个 `.npy` token 数组变成一批批 `(输入, 目标)`。看起来是全书最简单的一题（2 分，核心逻辑三行），但它背后的设计决定影响了整个训练流程的形状，而且真实系统在这里做的事比作业版本多得多。

#### 核心设计：把整个语料拼成一条 token 流

原始语料是一篇篇独立的文档。最直觉的做法是"一篇文档一个样本"，但那样每个样本长度都不同，喂进模型前必须 padding 到同一长度，而 padding 位置上的计算全是浪费。

handout 采用的做法是把所有文档**首尾相接拼成一条长长的 token 序列**（文档之间插一个 `<|endoftext|>` 作为分隔），然后从这条流里随机截取定长的窗口。这一下解决了三个问题：

任何一个起点 $i$ 都能截出一个合法样本，所以采样退化成一次 `randint`，不需要维护什么索引结构。所有样本长度严格相同，不需要 padding，硬件利用率拉满，也因此能开更大的 batch。最后，采样只需要读那一小段，不需要把整个数据集载入内存。

代价是**样本边界和文档边界脱钩了**——一条训练序列可能横跨两篇毫不相干的文档。这件事的后果放到后面"现代 dataloader"那一小节讲。

#### 输入和目标错开一格

从位置 $i$ 截一个长度为 $m$ 的窗口：

$$x = \text{tokens}[i:i+m], \qquad y = \text{tokens}[i+1:i+m+1]$$

$y$ 就是 $x$ 整体右移一格。位置 $j$ 的输入是 $x_j$，它要预测的是 $x_{j+1}$，也就是 $y_j$。

这正是 §4.1 开头那句"一次前向产出 $m$ 个训练信号"的落地形式：**这一个窗口同时是 $m$ 道"预测下一个"的题目**，而它们能同时成立完全依赖因果 mask。

由此定出合法起点的范围：需要 $i+m+1 \le n$，所以 $i$ 最大取到 $n-m-1$，一共 $n-m$ 个合法起点。测试就是按这个数卡的。

#### `np.memmap`：让 5.45 GB 的文件"假装"在内存里

`mmap` 是个 Unix 系统调用，它把磁盘文件映射进进程的虚拟地址空间，但**不实际读取内容**。等到你真的去访问某个地址时才触发缺页中断，由内核把对应的那一页从磁盘调进来。于是你可以像操作普通数组一样操作一个远大于内存的文件。

实测一下（`np.load(path, mmap_mode='r')`，owt_train 5.45 GB / 27.3 亿个 token）：

| 时刻 | 进程 RSS |
|---|---|
| 基线 | 473 MB |
| 打开 5.45 GB 的 memmap 之后 | 473 MB |
| 取了 8 个长度 1024 的窗口之后 | 476 MB |

**打开文件的那一步内存完全没涨**，取了 8 个窗口也只涨了 3 MB——那 3 MB 就是被真正碰到的那几页。这就是 memmap 的全部意义。

有两个配套的点：一是**`dtype` 必须和落盘时一致**（我们存的是 `uint16`），否则同一段字节会被按错误的宽度解读，读出来是一堆看似合理的垃圾数字，不会报错。handout 特意建议验证一下读出来的值没有超过词表大小，就是防这个。二是操作系统的 page cache 会把读过的页留着，所以同一段数据被反复采样时不会重复读盘。

#### 现代 dataloader 和这个玩具版差在哪

作业版本是"每步独立地随机采 $B$ 个起点"，三行就能写完。真实训练系统在这条路径上还要处理下面这些。

**跨文档污染。** 拼接流里的一条序列可能横跨两篇文档，于是模型会在第二篇文档的开头"看见"第一篇的结尾，并试图从中找规律。简单的应对是靠 `<|endoftext|>` 分隔符，指望模型自己学会在那里重置注意力；更严格的做法是**document masking**——把注意力 mask 从纯下三角改成分块下三角，让注意力根本无法跨越文档边界。GPT-2、GPT-3 用前者，近年不少模型（Llama 3 明确提到）用后者。这里值得注意的是，这个改动落在 §3.12 那个因果 mask 上：**mask 从"只依赖形状"变成了"依赖这个 batch 的内容"**，正好是笔记里讨论过的"什么时候不能把 mask 预建在 `__init__` 里"。

**有放回 vs 无放回。** 每步独立 `randint` 是**有放回**采样，等于把数据集当成一条无限流，压根没有 epoch 的概念。这在大规模下问题不大，但小规模下有个可以量化的浪费：抽 $K$ 条长度为 $m$ 的序列，某个 token 一次都没被覆盖到的概率约为 $\exp(-Km/n)$。当抽样总量刚好等于一个 epoch（$Km = n$）时，这个概率是 $e^{-1} \approx 37\%$。**也就是说"跑了一个 epoch 的量"实际上有三分之一的 token 从没被看到过**，同时另一些被看了好几遍。真实训练通常改成无放回地扫过一遍（把所有起点洗牌后顺序取），把这个浪费消掉。

**确定性与可恢复。** 训练一定会中断（§5.2 就是干这个的）。恢复的时候不光要还原模型和优化器，还要还原"读到哪了"。有两种做法：把 dataloader 的随机数状态一起存进 checkpoint，或者更省事的——**让第 $t$ 步的 batch 是 $t$ 的确定性函数**（比如种子取 `base_seed + t`），这样 dataloader 完全无状态，给个步数就能精确重放。后者是现在的主流做法。

**别让数据加载饿着 GPU。** 主进程一边算一边读，GPU 就会在等 IO。标准配方是 `DataLoader` 的多 worker 预取、`pin_memory=True` 配合 `.to(device, non_blocking=True)`，让 host 到 device 的拷贝和计算重叠起来。不过对本作业来说这完全不是瓶颈：一个 $B=8$、$m=1024$ 的 batch 只有 8192 个 `uint16`，也就是 16 KB，相对 PCIe 带宽微不足道。**真正会卡住的场景是在线分词**——如果不预先落盘而是每步现场跑 BPE，CPU 立刻变成瓶颈。§2 花那么大力气把语料预先编码成 `.npy`，收益就在这里。

**数据顺序本身是超参。** 多来源语料要按比例混合采样（The Pile 那种 domain weights），近年还流行在训练后期切到高质量子集做退火。这些都发生在 dataloader 这一层。

**再大就得流式。** memmap 的前提是"单机磁盘装得下"。超过这个规模就要用 webdataset、MosaicML streaming 之类的方案从对象存储按 shard 流式拉取；多机训练时还要保证每个 rank 读到不重不漏的分片。

#### 实现

主体就三步：抽 $B$ 个起点、按起点取窗口、搬到目标设备。

抽起点用 `np.random.randint(0, n - m, size=B)`。**上界写 `n - m` 而不是 `n - m + 1`**：`randint` 的上界是开区间，而合法起点最大是 $n-m-1$，正好对上。测试是直接卡这个边界的：它跑 1000 次采样，然后断言看到的最大起点恰好等于 `len(dataset) - context_length - 1`、最小起点恰好是 0。差一格就挂。

取窗口不要写 Python 循环。构造一个 $[B, m]$ 的下标矩阵（每个起点加上 `arange(m)`），一次高级索引就能把所有窗口取出来。目标只是同一个矩阵整体加 1。

**最后一步有个坑，我在这里栽了。** 我们落盘时用的是 `uint16`（§2.10：为了省一半空间，前提是词表不超过 65536）。而：

```
torch.from_numpy(uint16 数组)     ->  成功，得到 torch.uint16 张量
```

torch 2.11 是支持 `uint16` 这个 dtype 的，所以这一步**不报错**。真正的失败发生在两层之后：

```
Embedding 拿它当索引  ->  RuntimeError: Expected tensor for argument #1 'indices' to have one of the following scalar types...
cross_entropy 拿它当 target  ->  RuntimeError: expected scalar type Long but found UInt16
```

`uint16` 在 PyTorch 里是个"有 dtype 但几乎没有算子支持"的类型。所以必须显式转成 `int64`——PyTorch 的索引和 `cross_entropy` 的 target 都只认 `Long`。

这个坑的形态值得记：**转换那一步成功了，报错发生在两个模块之外**。错误信息指向 Embedding，而原因在 dataloader。和 §3.12 那批"静默失败"是同一个家族——只不过这次是响的，只是响错了地方。

顺带一个细节：`torch.from_numpy` 和原数组**共享内存**，而 `astype(np.int64)` 本身就产生了新数组，所以这里不必担心改到 memmap。但如果哪天真的直接 `from_numpy` 了一个 memmap 切片，要记得它是只读的。
