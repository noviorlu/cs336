## 1. 从 Unicode 说起

### 1.1 str 和 bytes 是两个层面

```
"café"          ← str：字符（Unicode 码点）的序列
   ↕  encode / decode
b'caf\xc3\xa9'  ← bytes：0–255 的字节序列
```

`encode` 把 str 变成 bytes（按 UTF-8 规则），`decode` 反向，二者互逆。

计算机底层只能存字节（0–255），但字符有 15 万多个，所以需要一套编码规则做映射。这也解释了为什么 `len()` 的结果会变：`len("café")` 是 4（数字符），`len("café".encode())` 是 5（数字节）。

有个小坑：`print(b'caf\xc3\xa9')` 打出来还是 `b'...'`，不会显示成 `café`。bytes 没有"给人看"的形式，想看内容必须显式 `.decode()`。

### 1.2 UTF-8 的变长机制

一个字符占几个字节，由它的码点范围决定：

| 码点范围 | 字节数 | 例子 |
|---|---|---|
| U+0000–U+007F | 1 | ASCII（`c`、`a`、`f`） |
| U+0080–U+07FF | 2 | `é`、`ñ`、希腊/西里尔字母 |
| U+0800–U+FFFF | 3 | 绝大多数常用汉字、假名、韩文 |
| U+10000–U+10FFFF | 4 | emoji、扩展区生僻字（如 `𠮷`） |

这里有个常见误解：**中文不都是 3 字节**。生僻字和扩展区的字在 U+20000 以上，是 4 字节。所以不要记"中文 = 3 字节"，要记「字节数由码点落在哪个范围决定」。

那 UTF-8 怎么做到变长而不产生歧义？靠每个字节的高位前缀自带角色标记（下面的 `x` 是真正承载码点的有效位）：

```
1 字节  U+0000–007F     0xxxxxxx
2 字节  U+0080–07FF     110xxxxx 10xxxxxx
3 字节  U+0800–FFFF     1110xxxx 10xxxxxx 10xxxxxx
4 字节  U+10000–10FFFF  11110xxx 10xxxxxx 10xxxxxx 10xxxxxx
```

`0` 开头是单字节（ASCII），`110`/`1110`/`11110` 开头分别是 2/3/4 字节序列的**首字节**，`10` 开头是**续接字节**。解码器从左往右扫，看一眼首字节前缀就知道后面还要读几个续接字节——这叫自解析。

举个实例，`é` 的码点是 U+00E9，填进 2 字节模板得到 `11000011 10101001`，也就是 `\xc3\xa9`，十进制是 `[195, 169]`。

### 1.3 为什么还有 UTF-16 和 UTF-32

三者都是"码点 → 字节"的编码方案，区别在编码单位的宽度：

| 编码 | 基本单位 | 一个字符占几字节 | 当初的动机 | 现在的定位 |
|---|---|---|---|---|
| UTF-8 | 1 字节 | 变长 1~4 | 兼容 ASCII、省空间、避开 `\x00` | 事实标准（超过 98% 的网页） |
| UTF-16 | 2 字节 | 变长 2 或 4 | 早期以为 2 字节（65536 个）够用，图定长好算 | 遗留：Windows / Java / JS 的内部字符串 |
| UTF-32 | 4 字节 | 定长 4 | 想要真定长、装下所有码点 | 极少用，太浪费 |

拿 "hello" 实测一下：UTF-8 是 `[104,101,108,108,111]`，5 个字节，没有 0；UTF-16 每个字符后面跟一个 0，共 12 字节；UTF-32 每个字符后面跟 3 个 0，共 24 字节。

### 1.4 byte-level BPE 好在哪

所有文本先 `encode("utf-8")` 变成 0–255 的字节，BPE 只在字节层面操作。这带来三个好处：

- **初始词表大小固定是 256**。注意不是 128——UTF-8 流里字节会取到 128–255。
- **永远不会遇到未登录词**。任何字符拆到字节都逃不出 0–255，所以不需要 `<unk>` 这个特殊 token。
- **"某字符占几字节"的复杂度被 UTF-8 这一步完全吸收**，训练算法对此完全透明。

### 1.5 一个常见误解：LLM 说中文时串到韩文/日文，不是因为"字节接近"

这是我在做作业时顺带想清楚的一件事。

LLM 并不在字节层面预测，它在 **token ID** 上预测。中文和日文的 token 在词表里是两个不同的 ID，ID 相邻也没有任何语义关系，所以"字节接近导致混淆"这个解释站不住脚。

真正的原因有四条：

1. 训练数据里 CJK 混杂，导致三者在 **embedding 空间**里互为邻居；
2. 中文高质量数据相对稀疏，采样时容易漂移；
3. 采样本身的随机性；
4. tokenizer 不匹配，中文被切得很碎。

所以直觉需要纠正一下：不是字节接近，而是**向量空间里互为邻居**。字节只是最底层的存储形式，模型根本不在那一层"思考"。这一点和后面 §3.6 讲的"高频 token 学得更充分"是同一件事的两面。

### 1.6 两道书面题

**理解 Unicode**

`chr(0)` 返回的是空字符（Null character, NUL），ASCII 码值 0。它渲染不出任何字形，不占显示空间，但仍然占一个字符位置；C 语言用它作字符串结束标志。

它的 `repr` 显示成 `'\x00'`（可见的转义形式），而 `print` 出来是空的。原因是 repr 面向调试，要精确无歧义，所以用可见转义把控制字符"显示出来"；print 输出字符本身，而终端渲染不了控制字符。

它出现在文本里的效果是：字符存在但渲染不出来。它不会截断字符串（不像 C 里的 `\0`），`len` 仍然把它计入一个位置。

**Unicode 编码**

*为什么在 UTF-8 字节上训练 tokenizer 优于 UTF-16/UTF-32？* 因为 UTF-8 对常见字符只用 1 字节，字节序列比 UTF-16/32 短得多；更关键的是，UTF-16/32 会插入大量填充的 `\x00`，这些 `\x00` 会成为高频字节对，让 BPE 把有限的合并名额浪费在无意义的填充上，学不到真正有用的子词。

这里有两个措辞坑要避开：不要说"UTF-8 是压缩/最优压缩"（它是编码规则，不是压缩算法）；不要说 BPE 是"聚类"（BPE 是频率驱动的贪心合并，不是 clustering）。

*为什么逐字节 decode 是错的？* 因为非 ASCII 字符在 UTF-8 里由多个字节共同编码，逐字节单独 decode 会把它们切断。例子：`"café".encode("utf-8")` 是 `[99,97,102,195,169]`，前三个 ASCII 字节能各自解码，但到 `\xc3`（195）时，它是 2 字节序列的首字节（二进制 `11000011`，`110` 开头声明后面还有 1 个续接字节），单独解码时续接字节缺失，直接报 `UnicodeDecodeError: unexpected end of data`。

*给一个不能 decode 成任何字符的双字节序列。* 核心是违反 UTF-8 的前缀规则（合法双字节必须是 `110xxxxx 10xxxxxx`）。三种非法方式：

| 例子 | 为什么非法 | 报错关键词 |
|---|---|---|
| `bytes([0xff, 0xff])` | `0xff` = `11111111`，前缀 `11111` 不属于任何合法类别 | invalid start byte |
| `bytes([0x80, 0x80])` | `0x80` = `10000000`，`10` 开头是续接字节标记，不能当开头 | invalid start byte |
| `bytes([0xc3, 0x28])` | 首字节 `0xc3` 是合法的 2 字节头，但 `0x28` 是 ASCII，不是 `10` 开头的续接字节 | invalid continuation byte |

推荐答后两个，因为能体现你理解了"续接字节"这个概念。

## 2. BPE Tokenizer

一句话概括 BPE：**从 256 个字节出发，反复把"最常相邻的 token 对"合并成新 token，直到词表达到目标大小。**

整个训练分三步：

```
① 256 个字节 + 特殊 token          → 初始词表
② 语料 → 按特殊 token 切开 → 正则切分 → 转字节 → 统计 {片段: 出现次数}
③ 循环 { 数所有相邻对 → 选最高频的 → 加入词表并记录 → 全局替换 }
```

产出两样东西：**vocab**（`dict[int, bytes]`，ID 到字节串的映射）和 **merges**（`list[tuple[bytes, bytes]]`，按创建顺序排列的合并规则）。

### 2.1 第一步：初始词表

初始词表 = 全部 256 个字节值（ID 0–255）+ 特殊 token。之后每合并一次，词表加 1。

$$\text{vocab\_size} = \underbrace{256}_{\text{初始字节}} + \text{合并次数} + \text{特殊 token 数}$$

反过来就是：**合并次数 = vocab_size − 256 − 特殊 token 数**。比如 TinyStories 用 `vocab_size=10000` 加 1 个特殊 token，就要合并 9743 次。

三种来源的 token，参不参与合并是不一样的：

| 来源 | 参与合并吗 |
|---|---|
| 256 个字节（初始化） | 参与，是合并的原料 |
| 合并产生的 token | 参与 |
| 特殊 token（人为加入） | **不参与**。它是硬边界，不进入 merge 统计，但占一个 ID |

造字节时有两个坑：`bytes([i])`（**方括号**）才是造一个值为 i 的单字节，`bytes(65)` 得到的是 65 个 `\x00`，`bytes('A')` 直接报错。另外把一个词转成字节要用 `list(token.encode("utf-8"))`——`[ord(c) for c in token]` 得到的是**码点**不是 UTF-8 字节，遇到非 ASCII 就错了。

特殊 token 这次只用到 `<|endoftext|>`。它们的共同本质是：人为定义、永不被拆开、占一个固定 ID 但不参与合并。

不同模型放置特殊 token 的位置不一样（GPT-2 放末尾、Llama 放开头），这纯粹是设计选择。实现时还有一点：接口签名是 `list[str]`，别写死"只有一个"——测试里就有多个特殊 token 的用例。

### 2.2 第二步：预分词

这一步不做任何合并，只是准备一张"片段 → 出现次数"的频率表。顺序很重要：

```
原始语料
→ 先按 special_tokens 切开（要 re.escape，因为 token 里含 | 等正则元字符）
→ 每段用 GPT-2 的正则切成 pre-token
→ 每个 pre-token 转成 UTF-8 字节序列 → 统计次数
```

产物长这样：`(l,o,w): 5`、`(l,o,w,e,r): 2`、`(w,i,d,e,s,t): 3`、`(n,e,w,e,s,t): 6`。

**为什么需要这一步？** 做个思想实验：如果不预分词，直接把整个文本当成连续字节流，你会数到大量跨词边界的字节对。后果有三条：

1. **语义割裂**。`dog`、`dog!`、`dog.`、`dog?` 会变成 4 个毫不相干的 ID，语义几乎一样却各学一份，白白浪费词表格子。
2. **跨词的无意义组合**。像 `e␣t`（横跨两个词）这种纯统计噪声会占掉词表，却学不到任何东西。
3. **效率灾难**。不预分词的话，每一轮要数的对数正比于**语料总字节数**；预分词之后，`the` 出现一百万次也只存一份加一个计数，工作量降到正比于**不同词的个数**，小好几个数量级。

切分的边界主要是空格，另外还有标点、数字/字母切换、英文缩写。要注意切出来的片段**不是最终 token**，它只是划定了合并的作用范围，片段内部仍然会被 BPE 继续切成子词。

GPT-2 用的正则（需要 `regex` 包，标准库 `re` 不支持 `\p{L}` 这种 Unicode 属性）：

```
PAT = r"""'(?:[sdmt]|ll|ve|re)| ?\p{L}+| ?\p{N}+| ?[^\s\p{L}\p{N}]+|\s+(?!\S)|\s+"""
```

六个用 `|` 连起来的选项，从左到右优先匹配：① 英文缩写后缀（`'s`/`'ll`/`'ve`/`'re`）② ` ?\p{L}+` 单词 ③ ` ?\p{N}+` 数字 ④ ` ?[^\s\p{L}\p{N}]+` 标点 ⑤ `\s+(?!\S)` 尾随空白 ⑥ `\s+` 兜底。

两个细节值得注意。一是**前导空格吸附**：选项②开头那个 ` ?` 会把空格吸到词的**前面**，所以 `some text` 里的 `text` 会切成 ` text`。这就是为什么 GPT-2 系模型里 ` the` 和 `the` 是两个不同的 token。二是**选项⑤必须排在⑥前面**：交替是从左到右优先匹配，具体规则要放前面、兜底放后面。

实测一下：`re.findall(PAT, "I'll pay $100 now!!")` 得到 `['I', "'ll", ' pay', ' $', '100', ' now', '!!']`。

**我在预分词里修过两个 bug，关键是 pytest 全绿也抓不到它们：**

| bug | 触发条件 | 后果 | 修法 |
|---|---|---|---|
| `re.split("", chunk)` | 特殊 token 列表为空 | pattern 是空串，等于在每个字符之间都切一刀，pre-token 全被打成单字符 | 空 pattern 时直接返回原串，不做 split |
| 分块边界硬编码 `b"<\|endoftext\|>"` | 特殊 token 不叫这个名字 | 找不到切点，边界全退化到文件末尾，32 个进程变成 1 个，并行完全失效（实测在 `<\|sep\|>` 语料上：修前 1 块、修后 32 块） | 用 `special_tokens[0].encode()`；没有特殊 token 时退化成单块 |

第一条后来在 `encode` 里以另一种形式又出现了一次（切分用的正则为空时要置成 `None`）。**同一个"空集合"边界，两个地方都要防。**

顺带一提，这套正则至今仍是主流骨架。GPT-4 的 `cl100k_base` 最重要的改动是**限制数字长度为 `\p{N}{1,3}`**：`12345` 会被切成 `123` + `45`，这样算术任务更稳定，词表也不会被各种长数字撑爆。

### 2.3 第三步：合并循环

每一轮四个动作，循环到词表满为止：

1. **数所有相邻对**（要加权）：遍历频率表，数每个 pre-token 内部的相邻对，乘以该 pre-token 的出现次数。
2. **选最高频的对**：平局时选**字典序更大**的（这正好是 Python `max` 对 `tuple[bytes, bytes]` 的默认行为）。
3. **记录**：新 token 加入词表拿到下一个 ID，该对追加进 merges 列表。**顺序很重要**，encode 时要按这个顺序重放。
4. **替换**：把所有 pre-token 内的该对合并成单个 token。回到第 1 步。

拿前面那个例子逐帧走一遍：

| 轮次 | 数对（只列关键项） | 选谁 | 为什么 | 替换后 |
|---|---|---|---|---|
| 1 | `(e,s):9  (s,t):9  (w,e):8  (l,o):7  (o,w):7` | `(s,t)` | 和 `(e,s)` 平局，字典序 `s`(0x73) > `e`(0x65) | `(w,i,d,e,st)`、`(n,e,w,e,st)` |
| 2 | **`(e,st):9`** ← 新冒出来的 | `(e,st)` | 最高频 | `(w,i,d,est)`、`(n,e,w,est)` |
| 3 | `(l,o):7  (o,w):7` | `(o,w)` | 平局，`o` > `l` | `(l,ow)`、`(l,ow,e,r)` |

最终 `merges = [(s,t), (e,st), (o,w)]`，词表里多了 `b'st'`、`b'est'`、`b'ow'`。

有两个核心理解：

- 这个循环本质上是**反复修改同一张频率表**：扫表 → 选最高频 → 记录 → 就地合并 → 用改动后的表再来一遍。
- **为什么必须串行**：第 2 轮选中的 `(e,st)` 是第 1 轮合并的**产物**，在第 1 轮之前根本不存在。所以无法提前知道第 2 轮会选谁——**这条依赖链无法打破**。（并行的可能性见 §2.6。）

### 2.4 让它跑得快：四个数据结构 + 三项技术

朴素实现每轮都全量重数所有 pair、重建所有词，复杂度是 $O(\text{轮数} \times \text{语料大小})$。我最终的实现靠四个常驻数据结构协同做**增量维护**：

| 结构 | 类型 | 作用 |
|---|---|---|
| `global_vocab_ids` | `list[list[int]]` | 每个词的 id 序列，原地修改（下标就是词的标识，必须稳定） |
| `global_vocab_counts` | `list[int]` | 每个词的出现次数，下标对齐 |
| `global_pair_counts` | `Counter` | 每个 pair 的全局加权计数——**这是真相源** |
| `global_pair_to_words` | `dict[pair, set[int]]` | pair → 含有它的词的下标集合，**增量更新的关键索引** |
| `global_word_pairs` | `list[dict[pair, int]]` | 每个词内部的 pair → 次数，常驻，用来判断成员关系 |

每一轮的流程变成：从堆里取出 best_pair，**只遍历 `pair_to_words[best_pair]` 里的那些词**（而不是所有词），每个词重建序列，只更新真正变化的 pair 计数。

#### 技术 1：delta 更新

考虑一个词 `[a,b,c,d,e]`（出现 5 次），合并 `(c,d) → X`：

| pair | 合并前 | 合并后 | delta | 要动吗 |
|---|---|---|---|---|
| `(a,b)` | 1 | 1 | **0** | 不动，它离合并点远 |
| `(b,c)`、`(c,d)`、`(d,e)` | 1 | 0 | −1 | 计数 −5，并 push 进堆 |
| `(b,X)`、`(X,e)` | 0 | 1 | +1 | 计数 +5，并 push 进堆 |

**为什么 delta 一定正确**：一个 pair 的全局计数等于各个词的贡献之和。这个词在合并前贡献 `old × count`、合并后贡献 `new × count`，净变化就是 `(new − old) × count`。只把这个 delta 加上去，全局计数就是对的。

而 `delta == 0` 的 pair 计数没变，意味着堆里那条旧条目**依然有效**，不用 push，不变量不会被破坏。

验证一个边界情形 `A B A B` 合并 `(A,B)`：合并前是 `{(A,B):2, (B,A):1}`，合并后是 `{(X,X):1}`，delta 全都对得上。

这个思路是「局部改动、大部分不变」这类增量维护问题的通法。

**增量维护的四条记账纪律**（每一条都是被 bug 逼出来的，静态看代码查不出来）：

- 计数减到 0 的 pair 必须从字典里删掉，否则后面会选到"僵尸对"；
- 遍历 `affected` 集合前必须先拷贝一份，因为循环体里会修改这个 set；
- 从集合里移除用 `.discard()` 而不是 `.remove()`，因为同一个词可能多次贡献同一个 pair（比如 `A B A B`）；
- 从字典里删 key 用 `pop(k, None)` 而不是 `del`，因为这个 key 可能已经在减计数那一步被删过了。

#### 技术 2：懒删除堆

这是个通用技巧，值得单独记一笔。

**问题**：Python 的 `heapq` 不支持高效修改堆里已有元素的优先级（要 O(n) 扫描才能找到它），但 BPE 里 pair 的计数在频繁变化。

**解法**：不改旧的，只 push 新的；旧的留着变成 stale（陈旧条目），弹出时验证一下再丢弃。

```python
def push(self, pair, count):          # 从不扫描堆，只做 sift-up，O(log n)
    heapq.heappush(self.heap, (-count, tie_break_key, pair))

def pop_best(self, pair_counts):      # 和「真相源」核对
    while self.heap:
        neg_count, _, _, pair = heapq.heappop(self.heap)
        if -neg_count == pair_counts.get(pair, 0) and -neg_count > 0:
            return pair               # 堆里的值 == 真值，有效
    return None                       # 否则是 stale，丢弃继续弹
```

几个要点：

- push 一个已存在的 pair 会留下**重复条目**（旧的 stale + 新的有效），这是**故意的**，不是 bug。
- **真相源在别处**：`pair_counts` 才是权威，堆只是一个"大概按优先级排好"的加速结构。
- 正确性靠两条不变量：① **无遗漏**——任何计数大于 0 的 pair，堆里至少有一条携带它当前计数的条目（靠"每次计数变动都紧跟一次 push"保证）；② **可鉴别**——堆里的 key 是 `(pair, count)` 的纯函数，对不上就是 stale。这两条合起来保证：第一个通过校验的弹出结果必然是真正的最优。
- **膨胀治理**：堆只增不减，而 `log n` 里的 n 就是堆长度。我加了个 `maybe_rebuild`，在堆长超过 `2×存活数+1024` 时按当前计数重建。

什么时候该想到这个技巧？**任何"优先队列 + 元素优先级频繁变化"的场合**——Dijkstra 的变体、事件调度、任务队列。标准库的堆不支持 decrease-key，懒删除是最常用的绕过法。判据是：修改频繁，且有一个独立的"真相源"能在 pop 时做验证。

#### 技术 3：用 min-heap 模拟 max，以及 tie-break 反转

规则是"频率高的优先，平局取字节字典序**大**的"，但 `heapq` 是 min-heap，所以：

- 频率：存 `-count`。
- 字节：需要反转字典序，用 `neg_bytes(b) = tuple(-x for x in b) + (1,)`。

**末尾那个哨兵 `(1,)` 是整个实现最大的坑。** `tuple(-x for x in b)` 确实反转了字节值，但元组比较里「前缀相同时短的更小」这条**长度规则没有被反转**，导致 `b'b'` 和 `b'bc'` 会选错。加上一个正数哨兵之后，更长的串在对应位置补的是负数，在 min-heap 里更小，于是复现了"长的更大"。

哨兵必须是正数：用 `0` 会和 `neg_bytes(b'\x00')` 撞车；用补码方案（`b"\xff"`）也会撞（`\x00` 的补码正好是 `\xff`）。

我写了穷举验证：对所有包含 `\x00`/`\xff` 的 1~3 字节串做 66306 组比较，朴素版有 **936 组违反**反序，哨兵版 **0 组违反**。

### 2.6 并行性分析：结论会随规模翻转

| 阶段 | 能并行吗 | 说明 |
|---|---|---|
| 预分词 | 可以，数据并行 | 用 `multiprocessing` 绕开 GIL，按特殊 token 切块。**价值全在这里**——它随数据量线性增长 |
| Merge loop | 看规模 | 每一轮都要"全局决策 + 依赖上一轮结果"，只能在**一轮之内**并行（把受影响的词分给多个 worker） |
| GPU / 线程 | 不行 | GPU 不适合这种符号处理；线程受 GIL 限制，而循环体是 100% Python 字节码 |

merge loop 划不划算，完全取决于每一轮的粒度（对照基准：派发 32 个空任务大约要 300 µs）：

| 规模 | 不同 pre-token 数 | 每轮词循环耗时（中位数） | 结论 |
|---|---|---|---|
| TinyStories valid + vocab 10k | 6 万 | **3.5 µs**——开销比工作量贵 85 倍 | 绝无可能 |
| OpenWebText train + vocab 32k | **660 万** | 0.3 ms（均值 20.5 ms）——开销只占 1.5% | 值得算一算 |

如果真要做，**正确的形状是永久分片**：每个 worker 常驻持有 `words[k::N]` 和自己那份局部 `pair_to_words`，父进程每轮只广播 `(id_a, id_b, new_id)`（几十字节），worker 回传局部 delta。而不是每轮把词的 id 序列 pickle 进 worker——实测一轮最多要搬 **714 万个 id**，搬运量正比于工作量，那就白搭了。

**但理论上限只有 2.82×**（优化后重测的分解：worker 侧 67%、父进程的 `pair_counts` + heap **28%** ← 这是硬地板、`pop_best` 5%）。优化前上限是 3.92×——第 10 条优化砍掉的正好是可并行的那部分，所以上限跟着掉了。要突破 28% 的地板，得连堆也分片，复杂度和 tie-break 的风险都要上一个档次。

再算上固定的通信开销约 9.5 s（31743 轮 × 一次 round-trip）：在 owt valid 上（loop 才 20.8 s）净收益只有 1.2×，**不值得**；在 owt train 上（loop 236.5 s，轮数相同）通信只占 4%，能到约 2.5×。

**同一份并行代码，在两个语料上一个赚一个赔。** 轮数固定而每轮工作量随语料增长，是并行在这里能成立的唯一原因。

### 2.7 优化方法论：五条教训

先说流程。每条优化都走一遍，不跳步：

**定基线**（跑 3 次取中位数，并把 merges 存下来作为正确性基准）→ **profile 找热点** → **一次只改一条** → **对拍 merges 逐条相同**（不同就直接回滚，不去 debug 性能）→ **测时** → **记账** → **收益低于 5% 就回滚** → 全部做完后在**目标语料**上确认。

#### 教训 1：测量规模决定结论，甚至能让结论反转

同一个改动，懒删除堆在小语料（corpus.en / vocab 500）上和不用堆**差不多甚至略慢**（维护开销约等于省下的扫描），但在 valid / vocab 10000 上是 9.8×。

再比如预分词的 `findall` 改动：单进程下 1.54×，32 进程下只有 1.29×（固定开销占比变大），到 2.23 GB 语料上才回到 1.67×。

所以要准备**两级语料**：迭代用的语料要快（几十秒一轮）**并且保留目标语料的特征**。owt valid（290 MB）合格；TinyStories **不合格**——它的 `affected` 中位数是 1，所有和"每轮粒度"相关的优化在它身上全都测不出来。

#### 教训 2：GC 是隐藏的大头，而且会把正确的优化伪装成负收益

第 10 条优化单独上、GC 开着的时候，测出来是 42.75 → 54.16 s，**看起来是 −27% 的负优化**，我差点直接回滚。关掉 GC 才发现它其实是 28.21 → 19.22 s，**正收益 47%**。

原因是：merge loop 每轮要分配几百万个小容器（新序列、per-word dict、heap key 元组），它们**不构成引用环**、靠引用计数就能回收，但分代 GC 仍会在每次 gen-2 扫描时遍历整个存活集合——而这个集合恰好被那些常驻 dict 撑得很大。**分配得越多，GC 罚得越狠。**

所以：**任何"多分配换少计算"的优化，评估前必须先把 GC 排除掉**，否则你测到的是 GC 的账，不是你的账。

#### 教训 3："空间换时间"不是无条件成立的，要看空间进了哪个数据结构

同一轮里两条改动都是花内存，结果完全相反：per-word 计数常驻（多占 2~3 GB）**快 1.42×**；让堆无限增长（多占 1.3 GB）**慢 2.6×**。

区别在于：dict 是 **O(1)** 查找，多占内存不影响单次操作的成本；堆是 **O(log n)**，而 n 就是堆长度。**给对数级的数据结构塞空间是自伤。**

#### 教训 4：每改一条就要重新 profile，优化清单会被上一条优化作废

"heap key 缓存"这条是照着第 10 条**之前**的 profile 定的（那时 `_neg` 被调用了 4080 万次）。而第 10 条减少了 touched pair、连带减少了 push，heap 早就不是热点了，实测收益 0。

#### 教训 5：微基准和整体跑可能给出相反的结论

第 10 条的微基准是**每个词快 3.5×**，整体却慢 27%——差异全在 GC 这种全局效应上。**微基准只能解释局部，不能拍板。**

#### 关于 profile 和验证

profile 用 `cProfile.run(..., 'prof')` 加 `pstats.Stats('prof').sort_stats('tottime')`。主要看 **tottime**（函数自身耗时，找瓶颈看它）和 **ncalls**（几百万次的就是热点）。

实战效果：profile 直接指出 `max` 占 7.3 s、`rank` 占 6.6 s（被调用了 **1 亿次**），加起来几乎是全部时间，直接指向"用堆替代每轮全扫"；后来又指出 667 万次 `Counter` 构造，指向了邻域增量。**先 profile 再优化，别猜。**

**怎么验证优化没改坏结果**（计数漂移这类 bug 静态看不出来，唯一可靠的办法是对拍）：

1. **差分测试**：写一个每轮全量重算的 brute-force 版本，逐条比对 merges 和 vocab。语料要**专门造刁钻的**——大量 pair 同频的 tie 语料（测 tie-break）、`aaaa` 这种重叠串（测贪心从左到右 + 重叠记账）、中文和带音标的拉丁字母（测多字节）、随机串。
2. **不变量断言**：每步 merge 之后从 `vocab_ids` 从零重算真值，校验 `pair_counts` 没有漂移、`pair_to_words` 和真值相等、**每个存活的 pair 都有一条携带当前计数的堆条目**（最后这条是懒删除正确性的命根子）。
3. **官方测试**。

| **压缩率**（训练语料全量） | **4.071 字节/token** | **4.363 字节/token** |
| 平均 token 长度 | 5.79 字节（中位 6） | 6.34 字节（中位 6） |
| **最长 token** | `b' accomplishment'`（15 字节） | 64 字节的**乱码**（见下） |
| 落盘大小 | 0.2 + 0.2 MB | 0.6 + 0.5 MB |

**怎么读这组数**：OpenWebText 的 4.363 只比 TinyStories 的 4.071 高 7%——**词表大了 3.2 倍，只换来这么点压缩率**。原因有两层：① 边际收益递减，BPE 先合并的都是最高频的模式，后面那 2.2 万个格子吃的都是长尾；② OpenWebText 的长尾里有相当比例是乱码和分隔线（见下），这些 token 覆盖的文本占比极低，对整体压缩率几乎没有贡献。

**词表翻倍不等于压缩率翻倍**——这是选 vocab_size 时要记住的。

顺带一个实用技巧：这个压缩率是**免费**得来的，而且**可以当作 `encode` 的现成验收标准**。写完 `encode` 后在训练语料上跑一遍，字节/token 应该和这个数很接近，对不上就是 `encode` 有 bug。不用另写 brute force。

它为什么是免费的？因为 merge loop 结束时，每个词的 id 序列就是"依次施加 merge 1..N 之后的结果"，而 `Tokenizer.encode` 做的也正是依次施加 merge 1..N。**训练结束时整个语料已经被编码过一遍了**，只需要在建索引时额外记下每个词的原始字节数（一个 int）。注意要用出现次数加权：频率表里 `the` 只存一份，但语料里它出现了上百万次。

#### 「最长 token 合理吗」——答案是不合理

OpenWebText 最长的 10 个 token **一个真词都没有**：

```
 64B  'ÃÂÃÂÃÂÃÂÃÂÃÂÃÂÃÂÃÂÃÂÃÂÃÂÃÂÃÂÃÂÃÂ'
 64B  '----------------------------------------------------------------'
 48B  '————————————————'
 32B  '________________________________'   '================================'
 32B  '................................'   '********************************'
```

那个 64 字节的是 `b'\xc3\x83\xc3\x82'` 重复 16 次，也就是 **double-encoded UTF-8 mojibake**（重复编码乱码）：一段 UTF-8 字节被误当成 latin-1 解码、再按 UTF-8 编码回去，每错一轮就多一层 `ÃÂ`。

举个例子，不换行空格 U+00A0 的 UTF-8 是 `\xc2\xa0`，误读成 latin-1 得到 `'Â '`，再编码成 UTF-8 就是 `\xc3\x82\xc2\xa0`。64 字节说明同一段文本在爬取管线里被**错误转码了很多轮**。

对照 TinyStories 最长的 10 个，全是规规矩矩的英文词：` accomplishment` / ` disappointment` / ` responsibility` / ` uncomfortable` / ` compassionate`……

**结论**：TinyStories 的最长 token **合理**——GPT-4 生成的干净儿童故事，最长 token 自然就是最长的常用词。OpenWebText 的最长 token **不合理**——它反映的是网页语料的编码损坏和排版分隔线，不是语言结构。

要强调的是：**算法没错，是数据脏**。这些字节序列确实高频，BPE 忠实地把它们学了下来。

这引出一个更值得追问的问题：**词表里到底有多少格子被垃圾占掉了？** 这直接吃掉压缩率，也吃掉 leaderboard 上宝贵的 token 预算。真实的预训练管线会先做数据清洗（去重、编码修复、过滤），这正是后面数据那个 assignment 的主题。

#### 序列化：为什么选 JSON + latin-1

落盘要存 `vocab.json` 和 `merges.json`。测试完全不碰加载函数，格式随便选，但有几个决定值得记一笔。

**首先，bytes 塞不进文本格式。** 实测 `vocab_size=300` 的词表里，**128/300 个 token 不是合法 UTF-8**（多字节字符的续接字节，单独拿出来就是非法的），直接 `b.decode("utf-8")` 会崩。三种解法：

| 方案 | 谁在用 | 做法 |
|---|---|---|
| byte → unicode 映射 | GPT-2 的 `vocab.json` / `merges.txt` | 把 256 个字节各映射到一个**可打印**字符（空格→`Ġ`、换行→`Ċ`）。这个 trick 是为了迁就 `merges.txt` 用空格分隔两个 token 的文本格式——不映射的话，token 本身是空格就产生歧义了 |
| **latin-1**（我选的） | — | 字节 0–255 一一映射到码点 U+0000–U+00FF，所以 `b.decode("latin-1").encode("latin-1") == b` 对**任意**字节串成立。merges 我存成 JSON 数组而不是空格分隔，所以不需要 GPT-2 那套 trick |
| base64 | tiktoken / Llama 3 | 最保险，代价是不可读 |

**有三层容易搞混**，以 id=195 为例：token 是 1 个字节（值 195）→ JSON 文本里是 1 个字符（码点 195，也就是 `'Ã'`）→ **磁盘上是 2 个字节**（`C3 83`，因为文件本身按 UTF-8 写）。所以所有 ≥128 的字节在磁盘上都膨胀一倍。

### 2.9 Tokenizer 的 encode / decode

测试结果：24 passed, 1 xfailed（那个 xfail 是测试自己标的，`encode` 不要求省内存）。

**但绿灯不等于证明。** 有个测试用装饰器把内存限制到 1 MB，可它在 `finally` 里就把限制还原了，而被装饰的函数是**生成器函数**——调用它只创建生成器、不执行，等真正迭代时限制早就撤了（实测：普通函数里 rlimit=14MB 生效，生成器迭代时是"无限制"）。

所以那个 PASSED 的证明力比看起来弱得多。真正的依据是**结构本身**（用 `yield` + 缓冲区只留未结算的尾巴）和我自建的对拍。**测试测的是它写下的那个条件，不一定是你以为的那个条件。**

#### 构造函数要建四张表

传进来的 `vocab` 和 `merges` 都答不了 encode 要问的问题：

| 表 | 类型 | 为什么需要 |
|---|---|---|
| `inverse_vocab` | `dict[bytes, int]` | `vocab` 方向反了；合并操作的是 bytes，输出要 ID |
| `merge_rank` | `dict[pair, int]` | 在 list 里查"排第几"是 O(n)；rank 就是它在 `merges` 里的下标 |
| `cached_word_ids` | `dict[str, list[int]]` | pre-token 记忆化。key 用 `str`，命中时能省一次 `.encode()` |
| `special_split_pat` | 编译好的正则 | 依赖 `self.special_tokens`，不能放模块级 |

两个坑：特殊 token 要追加进 vocab，并且**必须同步更新 `inverse_vocab`**；另外 `special_tokens` 这个参数即使 vocab 里已经全有也得传——`vocab` 只是 `id → bytes`，**它没有标记谁是特殊的**。

#### encode 分三段

① 用 `special_split_pat` 切开并保留分隔符，特殊 token 直接查表；② 普通段过 GPT-2 正则；③ 每个 pre-token 单独做合并。

第①步**必须独立，不能把特殊 token 塞进主正则当成一个 or 分支**。这是被 tiktoken 当裁判实测出来的：`'x <|endoftext|> y'` 合进主正则会得到 `['x', ' <|', 'endoftext', '|>', ' y']`——特殊 token 被切碎了。

原因是正则交替是逐位置尝试的：扫到 `<` 前面那个**空格**时，special 分支不匹配，而 ` ?[^\s\p{L}\p{N}]+` 这一支会贪心地吃掉 `' <|'`。**加个 or 分支救不了。**

切分正则有三个要点：`re.escape`、外层加捕获组（`re.split` 才会保留分隔符）、**按长度降序排列**（因为交替是从左到右优先，不是最长匹配）。

#### 合并单个 pre-token

做法是：拆成单字节 → 循环 { 挑 `merge_rank` 最小的相邻对，合并它的所有出现 } → 挑不到就退出。

这和"从头遍历所有 merge 规则"**完全等价**（实测 277 个 pre-token 零差异），但**快 119 倍**。

等价的依据是：训练时新 token 的 id 等于当时的词表长度，所以任何用到 `X` 的 merge，它的 rank 必然大于造出 `X` 的那条；而合并之后新冒出来的对只可能包含 `X`，所以都在前方。

成本对比：遍历法固定要跑 5 万次，挑最小法最多跑「词长−1」次，实际约 **3 次**（加权平均 pre-token 只有 4.22 字节）。

**这里不要用堆。** 候选只有约 3 个，且每轮只取一次最小值，实测 `min()` 在 3~2000 各种规模下都比 `heapify + pop` 快两倍多。对照训练那边堆赢了 9.8×——**同一个优化，规模不同结论相反**，又一次印证了 §2.7 教训 1。

#### encode_iterable 的三条不变量

要求是 5 MB 文件在 1 MB 内存里跑完，且必须和整体 `encode` 逐 token 相同。

| # | 危险 | 守法 |
|---|---|---|
| 1 | 特殊 token 横跨切点，split 只看到半截 | 结算上限设为 `len(buf) − (最长特殊token长度 − 1)`；如果仍落在某个特殊 token 匹配内部，再退到它的起点 |
| 2 | 最后一个正则匹配可能还没吃完（`\s+(?!\S)` 要看后一个字符） | **扣住最后一个匹配**不结算。只扣最后一个文本段——被特殊 token 夹住的段是硬边界 |
| 3 | **吐已经算好的 token，不能拿结算前缀重新跑正则** | 最短反例是 `'\n\n!!'`：整体切是 `['\n','\n','!!']`，但单独对 `'\n\n'` 跑 findall 时，前瞻在字符串末尾成功，得到 `['\n\n']`。**我在这栽了两次** |

实现上用 `itertools.chain(iterable, [None])` 加一个哨兵、延迟一拍，才能知道当前块是不是最后一块。

有个直觉上的做法行不通：「只在遇到特殊 token 时才结算」——因为 roundtrip 测试**没有传特殊 token**，没有刷新点，缓冲区会一路涨满整个文件。

已知局限：一个巨大的连续空白串整体是一个匹配，会全堆在缓冲区里。

#### decode

`b"".join(...).decode("utf-8", errors="replace")`。**必须先拼接再一次性解码**——merge 可能落在多字节字符的中间，逐个 token 解码会各自失败，变成两个 `�`。

**验证手段**：官方测试（含一批和 tiktoken 逐 token 对比的用例）+ 自建对拍器（1011 个刁钻用例 × 3 种特殊 token 配置 × 5 种切法，包括 chunk=1 和逐行）。上面那三条不变量是被反例逐个逼出来的，**每错一次就往语料里加一个用例**。

### 2.10 实验和数据落盘

#### 压缩率（字节/token，越大越好）

| 样本 | 用哪个 tokenizer | 字节 | token 数 | 字节/token |
|---|---|---|---|---|
| TinyStories 10 篇 | TinyStories (10k) | 7,633 | 1,861 | 4.102 |
| OpenWebText 10 篇 | OpenWebText (32k) | 60,084 | 13,586 | **4.422** |
| OpenWebText 10 篇 | **TinyStories (10k)** ← 交叉 | 60,084 | **17,952** | **3.347** |

只有后两行可比（同一份 OpenWebText 样本），第一行是另一份样本，只能横向看比值。

另外注意样本量差很多：10 篇儿童故事才 **7.6 KB**，10 篇网页有 **60 KB**。小样本的压缩率方差大，能和全量的 4.071 对上有运气成分——真要下结论应该看下面全量落盘的数字（4.116 / 4.371）。

**结论：用错 tokenizer，压缩率掉 24.3%、token 数多 32.1%。** TinyStories 的词表学自 GPT-4 生成的儿童故事，完全没有网页文本的词汇（URL、技术术语、非英文、排版符号），所以只能把 OpenWebText 切得更碎。

**这条有真实代价**：leaderboard 是固定 45 分钟的算力预算，token 效率低 32% 大致等于模型少看 32% 的文本；推理时 context window 也会更快耗尽。

顺带一提，这和"多语言不公平"是同一个机制——小语种被切碎，本质就是拿一个没覆盖这类文本的词表去编码。

#### 吞吐（单进程）

作业里拿 The Pile（825 GB）当尺度参照物，不是真的去跑，而是算一笔账：*这个 tokenizer 拿到真实规模的语料上要多久？* 一个慢 100 倍的实现（比如 `encode` 遍历全部 merge），同样这笔账就是 90 天，预处理直接变成工程阻塞。

| | 单进程 MB/s | 缓存命中率 | 处理 Pile 825 GB |
|---|---|---|---|
| TinyStories | **20.7** | 99.75%（每 401 次出现才真算 1 次） | 11.1 小时 |
| OpenWebText | **10.6** | 96.93%（每 32.5 次） | 21.5 小时 |

**别拿单进程除以 32 去估并行。** 实测 32 进程是 **187.2 MB/s**，加速比只有 **17.6×** 而不是 32×（效率 55%，损耗在 IO、pickle 回传、父进程拼接、负载不均）。所以 Pile 的实际估算是 **1.2 小时**，不是除以 32 得到的 0.67 小时。

**吞吐由缓存命中率决定，不由词表大小决定。** 同样 20 MB 的文本，OpenWebText 有 13.5 万个不同的 pre-token（TinyStories 才 1.3 万），真正需要做合并计算的次数多 10 倍。直觉容易归因于"词表大 3 倍所以慢"，实际原因是**语料多样性**。

#### 落盘产物（32 进程）

| split | 语料 | 耗时 | token 数 | 字节/token | 文件大小 |
|---|---|---|---|---|---|
| tinystories_train | 2.23 GB | 8.5 s (261 MB/s) | 5.41 亿 | 4.116 | 1.08 GB |
| tinystories_valid | 0.02 GB | 0.2 s | 546 万 | 4.117 | 0.01 GB |
| **owt_train** | **11.92 GB** | **63.7 s (187 MB/s)** | **27.27 亿** | 4.371 | **5.45 GB** |
| owt_valid | 0.29 GB | 2.5 s | 6640 万 | 4.367 | 0.13 GB |

**为什么存成 uint16**：范围 0–65535，装得下 32000 和 10000。换成 uint32 文件直接大一倍（5.45 → 10.9 GB），而训练时是用 `np.memmap` 随机采样的，**文件越小页缓存命中越好**。

前提条件是 `vocab_size ≤ 65536`，落盘时应该加断言。像 Llama 3（128k）、Qwen（15 万）那种词表就必须用 uint32。

**并行怎么做的**：按特殊 token 把文件切成「进程数 × 4」块，各个 worker 编码自己那块，父进程按块序拼接。

- **正确性**：边界落在特殊 token 的起点，而它是硬边界，pre-token 和 merge 都不会跨越，所以分块编码严格等于整体编码。实测验证过：valid 上 546 万个 token 与整体 `encode` 逐个相同，decode 回原文一字不差。
- **worker 回传 `np.uint16` 数组而不是 `list[int]`**：pickle 的是 2 字节/token 的连续 buffer，而不是几千万个 Python int 对象。
- **tokenizer 建在模块级**：Linux 上多进程走 fork，全局对象通过 copy-on-write 免费继承；而且 worker 跨任务复用同一个对象，缓存能累积（块数取 ×4 就是为了摊薄冷启动）。

最后一点值得单独说：**三条独立路径互相印证**——训练期从内部数据算出 4.071、采样 10 篇文档 encode 算出 4.102、全量落盘算出 4.116。完全不同的代码路径收敛到同一个数，这是**免费的正确性交叉验证**。

方法论上这比数字本身值钱：**任何时候一个量能用两条路算，就该都算一遍。**

### 2.11 延伸：分词的代价

> 这一节和作业实现无关，是顺带梳理的背景。

#### 三种主流分词算法

| | **BPE** | **WordPiece** | **Unigram LM** |
|---|---|---|---|
| 代表模型 | GPT 系、Llama 3、Qwen | BERT | SentencePiece：Llama 1/2、Gemma |
| 训练时选谁 | 频率最高的对 `count(AB)` | 似然提升最大，实践上约等于 `count(AB)/(count(A)·count(B))` | 反向操作：从大词表剪枝，去掉损失最小的 piece |
| **推理时怎么切** | **重放 merge 序列**（有序） | **词表内最长前缀匹配**（trie） | **Viterbi 求全局最可能的切分** |
| 交付物 | vocab + **merges** | **只要 vocab** | vocab + 每个 piece 的分数 |
| 贪心吗 | 是 | 是 | 否，全局最优 |
| 未登录词 | byte-level 下不存在 | 需要 `[UNK]` | 需要回退 |

**为什么 WordPiece 能贪心而 BPE 不能？** 因为两者把"编码"定义成了不同的东西：

- BPE 的定义是「**复现训练时发生过的那串操作**」，所以必然依赖顺序，必然要带着 merges 走。
- WordPiece 的定义是「**在词表里取最长**」，只依赖词表这个集合，与训练时怎么得到它无关。

这是设计取舍，不是谁更聪明。

**所以不能把 BPE 的 encode 改写成 trie 贪心。** 反例：merges 只有 `rank0: (b,c)→bc` 和 `rank1: (a,b)→ab`，编码 `"abc"`——BPE 挑 rank 最小的 `(b,c)`，得到 `[a, bc]`；trie 最长前缀得到 `[ab, c]`。**结果不同。** 不是那个算法不好，是它和你训出来的这套 merges 不配套。

#### 分词不是 Transformer 的缺陷，但有一条真实的因果链

分词发生在模型之外。Transformer 拿到的就是一串整数 ID，它不知道也不关心这些 ID 怎么来的。换成 RNN / LSTM / Mamba，问题一模一样。所以这不是 Transformer 架构的缺陷。

但有一条因果链值得记住：

> attention 是 $O(n^2)$，embedding 和最后的 softmax 是 $O(\text{vocab})$，所以分词是一道**压缩工序**，把序列长度压下来好让 $O(n^2)$ 付得起。

**它本身不产生任何语义价值。** 如果 attention 是免费的，直接喂字节就行——这正是下面那批工作的出发点。

#### 分词制造的真问题

| 问题 | 表现 |
|---|---|
| **算术差** | `12345` 的切法不稳定，学不到位值关系。GPT-4 限制数字长度就是为此打的补丁 |
| **字符级失明** | "strawberry 里有几个 r"——模型没见过字符，只见过几个 token ID |
| **多语言不公平** | 小语种被切得稀碎，同一句话花几倍 token，又贵又差 |
| **提示词边界效应** | 末尾多一个空格就换一套 token，行为跟着变（前导空格吸附） |
| **glitch token** | `SolidGoldMagikarp` 那一类：在词表里但训练语料几乎没出现，embedding 那一行从没被更新过，模型碰到就发疯 |
| **词表格子被垃圾占** | OpenWebText 词表里最长的 10 个 token 全是乱码和分隔线 |

**但最要命的一条不是"问题"而是"约束"**：**encode 必须和训练时完全一致。**

模型学的是「ID 47 后面常跟 ID 892」这种统计规律。训练时用 BPE 的 rank 顺序切、推理时改用贪心切，同一句话会变成一串不同的 ID，分布一偏模型立刻退化。这就是为什么测试里有一堆要求逐 token 对上 tiktoken 的用例——**tokenizer 不是"差不多就行"的组件，它是模型的一部分。**

#### 去 tokenizer 化的尝试

思路都是「把压缩这一步交给模型自己学，而不是外挂一个固定词表」。SSM 和线性注意力让长序列变便宜之后，这条路更有希望了。

| 工作 | 一句话 |
|---|---|
| **CANINE**（2021, Google） | 字符级编码器，下采样后再进 Transformer |
| **ByT5**（2021, Google） | 直接吃 UTF-8 字节的 T5，无词表 |
| **Charformer**（2021） | 学习式的子词切分，端到端可微 |
| **MegaByte**（2023, Meta） | 固定大小 patch + 局部/全局两级 Transformer，让字节级序列可扩展 |
| **Byte Latent Transformer**（2024, Meta） | 按**熵**动态划分 patch——信息量大的地方切细，平淡处切粗 |

读这批工作时要盯的共同问题：① 序列变长后算力怎么摊（这是分词存在的唯一理由）；② 去掉词表后，前面那张表里的问题解决了几条、又新增了什么；③ 和固定词表相比，同算力下的实际质量。

### 2.12 §2 小结

BPE 部分的 34 分全部拿下。产出的四个 `.npy` 文件就是后面训练时用 `np.memmap` 读的输入。

**要记住 tokenizer 速度和 LM 训练速度无关**：训练读的是已经落盘的 memmap 数组，tokenizer 不在那个循环里。真正影响训练的是它的**输出**——`vocab_size`（决定 embedding 和 LM head 的参数量、以及 softmax 开销）和**压缩率**（决定同样 token 预算下模型能看到多少文本，对 45 分钟的 leaderboard 是实打实的杠杆）。

所有优化都保持了 merges 逐条相同，也就是没有改变输出，所以没有影响训练。

最后一个小技巧：**数据探查用命令行比写 Python 快**。`grep -c/-oF`、`wc -l/-c`、`stat -c %s` 就够了。实测 TinyStories valid 有 27630 个 `<|endoftext|>`、22.5 MB；train 2.23 GB，倒推约 273 万篇文档，平均约 816 字节一篇。

## 3. Transformer 架构

这一章要实现从 token ID 到 logits 的完整前向，共 11 个小问题、29 分。实现顺序严格自底向上：Linear → Embedding → RMSNorm → SwiGLU → RoPE → softmax → 注意力 → 多头注意力 → Block → 完整 LM → 资源估算。

**和 §2 相比，战场变了。** §2 的失败模式是**算法逻辑**（计数漂移、tie-break、增量维护的记账），要靠 brute-force 对拍去抓；§3 的算法是给定的，失败模式几乎全是**形状、广播、维度顺序、dtype**，要靠形状断言、toy 输入和数学不变量去抓。工具也得跟着换。

进度：

| 小问题 | 分 | 状态 |
|---|---|---|
| Linear | 1 | ✅ |
| Embedding | 1 | ✅ |
| RMSNorm | 1 | ✅ |
| SwiGLU 前馈网络 | 2 | ✅ |
| RoPE | 2 | ⬜ |
| softmax | 1 | ⬜ |
| 缩放点积注意力 | 5 | ⬜ |
| 因果多头自注意力 | 5 | ⬜ |
| Transformer Block | 3 | ⬜ |
| 完整 Transformer LM | 3 | ⬜ |
| 资源估算（书面） | 5 | ⬜ |

### 3.1 整体地图

端到端的形状流：

| 阶段 | 输出形状 | 备注 |
|---|---|---|
| 输入 | `(batch, seq)` | 整数 token ID，来自 §2.10 落盘的 `.npy` |
| Token Embedding | `(batch, seq, d_model)` | 查表 |
| Transformer Block × num_layers | `(batch, seq, d_model)` | **进出同形状** |
| 最后一个 RMSNorm | `(batch, seq, d_model)` | pre-norm 架构特有 |
| LM head（Linear） | `(batch, seq, vocab_size)` | **logits，不是概率** |

两个骨架级的理解：

1. **`d_model` 是一条从头贯到尾的总线**，叫做残差流（residual stream）。中间那些 block 谁也不改变它的宽度，每个 block 只是往这条总线上"加"东西。
2. **block 进出同形状，所以能无脑堆叠**。这不是巧合，而是设计约束——正因如此 `num_layers` 才能当成一个自由超参。

pre-norm block 里两个子层是同一个模式：

$$y = x + \text{Sublayer}(\text{RMSNorm}(x))$$

子层一是带 RoPE 的因果多头自注意力，子层二是 SwiGLU 前馈网络。也就是**先 norm、再主操作、最后残差**。注意残差加回去的是 `x` 而不是 `RMSNorm(x)`——**这正是"残差流保持干净"的含义**。

有三个问题值得先想清楚：

**为什么 pre-norm 最后还要补一个 RMSNorm？** post-norm 里每个子层出口都归一化过，输出天然有界；pre-norm 把 norm 挪到了入口，残差流上的量层层累加就没人约束了，LM head 拿到的东西尺度会失控。所以必须在最后补一次。后面消融实验里 `pre_norm_ablation` 测的就是这个。

**位置信息在哪一步进入模型？** 对着架构图找一遍会发现，**embedding 之后没有任何位置编码**。位置信息只在每一层 attention 内部通过 RoPE 注入，而且只作用于 Q 和 K。这和 GPT-2 不同（GPT-2 是可学习的绝对位置 embedding，直接加在 token embedding 上），所以本模型只有**一张** embedding 表。

**模型返回 logits 还是概率？** 是 logits。作业文档自己有点不一致——开头说返回 "normalized probability distribution"、架构图顶上也画着 Softmax，但具体那道题说的是 "unnormalized distribution over the vocabulary (the logits)"。以后者为准。理由：cross-entropy 需要在内部做 log-softmax 才能数值稳定；生成时的 temperature / top-p 也要在 logits 上介入。

**可学习参数清单**（做资源估算时要用）：

| 组件 | 形状 | 个数 |
|---|---|---|
| token embedding | `(vocab_size, d_model)` | 1 |
| 每个 Block：注意力四个投影 + 前馈三个矩阵 + 两个 RMSNorm 的 gain | — | 9 × num_layers |
| 最后的 RMSNorm | `(d_model,)` | 1 |
| LM head | `(vocab_size, d_model)` | 1 |

两个容易漏的点：**RoPE 没有参数**（它的 cos/sin 是 buffer 不是 Parameter）；**本作业不做 weight tying**，LM head 和 token embedding 是两个独立的矩阵，所以 `vocab_size × d_model` 要算两次。

最后，构造参数里的 **`context_length` 只有一个用途——决定 RoPE 预计算 buffer 的长度**。它不出现在任何参数矩阵的形状里，这也是这套架构理论上能外推到更长序列的原因（效果另说）。

### 3.2 张量代数：einops 和内存序

作业文档花了整整两页讲 einsum 记号，不是凑字数。到多头注意力那一步，你要同时管 batch、seq、head、d_k 四个维度，用 `view` + `transpose` 拼很容易写出"跑得通但数值错"的代码。

**核心思想**：轴从"位置"变成"名字"——声明输入和输出各个轴叫什么，中间的 view/transpose/permute 交给库去推。所以文档里说 "documentation is implementation"，不可能出现"注释写着 `(b,h,s,d)` 但代码其实是 `(b,s,h,d)`"这种漂移。

三个 op：`rearrange`（纯搬运，元素数不变）、`reduce`（聚合）、`einsum`（收缩）。常用动作：

| 动作 | pattern |
|---|---|
| 换序 | `"a b c -> a c b"` |
| 合并轴 | `"a b c -> a (b c)"` |
| 拆分轴 | `"a (b c) -> a b c", b=4`（必须给出其中一个大小；不整除直接报错，等于免费的形状断言） |
| 加一个长度 1 的轴 | `"a b -> a 1 b"` |
| **任意批维** | `"... a b -> ... b a"` |

einsum 的判定只有两条规则：**同名的轴对齐配对相乘**；**左边有、右边没有的轴，沿它求和消去**。

有两个坑要记住。

**第一个是 `(a b)` 的顺序语义**：左边的 `a` 是慢变轴、右边的 `b` 是快变轴（合并后索引等于 `a*len(b)+b`，和 row-major 内存序是同一条规则）。**合并和拆分只有 `(a b)` 对 `(a b)` 才互逆。** 拆分时顺序写反的话，形状完全正确、代码照样跑、但元素被洗牌了，数值全错。到多头注意力拆 head 时，这就是决定成败的一行。

**第二个是 API 陷阱**：`einops.einsum(t1, t2, "pat")` 是张量在前，而 `torch.einsum("pat", t1, t2)` 是 pattern 在前、且只能用单字母轴名。建议全程只用 einops 版。

#### 行/列向量与 row-major 到底在说什么

作业文档里有一节讲这个，初读容易晕。精髓是：

数学习惯用列向量（$y = Wx$），这种写法批量化时 batch 只能放**后面**。但 PyTorch 是 row-major，batch 必须放**前面**——因为这样每个样本的特征在内存里是连续的一段，取一个样本等于顺序读一段内存，缓存友好；反过来存成 `(d_in, batch)` 就被打散成跳读了。

batch 在前就只能用行向量式 $y = xW^\top$，于是**数学和代码之间永远差一个转置**。

但要注意：**两种约定对 $W$ 的存储形状没有分歧，都是 $(d_{out}, d_{in})$**。分歧只在于 $x$ 从哪一侧乘进来。

而且——**用 einsum 就对这一节免疫**。写 `"... d_in, d_out d_in -> ... d_out"`，轴名一标，根本不存在"该不该转置"这个问题。

### 3.3 命名约定：模块树和 state_dict

这一条看起来琐碎，但它决定了后面九道题好不好写。

`state_dict` 的 key 是**属性名沿模块树拼接**出来的。所以属性名写错一个字母，整条路径就废了。课程提供的测试适配器文档里列出了参考实现的完整命名，开工前照着定名，后面每个适配器都只需要一行 `load_state_dict`：

| 层级 | 属性名 |
|---|---|
| LM | `token_embeddings` / `layers`（必须是 `nn.ModuleList`）/ `ln_final` / `lm_head` |
| Block | `attn` / `ln1` / `ln2` / `ffn` |
| 注意力内部 | `q_proj` `k_proj` `v_proj` `output_proj` |
| 前馈内部 | `w1` `w2` `w3` |
| 叶子参数 | `weight` |

拼出来的 key 形如 `layers.3.attn.q_proj.weight`、`ln_final.weight`。

注意 `layers` 必须用 `nn.ModuleList`。普通 Python list 里的子模块**不会被注册**，参数进不了 `state_dict`，优化器也看不见。

**`load_state_dict` 是原地拷贝**，等价于 `param.data.copy_()`。这意味着参数的 device 和 dtype **不会改变**，传进来的张量会被自动转换。建议保持 `strict=True`：key 或形状对不上就报错，**这是免费的命名校验和形状校验**。

三个坑：

1. 有些适配器给的是**裸 Tensor** 而不是字典，要自己包成一个单键字典（叶子模块没有路径前缀，key 就是 `weight`）；而 block 和 LM 那两个适配器给的**本身就是字典**，key 已经是全路径，可以直接传。
2. **device 和 dtype 要在构造时就对齐**，而且要取自权重张量（不是输入激活）。device 不一致的话 forward 会报错（**响的**）；dtype 不一致的话会**静默转换精度**（**哑的，更麻烦**）。
3. **persistent buffer 也会进 `state_dict`**。所以 RoPE 的 cos/sin 如果按默认方式注册，会多出参考实现没有的 key，`strict=True` 直接失败。**这才是作业要求 `persistent=False` 的真实原因**，不只是省磁盘。

调试技巧：key 对不上时，把两边的 key 集合做**对称差**，一眼看出谁多谁少。

还有一条设计原则：**适配器只做胶水**。里面出现的每一点逻辑，都说明模块本该提供而没提供。发现自己在适配器里写形状变换或默认值填充，就是模块接口设计有问题。

### 3.4 参数初始化

作业给了一组够用的初始化，细节留到后面的 assignment：

| 参数 | 分布 | 截断 |
|---|---|---|
| Linear 权重 | $\mathcal{N}(0,\ \sigma^2=\frac{2}{d_{in}+d_{out}})$，也就是 Xavier/Glorot | $[-3\sigma, 3\sigma]$ |
| Embedding | $\mathcal{N}(0,\ \sigma^2=1)$ | $[-3, 3]$ |
| RMSNorm 的 gain | 全 1（恒等变换） | — |

**Xavier 的分母是怎么来的**：前向传播希望激活方差逐层不变，这要求 $\sigma^2 \sim 1/d_{in}$；反向传播希望梯度方差不变，这要求 $\sigma^2 \sim 1/d_{out}$。两者一般不可兼得，取调和平均就得到了这个式子。

数值上感受一下：GPT-2 XL 的 $d_{model}=1600$，注意力那几个方阵的 $\sigma \approx 0.025$。而 GPT-2 论文里用的是固定 0.02——**同一个数量级**，不是巧合。

**Embedding 为什么不套 Xavier**：Xavier 的推导前提是"输出等于 $d_{in}$ 项的加权和"，靠求和的方差累积来定标度。但 embedding 是**取一行**，那个累积效应根本不存在，所以推导不适用，直接取单位方差。

**gain 如果顺手写成 0**：前向输出恒为 0、梯度也断了，loss 会卡在 $\ln(\text{vocab\_size})$ 一动不动。

**最大的坑**：`torch.nn.init.trunc_normal_` 的 `a`/`b` 参数是**绝对边界值**，默认是 `±2.0`。如果写 `std=0.02` 又不传 a/b，实际截断发生在 $\pm 100\sigma$，**等于完全没截断**。a/b 必须跟着算出来的 $\sigma$ 走。

另外三个值得知道的点：

- **截断不等于 clamp**。`randn().clamp()` 会把两条尾巴压成 $\pm 3\sigma$ 处的两个**点质量**，分布形状就变了；而 `trunc_normal_` 是逆 CDF 采样，直接从截断分布里抽。截断也不是理论洁癖：$3\sigma$ 外的概率是 0.27%，GPT-2 XL 的某个矩阵有 686 万个元素，**必然出现约 1.8 万个离群值**。
- **`torch.empty` + 就地初始化是 PyTorch 官方 idiom**（`nn.Linear.reset_parameters` 就这么写）。`empty` 只分配内存不填值，紧接着被逐元素全覆盖，省掉了一次注定要被覆盖的填充。
- **实测 `std()` 会比名义 $\sigma$ 低约 1.3%**，因为截断砍掉两条尾巴必然让方差缩水，而 PyTorch 不做补偿性 rescale。看到 0.987σ 是**正确行为，别当 bug 去查**，更不要后处理去凑。

最后是一条方法论上的提醒：**初始化这一块 pytest 完全测不到。**

测试都是加载给定的权重再比数值，你写的 `trunc_normal_` 根本不会被执行。$\sigma$ 写错、gain 写成 0、忘了截断，**测试照样全绿**。账要到真正训练时才结（loss 不降或者前几百步炸掉），那时已经隔了十几个组件，极难回溯。更麻烦的是作业文档自己说 "pre-norm 对初始化异常鲁棒"——意味着你连一个明确的失败信号都不会有。

所以要自己加断言：检查 `weight.std()` 是否接近理论 $\sigma$（允许低 1.3%）、`weight.abs().max()` 是否不超过 $3\sigma$。30 秒的事，能省掉后面一个下午。这是 §2.9 那条"绿灯不等于证明"的延续。

### 3.5 Linear

要点：不带 bias（跟随现代 LLM 的做法）；参数存 $W$ 而不是 $W^\top$，形状 `(d_out, d_in)`；属性名叫 `weight`；必须包在 `nn.Parameter` 里；必须支持任意批维；禁用 `nn.Linear` 和 `F.linear`。

我在这道 1 分的题上踩了五个坑，前两个**测试完全抓不到**：

| # | 坑 | 后果 |
|---|---|---|
| 1 | 参数没包进 `nn.Parameter`，只是个普通 tensor | 不进 `state_dict`、优化器看不见、`.to()` 搬不走、`load_state_dict` 无效。这四件事后面全是刚需 |
| 2 | `std` 硬编码成 0.02，且不传 `a`/`b` | 分布和截断双错，测试全绿 |
| 3 | einsum pattern 里批维写死成 `b` | 喂三维输入直接报错 |
| 4 | 属性名叫 `W`、类名小写 | 对不上参考 state_dict，后面两道大题要手工搬十几个张量。**这条有连锁后果，越晚改越贵** |
| 5 | 适配器里用 `weights.shape` 反推维度 | 见下 |

第 5 条值得展开。适配器的签名同时给了 `d_in`/`d_out`（**声明的契约**）和 `weights`（**实际的数据**）。用 `weights.shape` 去构造，模块形状就完全由数据定义了，于是 `load_state_dict` 的形状检查变成自己和自己比，**永远不可能报错**。而用 `d_in`/`d_out` 构造，它才真的在比对契约和数据，权重转置之类的错误会当场抛出 `size mismatch`，一眼定位。

这其实就是 §2.10 那条方法论的微型版：**任何时候一个量能用两条路算，就该都算一遍。**

### 3.6 Embedding

实现 Embedding 层的核心考点是禁用 `nn.Embedding`，要求我们自己用张量的高级索引（Advanced Indexing）完成查表。

**主要踩坑与心得：**

1. **高级索引的维度魔法**
   `weight` 的形状是 `(vocab_size, d_model)`。而输入 `x`（Token IDs）的形状是 `(batch, seq)`。
   当你写下 `weight[x]` 时，PyTorch 会保持 `x` 的骨架完全不变，把里面的每一个整数 ID 替换为 `weight` 中对应的整行向量。
   输出的形状立刻自然而然地扩展成了 `(batch, seq, d_model)`。这就是为什么代码能短到只有一行，而且天然支持任何形状的批维扩展。

2. **为什么“查表”是可微的？**
   我曾困惑过：直接用索引去挑一行，这不是不可微的离散操作吗？
   其实，查表在数学上严格等价于**输入 One-Hot 矩阵乘 Embedding 矩阵**。因为 One-Hot 里全是 0，所以底层直接用散列寻址优化了运算。反向传播时，它执行的是 `scatter-add`：把收到的梯度按行号累加回权重表里。

### 3.7 RMSNorm

RMSNorm（Root Mean Square Layer Normalization）是在 LayerNorm 的基础上去掉了减去均值的步骤，只保留了基于 RMS 的缩放操作，最后乘以可学习的参数 $g_i$：

$$\text{RMSNorm}(a_i) = \frac{a_i}{\text{RMS}(a)} g_i, \qquad \text{RMS}(a) = \sqrt{\frac{1}{d_{model}}\sum_{i=1}^{d_{model}} a_i^2 + \varepsilon}$$

去掉减均值这一步的好处是少一趟归约、少一次遍历，而实践上效果不比 LayerNorm 差——Llama 系列用的就是它。gain 是 `d_model` 个可学习参数，初始化为全 1（见 §3.4），所以刚开始这一层只做归一化、不额外缩放。

注意 $\varepsilon$ 的位置：它加在**根号里面、均值上面**，不是加在开方之后的分母上。有些实现是后者，数值上差别很小，但既然测试要和参考实现逐个数比对，就按作业写的来。默认值 `1e-5`。

#### 坑一：必须先 upcast 到 fp32

作业文档在这里直接给了代码骨架，要求先把输入转成 `torch.float32`，算完再转回原来的 dtype。理由是**平方那一步会溢出**。

具体一点：fp16 能表示的最大值约 65504，所以只要某个激活值的绝对值超过 256，$a_i^2$ 就直接变成 `inf`，接下来求和、开方、相除全是 NaN。bf16 的动态范围和 fp32 一样宽、不会溢出，但它只有 8 位尾数，几百上千个数累加起来精度损失很可观。两种情况都要靠升精度解决。

这是整份作业里**第一次出现"为了数值稳定而临时提高精度"这个模式**，后面还会见到：softmax 要减最大值、cross-entropy 要用 log-sum-exp 而不是先 softmax 再取对数。共同点都是——**中间量的动态范围比输入输出大得多，所以要在中间那一段额外小心。**

一个容易忽略的细节：算完一定要转回**输入的** dtype 再返回。如果直接返回 fp32，这个 tensor 会沿着残差流一路把后面所有层都拖成 fp32，混合精度训练就白做了。

#### 坑二：为什么必须加 `keepdim=True`

计算均方根的代码如下：
`rms = torch.sqrt(torch.mean(x ** 2, dim=-1, keepdim=True) + self.eps)`

如果不加 `keepdim=True`（使用默认的 `keepdim=False`），`torch.mean` 作为归约操作（Reduction），会在数学上“消耗”掉求平均的那个维度。
例如，输入张量 `x` 形状是 `[batch_size, seq_len, d_model]`（如 `[2, 10, 512]`），在 `dim=-1` 上求平均后，如果不保留维度，结果 `rms` 的形状就会变成 `[2, 10]`。最后一个维度 `512` 彻底消失。

而下一步我们要做的操作是归一化：`x / rms`。
此时 PyTorch 会尝试利用广播机制（Broadcasting），从右向左对齐两者的维度：
`x`:   `[2, 10, 512]`
`rms`:     `[2, 10]`
从最右边对齐时，`512` 和 `10` 既不相等，也没有一个是 `1`，PyTorch 就会直接抛出经典的形状不匹配报错：`RuntimeError: The size of tensor a (512) must match the size of tensor b (10) at non-singleton dimension 2`。

加上 `keepdim=True` 的意义就是**充当 1 维的占位符**。
加上之后，`rms` 算出来的形状会是 `[2, 10, 1]`。
当再次计算 `x / rms` 时：
`x`:   `[2, 10, 512]`
`rms`: `[2, 10, 1]`
最右侧维度是 `512` 和 `1`。只要其中一个是 `1`，PyTorch 的广播机制就会将其自动复制扩展（把这个 1 扩展 512 份），从而使得向量中的这 512 个特征都能顺利地除以相同的 `rms` 标量值。

所以总结下来：留着维度是为了**之后做除法时能触发广播机制**。后面写 Attention 里的各种 mask 和 softmax 操作时，这个关于张量维度的坑还会反复遇到。

### 3.8 SwiGLU 前馈网络：命名绑定与数学对齐

与传统的以 ReLU 为核心的前馈网络不同，现代大模型（如 Llama 3、Qwen 2.5 等）普遍采用带有门控机制的 SwiGLU。其核心数学计算过程如下：

$$FFN(x) = SwiGLU(x, W_1, W_2, W_3) = W_2(\text{SiLU}(W_1 x) \odot W_3 x)$$

其中，$\odot$ 表示逐元素乘法，而 SiLU 激活函数定义为：

$$\text{SiLU}(x) = x \cdot \sigma(x) = \frac{x}{1 + e^{-x}}$$



### 3.9 RoPE：用旋转编码相对位置

RoPE 的核心是将绝对位置信息转化为特征在复数平面上的旋转角度，使得 Query 和 Key 的内积能自然体现它们的相对位置。

**核心数学公式：**

对于位置 $i$ 上的向量，把相邻两维看成一对 2D 向量，旋转一个正比于 $i$ 的角度：

$$R^i_k = \begin{pmatrix} \cos\theta_{i,k} & -\sin\theta_{i,k} \\ \sin\theta_{i,k} & \cos\theta_{i,k}\end{pmatrix}, \qquad \theta_{i,k} = \frac{i}{\Theta^{(2k-2)/d}}$$

（注：$i$ 是序列中的位置索引，$k$ 是维度对的索引，$\Theta$ 通常默认 10000）。

利用旋转矩阵的角度可加性，内积结果只与两者的相对距离相关，优雅地消去了绝对位置：
$$\langle R_i q,\ R_j k \rangle = q^\top R_{j-i}\, k$$

1. **打表预计算与 Buffer 挂载陷阱**：
   千万不要构造完整的 $d \times d$ 稀疏矩阵。在 `__init__` 中算出形状为 `(max_seq_len, d_k/2)` 的 `cos` 和 `sin` 角度表即可。
   算完后，必须用 `self.register_buffer("cos_cached", cos_tensor, persistent=False)` 挂载它。这背后的底层逻辑极其致命：

   **第一层：为什么要用 register_buffer？**
   在 PyTorch 里，如果在 `__init__` 中只写 `self.cos_cached = cos_tensor`，它其实就是一个普通的 Python 属性。当你以后调用 `model.to('cuda')` 把模型推到显卡上去训练时，这个普通的 `cos_tensor` 会被遗留在 CPU 上。等到前向传播运算时，就会爆出著名的 `Expected all tensors to be on the same device` 错误。
   为了让 PyTorch 知道“这个变量属于模型，请带着它一起搬家”，必须用 `self.register_buffer`。

   **第二层：那为什么一定要加 persistent=False？**
   凡是被 `register_buffer` 注册的变量，PyTorch 默认会认为它是模型非常宝贵的“状态财产”（比如 BatchNorm 里的均值和方差），所以在你保存模型（`model.state_dict()`）的时候，它会被写进最终的权重文件里。
   但是，RoPE 里的 `cos` 和 `sin` 矩阵根本不需要被保存！因为它们只是一堆死板的数学常数，不参与梯度更新，任何时候都能重新算出来。为了节省磁盘空间，业界标准的做法都不会把这两个表保存在官方的模型快照里。

   **灾难是怎么发生的？**
   当你运行测试脚本时，脚本会掏出一套标准的预训练权重，强行塞进你写的模型里：`model.load_state_dict(reference_weights, strict=True)`。
   因为是 `strict=True`，PyTorch 会进行逐词核对：
   - 你的模型举手：“报告！我这儿有一个叫 `cos_cached` 的变量，请把它的权重发给我！”
   - 标准权重：“什么 `cos_cached`？我的账本里根本没有这个东西啊！”
   - 结果：对账失败，PyTorch 抛出 `RuntimeError: Missing key(s) in state_dict: "cos_cached", "sin_cached"`，程序崩溃。

   （注意报的是 **Missing** 而不是 Unexpected。这两个名字方向相反，很容易记反：**Missing 是"你的模型要、但给的字典里没有"，Unexpected 是"字典里有、但你的模型不认识"**。这里是前者。）

   **总结：**
   加了 `persistent=False`，就是给这个 Buffer 贴上了一张“临时通行证”：“请 PyTorch 帮我管好它在 GPU 上的显存，但盘点资产（导出/导入 state_dict）的时候，请当作它不存在。” 这样既享受了设备自动同步的便利，又完美避开了对暗号失败的崩溃。
2. **相邻配对**：本作业的数学定义要求对特征向量进行**相邻配对** `(0,1), (2,3), (4,5)...`，切忌使用某些开源模型里的前半段+后半段对半配对，否则数值对不上。
3. **查表旋转与 Flip 大法**：
   在真正做 2D 旋转时，最极简且被主流开源大模型采用的写法是“翻转取反大法”。
   利用向量分解的几何意义：点旋转 $\theta$ 相当于**原向量缩放**加上它的**正交向量投影**。
   我们通过 `x_reshaped.flip(-1) * [-1, 1]` 直接构造出原向量 $[x, y]$ 的正交向量 $[-y, x]$。
   然后即可一气呵成地进行整体运算：`x_reshaped * cos + orthogonal_x * sin`。
   这种写法免去了繁琐的显式拆分切片，省去了 `torch.stack`，在工业界源码中极为常见。最后只需用 `rearrange(..., '... n c -> ... (n c)')` 将二维坐标系重新拍平即可。
4. **下标约定：讲义和代码用了两套起点**

   这是我在这道题上耗掉时间最多的地方，而且它不是数学问题，纯粹是记号问题。

   讲义的 $k$ **从 1 开始**（$k \in \{1,\dots,d/2\}$），所以指数写作 $(2k-2)/d$。但代码里生成这串指数最自然的写法是从 0 开始数，指数就变成了 $2k/d$。

   **两者数值完全一样**：讲义 $k=1$ 时指数为 0，代码第一个元素也是 0；讲义 $k=2$ 时是 $2/d$，代码第二个也是 $2/d$。令 $k' = k-1$ 即可互相转换。

   但如果注释里不写清楚用的是哪一套，过两天回头看就会怀疑自己写错了公式。**解决办法不是在每行注释里重复解释，而是在类的开头声明一次**：

   ```
   下标约定（全类统一，均 0-indexed）：
     i   位置          0 .. max_seq_len-1
     k   维度对编号     0 .. d_k/2-1     讲义用 1..d_k/2，讲义的 (2k-2) 即此处的 2k
     c   对内分量       0 或 1           一对 (x, y) 的两个坐标

   角度定义：theta[i, k] = i / Theta ** (2k / d_k)
   ```

   声明之后，逐行注释就能直接写成 `inv_freq[k] = ...`、`freqs[i, k] = ...` 这种带下标的形式。**把二维表的两个轴写进注释，比写一个孤零零的标量公式清楚得多**——读者一眼就知道哪个轴是位置、哪个轴是频率。

   还有一条容易忽略的：**einops 的轴名必须和这套术语一致**。如果同一个长度为 $d_k/2$ 的轴，在查表那两行叫 `half_k`、在拆分那行叫 `n`，einops 的自文档化价值就打了对折。顺带一个命名建议：那个长度为 2 的轴与其叫 `c`，不如叫 `xy`——它字面上就是被旋转的二维向量的两个坐标，`"... (k xy) -> ... k xy"` 几乎不需要注释。

   这件事让我修正了对 §3.2 那句 "documentation is implementation" 的理解：**它不是"用了 einops 就自动获得"的，而是要把轴名当作一套术语来维护**——统一起点、统一命名、在一个地方声明。工具让这件事变得可能，纪律还得自己上。

5. **精度：哪一步必须 fp32，哪一步可以降**

   这里必须把两件事分开看，它们的要求完全不同：

   | | 精度要求 | 为什么 |
   |---|---|---|
   | **算角度表**（`arange` × `inv_freq`，取 cos/sin） | **必须 fp32** | 见下 |
   | **应用旋转**（乘 cos、乘 sin、加减） | bf16 完全没问题 | 就是几次乘加，动态范围很小 |

   角度表必须 fp32 的理由比"防止溢出"更硬：**bf16 只有 8 位有效精度，能精确表示的整数上限是 256。** 也就是说位置索引超过 256 之后就开始丢值，位置 1000 和 1001 可能变成同一个数，位置编码直接废掉。（fp16 好一点，上限 2048，但对 32K 上下文照样不够。）

   这也是 HuggingFace 的实现把 `inv_freq` 固定注册成 fp32、并在这段专门禁用 autocast 的原因。

   而旋转那一步在 bf16 下做乘加毫无问题。所以正确的做法是：**表用 fp32 存，用的时候把 cos/sin 降到输入的 dtype，全程不要把 `x` 升上去**——方向反了，内存带宽的开销差一倍。

   还有一个连带的坑：如果模块里除了 cos/sin 还有别的常量 buffer（比如 flip 写法需要的符号向量），**三者的 dtype 处理必须一致**。我一开始让符号向量跟着构造参数走、又忘了在 forward 里转换，结果 bf16 输入会被静默提升成 fp32 返回——测试跑的是 fp32，两边碰巧一致，照样绿。又一次「绿灯 ≠ 证明」。

   **复数写法为什么被锁死在 fp32**：PyTorch 的复数 dtype 只有 `complex32`（fp16 分量，beta，很多算子未实现）、`complex64`、`complex128`——**没有任何一个以 bf16 为分量**。`view_as_complex` 遇到 bf16 直接抛错，而且它还要求最后一维正好是 2 且内存连续，前面做过 `rearrange` 的话可能要额外拷贝一次。这是硬约束，不是"支持得不够好"的程度问题，也是复数写法在工业界不被采用的第一原因。

   **fp8 是另一回事**：现在的 fp8 训练方案里，fp8 只用在**矩阵乘法的输入**上（线性层、$QK^\top$、$\text{attn}\cdot V$），RMSNorm、RoPE、softmax、残差相加全都跑在 bf16 或 fp32。原因是逐元素运算是 memory-bound，瓶颈在带宽不在算力，用 fp8 没有好处，而且它们恰恰是数值最敏感的地方。

   顺带纠正一个容易望文生义的说法：**RoPE 用不到 Tensor Core**。它是纯逐元素运算，Tensor Core 是矩阵乘法单元，任何 dtype 下都轮不到它。升精度的真实代价只有一条——内存带宽翻倍。

   最后：**这份作业里怎么写都能跑过**，因为测试是 fp32 的。上面这些是到真机上训练才会咬人的东西。这和 §2.7 教训 1「测量规模决定结论」是同一个主题——**同一个模块，玩具规模和生产规模的最优解不一样**。


### 3.10 Softmax：为什么要先减最大值

softmax 把一串分数变成一个概率分布：

$$\text{softmax}(v)_i = \frac{\exp(v_i)}{\sum_{j} \exp(v_j)}$$

直接按这个式子写会炸。问题出在 $\exp$ 上——**它的输出动态范围远大于输入**，而浮点数的上限是有限的：

| dtype | 能表示的最大值 | $\exp(x)$ 溢出的阈值 |
|---|---|---|
| fp32 / bf16 | ≈ $3.4 \times 10^{38}$ | $x > 88.7$ |
| fp16 | 65504 | $x > 11.1$ |

注意力分数是 $q \cdot k / \sqrt{d_k}$，正常训练时大多在个位数到几十，但**训练早期或初始化不好时冲到 88 以上完全可能**；fp16 下 11 这个阈值更是随手就能突破。一旦 $\exp$ 溢出成 `inf`，分子分母都是 `inf`，相除得到 `NaN`，整个前向就毁了。

**解法：先把每个元素减去这一维的最大值。**

这么做不改变结果，因为 softmax 有**平移不变性**——给所有输入同时加一个常数 $c$，分子分母会同时乘上 $e^c$，约掉了：

$$\frac{\exp(v_i - c)}{\sum_j \exp(v_j - c)} = \frac{e^{-c}\exp(v_i)}{e^{-c}\sum_j \exp(v_j)} = \text{softmax}(v)_i$$

取 $c = \max_j v_j$ 之后有两个好处：

- **最大项恰好变成 $\exp(0) = 1$**，其余都 $\le 1$，**上溢彻底不可能发生**。
- **分母至少是 1**（因为最大项贡献了 1），不会出现"分母下溢成 0"导致的除零。

至于下溢——那些远小于最大值的项 $\exp(\text{很负的数})$ 会变成 0。**这是安全的**：它们本来的概率就接近 0，舍入成 0 不影响结果。

#### 实现上的两个点

**减的必须是"做 softmax 的那一维"的最大值，而且要 `keepdim=True`。** 这和 RMSNorm 那个坑（§3.7）是同一件事：归约会消掉一维，不保留就没法广播回去。**同一个模式在这一章出现了第二次**，后面 attention 的 mask 还会再遇到。

**警惕一整行全是 $-\infty$ 的情况。** 如果某一行的所有位置都被 mask 掉了，那这一行的最大值是 $-\infty$，$-\infty - (-\infty) = \text{NaN}$，softmax 直接产出一整行 NaN。

因果掩码不会触发这个（第 $i$ 行至少能看到自己），但**带 padding 的批处理会**——一个全是 padding 的位置就是这样。这份作业里不会碰到，但它是真实训练里非常经典的一个 NaN 来源，值得先知道。

#### 这是一个反复出现的模式

到这里，"为了数值稳定而在中间步骤额外小心"已经是第三次出现了：

| 位置 | 危险的中间量 | 手段 |
|---|---|---|
| RMSNorm（§3.7） | $a_i^2$ 会溢出低精度 | 先升到 fp32 再算 |
| **softmax（这里）** | $\exp(v_i)$ 会溢出 | 先减去最大值 |
| cross-entropy（§4.1） | 先 softmax 再取 log，两次误差叠加 | 合成一个 log-sum-exp 一步算完 |

共同点是：**输入和输出都很温和，只有中间量的动态范围爆炸。** 所以看到 $\exp$、平方、除法这类会放大动态范围的运算时，就该条件反射地问一句"中间量会不会越界"。

顺带一提，`torch.softmax` 内部就是这么做的——自己实现一遍的价值在于知道它为什么这么做。

### 3.11 Scaled Dot-Product Attention

$$\text{Attention}(Q,K,V)=\text{softmax}\!\left(\frac{QK^\top}{\sqrt{d_k}}+\text{Mask}\right)V$$

形状：`q: ... queries d_k`、`k: ... keys d_k`、`v: ... keys d_v` → 输出 `... queries d_v`。
用 `einsum` 而不是 `@`：前面的 `...` 里可能有 batch、也可能有 heads（§3.12 会多塞一维进来），`einsum` 按名字对齐，不用关心到底有几个前导维度。

#### 三个概念问题

**① softmax 沿哪个维度？——`dim=-1`，也就是 keys。**

打分矩阵是 `[..., queries, keys]`：**行 = 一个 query 对所有 key 的打分**。
"注意力"的本质是分配权重：固定一个 query，它分给所有候选 key 的权重之和必须是 1 ⇒ 沿**列**（最后一维）归一化。
沿 queries 归一化没有意义——那会变成"所有 query 对同一个 key 的竞争"，不是 attention 的语义。

**② mask 为什么必须是 $-\infty$，不能相乘。**

直觉上"把不该看的位置乘 0"是错的：

$$\text{softmax 之前置 } 0 \;\Longrightarrow\; e^{0}=1$$

被乘成 0 的位置在 softmax 里得到的是 $e^0=1$，**不但没被屏蔽，反而拿到了不小的权重**——比那些真实得分为负的位置还高。要让 softmax 输出 0，必须在**进 softmax 之前**把它变成 $-\infty$（$e^{-\infty}=0$），用 `masked_fill`。

> ⚠️ mask 的布尔约定要**去测试里核对**：`True` 是"保留"还是"屏蔽"，两种约定都有人用，弄反了整个注意力就翻过来了。这属于"契约不在类型里、只在文档/测试里"的一类坑。

**③ RoPE 不在这一层。**

这个函数是**纯计算引擎**：给我 Q、K、V 和 mask，我按公式算。至于 Q、K 有没有加绝对位置编码、有没有做 RoPE 旋转、有没有 ALiBi 偏置——它一概不问。

RoPE（§3.9）是在 **MultiHeadAttention 内部、投影和切头之后、调用本函数之前**，**只对 Q 和 K** 施加的。保持这层的纯粹性，换位置编码方案时这个函数一行都不用改。

#### 踩过的四个坑

| # | 写法 | 问题 |
|---|---|---|
| 1 | `/ Tensor.sqrt(v.dim[-1])` | `.dim` 是**方法**、返回维度**个数**不是大小，要 `.shape[-1]`；`Tensor.sqrt` 吃张量不吃 int，标量用 `math.sqrt`。另外公式里是 $\sqrt{d_k}$，该取 `q.shape[-1]`——虽然通常 $d_k=d_v$，但取 v 是**恰好对而不是真的对** |
| 2 | `maskQK = mask * QK` | 见上面 ②，$e^0=1$ |
| 3 | 没判断 `mask is None` | 推理时不传 mask，`None * QK` 直接 `TypeError` |
| 4 | 算了 `maskQK` 却把 `QK` 传进 softmax | **算了没用**。这类 bug 最阴——不报错，结果只是"看起来差不多"，得靠测试或对拍才发现 |

第 1 和第 4 条有个共同教训：**"恰好对"和"真的对"要分开**。`v.shape[-1]` 在 $d_k=d_v$ 时给出正确的数，但理由是错的；哪天用了 $d_k \neq d_v$ 的变体（比如 MQA/GQA 里 V 的维度不同）就会静默出错。

#### 这一层的接口设计值得单独记

`scaled_dot_product_attention` 的形状签名全用 `...` 泛化前导维度，带来一个后面直接兑现的好处：**MultiHeadAttention 把 heads 切出来当成一个额外的前导维度之后，可以原样调用它，一行都不用改**——`heads` 被自动当作 batch 处理。

这是"**让底层组件对上层的组织方式无知**"的一个具体例子，和 §2 里 `COMPILED_PAT` 能同时被训练和 encode 复用是同一种性质：**接口只承诺自己那一层的语义，不假设调用方怎么组织数据。**

### 3.12 Multi-Head Self-Attention：公式与形状

#### 为什么要从单头变成多头

**一个 head 只能表达一种关注方式**，因为它的输出是 V 的加权平均、而 softmax 强制权重和为 1 ⇒ **注意力是零和的**，多看一个地方必然少看另一个。

但一个 token 常常需要**同时**获取性质完全不同的信息。例如

> The keys that I lost **were** on the table.

`were` 既需要 `keys`（主谓一致，决定用 were 不是 was），又需要 `table`（语义）。两者毫无关系，却共用同一份 1.0 预算：

| 权重分配 | 输出 | |
|---|---|---|
| 全给位置1 | `[1.0, 0, 0, 0]` | 语义丢了 |
| 全给位置3 | `[0, 0, 1.0, 0]` | 语法丢了 |
| 各 0.5 | `[0.5, 0, 0.5, 0]` | **两个都只剩一半，都糊了** |

这就是 Vaswani 原文那句 **"With a single attention head, averaging inhibits this."**

**修法：并排做 $h$ 次，每次有自己独立的 1.0 预算**，最后 concat ⇒ 两种信息都是满强度。

**但朴素做法要 $h$ 倍参数和计算**，于是让每个头只在 $d_k=d_{\text{model}}/h$ 维里工作，$h \times d_{\text{model}}/h = d_{\text{model}}$，总量回到原来。

> **逻辑顺序别搞反**：想要的是「$h$ 套互不竞争的注意力分布」（表达力）；**切分只是把成本压回单头水平的手段**，不是目的。所以 `rearrange('... seq (h d) -> ... h seq d')` 做的是「把 $d_{\text{model}}$ 个提取器分成 $h$ 组」，不是「把 token 拆开」。

#### 三处常见的误说法

| 常见说法 | 实际 |
|---|---|
| "把词向量切成 8 份分给各头" | **没有切词向量**。每个头都完整看到全部 $d_{\text{model}}$ 维，切的是 $W_Q$ 的**输出维度**（行分组）。切输入会让每个头对 $1-1/h$ 的特征全瞎（实测验证过） |
| "参数量和计算量完全一样" | 参数量和**矩阵乘** FLOPs 一样；但**打分矩阵大 $h$ 倍**（$d_{\text{model}}$=512/seq=1024 时实测 104 万 vs 838 万个元素）⇒ softmax 计算量和激活显存都是 $h$ 倍。**矩阵乘免费，softmax 和中间张量不免费** |
| "Head 1 管语法、Head 2 管语义" | 头**没有被指派角色**，大部分是多义的（polysemantic）。可解释性研究确实找到过功能明确的头（induction head、previous-token head），但那是**训练涌现，不是设计**。准确说法：**结构允许分工，训练可能产生分工** |

> ⚠️ **别用 roofline 解释"为什么多头"**。参数量和矩阵乘 FLOPs 完全相同、而多头在打分矩阵上更吃内存——一个在 compute 和 memory 上都不更优的设计，不可能是被它们驱动的。
> **判据**：先比两个方案的 FLOPs 和访存量。差很多 → 用 roofline 解释（**MQA/GQA** 是纯 KV-cache 带宽驱动、**FlashAttention** 的前提就是 attention 是 memory-bound）；几乎不差 → 它买的一定是表达力或优化性质（多头、残差、norm 的位置）。

#### 那 compute / memory 的考量在哪？——在 MQA / GQA

推理（自回归解码）时每生成一个 token 都要把之前所有的 K、V 从显存读一遍，这是**彻底的 memory-bound**：GPU 算得快，卡在等数据。缓存大小

$$\text{KV cache}=2\cdot L\cdot \text{seq}\cdot (h_{kv}\cdot d_k)\cdot B$$

实测（$d_{\text{model}}$=4096、seq=8192、32 层、fp16）：

| 方案 | Q 头 | KV 头 | KV cache |
|---|---|---|---|
| 单头（$d_k$=4096） | 1 | 1 | **4.29 GB** |
| MHA 32 头 | 32 | 32 | **4.29 GB** ← 和单头**完全一样** |
| GQA 32/8（Llama 3） | 32 | 8 | 1.07 GB |
| MQA 32/1 | 32 | 1 | 0.13 GB |

⚠️ **多头不增加 KV cache 一个字节**——标准多头里 $h\cdot d_k=d_{\text{model}}$，头数在式子里被消掉了。
**真正砍它的是 MQA/GQA**：让 $h_{kv}\cdot d_k < d_{\text{model}}$，即 **K/V 的总宽度比 $d_{\text{model}}$ 还窄**。这是对「单头和多头共同基线」的偏离，不是在修多头的毛病。
⇒ 又一次印证上面那条判据：**两个方案的某项指标相同时，别拿这项指标去解释它们的差异。**

另一处常见误说法：「多头把大矩阵切碎，对 GPU 不友好」。**Q/K/V 投影仍是三次完整的 $d_{\text{model}}\times d_{\text{model}}$ 大 GEMM**（handout 要求 "a total of three matrix multiplies"），切头是之后的 reshape、零计算。被拆成批量小矩阵乘的只有 $QK^\top$ 和 $AV$，而 `h` 在那里提供的是**并行度**不是碎片。$d_k$ 守在 64/128 的真实理由是 **tile 效率**（$d_k$ 太小时单个 tile 打不满 tensor core），不是"避免切碎"。

#### handout 的三条式子（§3.4.5）

$$\text{MultiHead}(Q,K,V)=\text{Concat}(\text{head}_1,\dots,\text{head}_h)$$
$$\text{head}_i=\text{Attention}(Q_i,K_i,V_i)$$
$$\text{MultiHeadSelfAttention}(x)=W_O\,\text{MultiHead}(W_Q x,\;W_K x,\;W_V x)$$

其中 $Q_i,K_i,V_i$ 是把 $Q,K,V$ 沿 embedding 维切出的第 $i$ 片，$\text{Attention}$ 就是 §3.11 那个引擎。

| 参数 | 形状 | 说明 |
|---|---|---|
| $W_Q,\;W_K$ | $\mathbb{R}^{h d_k \times d_{\text{model}}}$ | |
| $W_V$ | $\mathbb{R}^{h d_v \times d_{\text{model}}}$ | |
| $W_O$ | $\mathbb{R}^{d_{\text{model}} \times h d_v}$ | |

作业里取 $d_k=d_v=\dfrac{d_{\text{model}}}{h}$，所以 $h d_k = h d_v = d_{\text{model}}$，**四个投影矩阵都是方阵** $d_{\text{model}}\times d_{\text{model}}$。

> 注意 $d_k=d_v=d_{\text{model}}/h$ 是**这个作业的取值**，不是定义。MQA / GQA 这类变体里 K、V 的头数比 Q 少，$h d_v \neq d_{\text{model}}$，那时上面那张形状表才显出必要性。这也是 §3.11 坑 1 说的"恰好对 vs 真的对"。

#### 关键理解一：为什么只需要三次矩阵乘，而不是 $3h$ 次

式 (13) 字面读是"每个头各做一次小投影"，但 $W_Q \in \mathbb{R}^{h d_k \times d_{\text{model}}}$ 本来就是**一整块**。把它的**输出维度**切成 $h$ 段、每段 $d_k$，得到的正是各头的投影矩阵。所以

$$\underbrace{x W_Q^\top}_{\text{一次大 GEMM}} \;\to\; [\dots,\text{seq},\,h d_k] \;\xrightarrow{\text{reshape}}\; [\dots,h,\text{seq},d_k]$$

和"做 $h$ 次小投影再堆起来"**在数学上完全相同**，但一次大矩阵乘远快于 $h$ 次小的。handout 明确要求"a total of three matrix multiplies"（Q、K、V 各一次），脚注还留了个 stretch goal：三个拼成一个更大的矩阵，只做一次。

**切头是纯粹的 reshape，不是计算。** 参数量、FLOPs 都和单头一样——多头改变的只是"这些维度如何分组做 softmax"。

#### 关键理解二：heads 维度必须放在 seq 前面

$$[\dots,\ \text{seq},\ (h\ d_k)] \;\longrightarrow\; [\dots,\ h,\ \text{seq},\ d_k]$$

因为 §3.11 的引擎把**最后两维**当作 `queries × d_k` 来算，前面的 `...` 一律视为 batch。heads 放到 `...` 里，就自动获得"每个头独立做 attention"的语义——**引擎一行都不用改**。

放成 `[..., seq, h, d_k]` 则会让引擎把 `h` 当成 queries、`d_k` 当成特征，算出来的东西毫无意义且**不报错**。

#### 关键理解三：Concat + $W_O$ ≡ 各头结果分别投影后求和

$\text{Concat}$ 得到 $[\dots,\text{seq},h d_v]$，再乘 $W_O \in \mathbb{R}^{d_{\text{model}}\times h d_v}$。把 $W_O$ 沿**输入维度**切成 $h$ 段 $W_O^{(i)}$，则

$$W_O\,\text{Concat}(\text{head}_1,\dots,\text{head}_h)=\sum_{i=1}^{h} W_O^{(i)}\,\text{head}_i$$

⇒ 各头的信息是在 $W_O$ 这一步**相加融合**的，不是简单并排。这也解释了为什么 $W_O$ 不能省——没有它，各头的输出就只是拼在一起、从未交互过。

#### 完整形状流

| 步 | 操作 | 形状 |
|---|---|---|
| 0 | 输入 $x$ | `... seq d_model` |
| 1 | 三次投影 | 各 `... seq d_model`（即 `... seq (h d_k)`） |
| 2 | 切头 `... seq (h d) -> ... h seq d` | `... h seq d_k` |
| 3 | **RoPE 只作用于 Q、K** | 不变 |
| 4 | 因果 mask + §3.11 引擎 | `... h seq d_v` |
| 5 | 合头 `... h seq d -> ... seq (h d)` | `... seq d_model` |
| 6 | $W_O$ | `... seq d_model` |

#### 两条 handout 明写的约束

**① 因果 mask**：位置 $i$ 只能看 $j \le i$。用 `torch.triu` 或广播的下标比较造出来，然后**直接交给 §3.11 的引擎**——它已经支持 mask，不要在这里另写一套屏蔽逻辑。
mask 形状是 `seq × seq`，要能广播到 `... h seq seq`（heads 之间共用同一个 mask）。

**② RoPE 只给 Q、K，不给 V**，而且 **head 维度当作 batch 处理**——每个头施加的是**完全相同**的旋转。
理由：RoPE 编码的是**位置**，位置是 token 的属性，与"第几个头"无关。V 不参与打分（打分只由 $QK^\top$ 决定），所以旋转 V 没有意义。

> 为什么"旋转 Q 和 K"能编码**相对**位置：RoPE 让 $\langle R_m q,\ R_n k\rangle$ 只依赖 $m-n$（§3.9）。而 attention 的打分正是 $q\cdot k$ ⇒ 位置信息以相对形式进入打分，V 完全不受影响。

#### 因果 mask 建在哪：`__init__` 还是 forward

三种做法在生产里都跑过，所以问题不是"哪个对"，而是"什么决定了选哪个"：

| 做法 | 代表 | 建的次数 |
|---|---|---|
| `__init__` 预建 buffer，forward 切片 | GPT-2（`register_buffer("bias", tril(...))`，用时 `[:,:,:T,:T]`） | 一次 |
| forward 现造 | Llama 参考实现，每次 `full + triu` | 每步每层 |
| **根本不物化** | FlashAttention / `F.scaled_dot_product_attention(is_causal=True)` | 从不 |

**判据只有一条：mask 依赖形状，还是依赖数据？**

- 纯因果 mask 只依赖 `seq_len` 一个整数 ⇒ 完全静态 ⇒ 可以预建
- padding / sliding window / packed sequence 依赖这一批数据 ⇒ 只能 runtime

而真实模型几乎总要把两者相与，所以 Llama 走 runtime **不是因为预建不好，是因为它的 mask 本来就不是纯静态的**。

**预建的代价在层数上**（bool，$O(L^2)$；对比 RoPE 表的 $O(L\,d_k)$）：

| $L$ | 单个 mask | ×32 层 | RoPE 表（$d_k{=}128$） |
|---|---|---|---|
| 256 | 64 KB | 2 MB | 32 KB |
| 8192 | 64 MiB | **2 GiB** | 4 MB |

⇒ 一个线性、一个平方。**要预建也该在模型级共享，而不是每层各存一份。**

两条延伸：

- **GPT-2 的 `attn.bias` 最初忘了 `persistent=False`**，那个下三角矩阵被写进了 checkpoint，HF 至今要在 `_keys_to_ignore_on_load_missing` 里过滤。呼应 §3.3 坑 3——**由形状唯一决定的常量不该进 state_dict**。
- **显式 mask 张量和 FlashAttention 互斥。** FlashAttention 的全部意义是永不物化 $S\times S$ 的打分矩阵；你递给它一个 $S\times S$ 的 mask，就把 $O(S^2)$ 显存搬了回来。所以现代接口把因果性表达成一个 **flag**，让 kernel 在分块循环里用下标比较跳过。

**本作业的选择**：§3.11 的引擎只接受物化的张量，第三条路关掉了。而 forward 里 `x.shape[-2]` 唾手可得 ⇒ **不需要从 `__init__` 传 `max_seq_len` 进来**——非 RoPE 那条适配器恰好也不传它。

> 教训：差点把一个 forward 里本来就有的信息，改成从构造函数传入。**信息在哪一层可得，就在哪一层取**；往上提会凭空制造一个"那条路径没有这个参数"的问题。

#### mask 的两种约定：布尔 vs 加性浮点

PyTorch 的 SDPA 两种都支持，**而它们的"保留"值正好相反**：

| | 布尔 | 加性浮点 |
|---|---|---|
| 写法 | `masked_fill(~mask, -inf)` | `scores + mask` |
| **保留** | `True` | **`0.0`** |
| 代表 | nanoGPT、PyTorch 默认 | HF Transformers 传统实现 |

**最阴的坑**：`mask == False` 对浮点张量的含义是 `mask == 0.0`。所以一个标准加性 mask 传进来，会被**完全反向**解读——该保留的全屏蔽、该屏蔽的全放行，**且不报错**。用 `~mask` 代替 `mask == False`，float 会直接抛异常。

另外三条：

- **HF 用 `torch.finfo(dtype).min` 而不是 `-inf`**（`-inf` 参与算术易出 NaN）。但它自己有坑：因果 mask + padding mask 都用 `finfo.min`，**相加会溢出成 `-inf`**。
- **mask 必须加在 `/√d_k` 之后**，否则连 mask 值一起被除。用 `finfo.min` 时除完仍极负，所以"看起来对"——又一个"恰好对"。
- **整行全屏蔽 → NaN**：`x_max = -inf`，`x - x_max = -inf - (-inf) = nan`。纯因果不会触发（对角线保底），**一旦叠加 padding mask 就会**。

**布尔是加性的特例**（bias 只取 0 或 $-\infty$）。加性能表达布尔表达不了的东西——**ALiBi** 的距离斜坡、**T5 的相对位置偏置**，这些是"部分抑制"而非"完全屏蔽"。业界的分化由此而来：只做因果就用布尔（或干脆不物化），要注入位置偏置就用加性。

#### 一次静态扫描：六个静默失败

MHA 写完后做的一次通读，抓到六个**测试不一定能拦住**的问题。列在这里不是为了记结论，是为了记**它们的共同结构**。

| # | 症状 | 机制 | 为什么哑 |
|---|---|---|---|
| 1 | RoPE 完全没生效 | 调用点 `mha(x, token_positions)` 把位置传进了 `mask` 形参 | 形参默认值让漏传合法；Int 张量进 `mask == False` 变成"屏蔽 key 0 那一列"，形状全合法 |
| 2 | **因果性泄漏** | `if mask is None: mask = causal` —— 一传外部 mask 因果性就没了 | 表现是 **loss 掉得异常漂亮**，会去怀疑 lr / 数据 / 初始化 |
| 3 | RoPE 静默跳过 | `if rope is not None and token_positions is not None` | 触发点在**下一道题**：`run_transformer_block` 的签名里没有 `token_positions`，但它要求用 RoPE |
| 4 | RoPE 旋转错位 | positions 无 head 维，右对齐时 batch 撞上 $h$ | 测试传 `[1, seq]` 才侥幸对；conftest 里 `batch = heads = 4`，传 `[batch, seq]` 会**静默算错而不是报错** |
| 5 | `*` 当逻辑与用 | bool 上结果正确，但对非 bool 静默做算术 | `&` 会直接抛类型错误 |
| 6 | RMSNorm gain 未初始化 | `torch.empty` 后没有 `ones_` | 测试一律 `load_state_dict` 覆盖它 ⇒ 全绿；从零训练第一步 NaN |

**六个里有五个的共同结构：降级路径不出声。** "参数没传就用默认"、"没有 mask 就用因果"、"没有位置就跳过 RoPE"——每一条单独看都像是贴心的容错，合起来就是一张让错误安静穿过的网。

四条可直接复用的做法：

1. **把隐含契约变成运行时断言。** 注解写了 `Bool` 但 `mask == False` 接受任何 dtype，类型系统拦不住（jaxtyping 默认不做运行时检查）。**一条 dtype 断言能让 #1 在第一次调用就崩，而不是变成一个跑得通的错数。**
2. **用运算符的类型约束代替记忆。** `&` 不接受 float、`~` 不接受 float ⇒ 选它们等于免费拿到 #5 和加性 mask 反转的防护。这比"记住要检查 dtype"可靠。
3. **缺省值应该是"补全"，不是"跳过"。** #3 的正解是位置缺省时按 `arange(seq_len)` 生成——但要知道**这只在一次喂完整序列时成立**；增量解码（KV cache）时第一个 token 的位置是 `past_len` 而不是 0，HF 就是从 `past_key_values_length` 算的。**默认值是假设，不是恒等式。**
4. **约束写在制造它的那一层。** #4 的断言该放在 MHA 而不是 RoPE：`[batch, seq]` 的 positions 对 RoPE 本身完全安全（`run_rope` 直接调用时四维对四维），**是 MHA 塞进 head 维之后才产生的风险**。写进 RoPE 会平白削弱一个更通用的组件。

最后一条对照，说明为什么值得给 mask 和 positions 补断言：

> 同一次改名（`o_proj → output_proj`、`scale → weight`），漏改适配器会让 `load_state_dict(strict=True)` **立刻抛异常并列出 missing / unexpected 的 key**；而上面六个是"跑得通但算错"。**同样是不匹配，一个有 strict 检查、一个没有，调试成本差两个数量级。**

### 3.13 Transformer Block 与完整 LM

#### 两条式子，和一个形状看不出来的错

handout 只给了第一个子层（式 15），第二个完全对称：

$$y = x + \text{MHA}(\text{RMSNorm}(x)) \qquad z = y + \text{FFN}(\text{RMSNorm}(y))$$

**`+` 号左边是原始的 $x$，不是 $\text{RMSNorm}(x)$。** 这是 pre-norm 最常见的实现错误，两种写法**形状完全一样、不报错**：

```
x + attn(ln1(x))          ✓
ln1(x) + attn(ln1(x))     ✗
```

"pre-norm" 的含义是 **norm 在分支内部，残差通路上什么都没有**。那条从第一层直通最后一层的加法链——**残差流（residual stream）**——全程是裸的。

#### 为什么 pre-norm 必须补一个 `ln_final`

handout 只写了要求（"additionally **requires** ... layer normalization after the final Transformer block"），没写理由。理由就是上一段：

- **pre-norm**：$x_{l+1} = x_l + f(\text{norm}(x_l))$ ⇒ 残差流**从未被归一化**，$L$ 层不断往上加，尺度随深度增长 ⇒ `lm_head` 会看到一个尺度取决于层数的输入 ⇒ **必须在出口补一次归一化**
- **post-norm**：$x_{l+1} = \text{norm}(x_l + f(x_l))$ ⇒ 每层出口都被重新缩放 ⇒ 出口天然是归一化的，不需要补

同一个性质还解释了另外两件事：pre-norm **不需要 learning-rate warmup**、能堆到几十上百层——因为从 loss 到任意一层的梯度通路上**没有 norm**，只有恒等加法。§3.4 里"pre-norm 对初始化异常鲁棒"是同一件事的第三种说法。

#### 输出必须是 logits，不是概率

Figure 1 里画了 softmax，但那画的是**模型**；这个 `nn.Module` 的返回值边界**故意划在 softmax 之前**。handout 文字说了三次 unnormalized / logits。

三个理由，第一个有具体数字：

**① `log(softmax(x))` 和 `log_softmax(x)` 数学相同、数值差很远。**
交出 logits ⇒ cross-entropy 走 $z_i-\max-\log\sum_j e^{z_j-\max}$，**极小的概率从未被物化**。交出概率 ⇒ 只能 `log(p)`，而 $p$ 已被 `exp` 压过一轮。

> fp16 的最小正规数是 $2^{-14}=6.1\times10^{-5}$。**GPT-2 词表 50257，均匀分布下每个 token 是 $2.0\times10^{-5}$——已经落进 subnormal 区。** 训练初期模型就接近均匀，这不是极端情况。再低（$<6\times10^{-8}$）直接归零，$\log 0=-\infty$，梯度全 NaN。

**② 双重 softmax 是一个会静默训练的错误。** 若模型返回概率而下游用 `F.cross_entropy`（内部自带 `log_softmax`），得到 $\text{softmax}(\text{softmax}(z))$——不报错、不 NaN、loss 还会降，只是降得很慢。

**③ 采样需要 logits。** 温度采样是 $\text{softmax}(z/T)$。从概率反推数学上可行（$p^{1/T}$ 再归一化即得），但**数值上已经损失**：下溢成 0 的 token 无论 $T$ 多大都回不来。

佐证：HF 的 `...ForCausalLM` 返回的字段就叫 `logits`；PyTorch 的 `nn.CrossEntropyLoss` 文档第一句是 "between input **logits** and target"，**它压根没有接受概率的版本**。

> 附带一条：§3.10 实现的 `softmax` 在这一层**用不上**，它的用处在生成时的采样。**"实现了一个组件"不等于"这一层要用它"。**

#### 端到端测试只告诉你"错了"，不告诉你"错在哪"

| 测试 | 失败时的信息量 |
|---|---|
| `test_embedding` 等单元测试 | **就是这个模块错了** |
| `test_transformer_lm` | 整条链某处不对（4 层 + 7 种组件） |

⇒ **排查顺序应沿着"已通过的单元测试"向"没被单独测过的部分"收敛**。到 LM 这一步，没被单独测过的只剩组装逻辑本身（顺序、`ln_final`、`lm_head`）。

端到端的容差也被放宽了：`atol=1e-4, rtol=1e-2`，而单元测试是 `1e-5`。**误差在层间累积是正常的**，不是谁写错了。

`test_transformer_lm_truncated_input` 单独值得看：输入截半，但 `context_length` 仍传完整值 ⇒ 测的是 **`seq_len < context_length` 时对不对**。因为 mask 按 `x.shape[-2]` 现造、位置按 `arange(seq_len)` 生成，这道测试是**免费过的**。若当初选了"`__init__` 按 `max_seq_len` 预建 mask"，这里就必须记得切片。

#### 一次重构：把 mask 和 positions 提到顶层

`mask` 和 `token_positions` **只依赖 `seq_len`**，对整个模型是同一份，却原本被放在最内层的 MHA 里算 ⇒ $L$ 层重复 $L$ 遍。于是把构造上提到 `TransformerLM.forward`，逐层透传。

方向是对的（HF / Llama 就是这么做的），但**代价必须记清楚**：

| | 消除的 | 制造的 |
|---|---|---|
| 重复 | $L$ 次**运行时**执行 | **4 份源码副本**（3 个适配器 + LM） |
| 安全性 | — | **MHA 不再自带因果性** |

第二行是重点：MHA 的 `mask` 仍然是 `= None` 的可选参数，而 `mask=None` 时 SDPA 走**全双向注意力**。也就是说，**我们在 §3.12 花力气消灭的最高危故障模式（因果性泄漏）被换了个形式放回来了**——现在它不再是"传了 mask 就失去因果性"，而是"不传 mask 就没有因果性"。

**两全的改法**：把 MHA 的 `mask` 变成**必填参数**（去掉默认值）。忘了传是 `TypeError`，不是信息泄漏。顶层构建一次的收益保留，静默路径关闭。

**规模判据**（§2.7 教训 1 的复现）：

| 配置 | 每次前向的 mask 分配 |
|---|---|
| $L{=}4$、seq$=256$（本作业） | $4\times 64$ KB —— **收益无法测量** |
| $L{=}32$、seq$=8192$ | $32\times 64$ MiB = **2 GiB 分配 churn** |

⇒ 这是一个**在当前规模上收益为零、但在生产规模上确实重要**的优化。做它没错，但要清楚**它此刻不是被测量证实的**，而且换来了一条真实的安全性倒退。

> 还有一条：适配器里现在出现了逻辑（三处复制的 `tril`）。按 §3.3 记的那条原则——**"适配器里出现的每一点逻辑，都说明模块本该提供而没提供"**——这正是"MHA 该自带因果性却不再自带"的信号。原则先于结论：绿灯没有推翻它。

#### 一条工作方式上的记录

这一节的多数结论来自**先跑测试、再读代码**，而不是采信任何一方的报告。实际发生过的偏差：

- 另一个 AI 报告 "5 passed"（那是 `-k "multihead or transformer"` 的子集），全量是 13 passed
- 同一份报告称重构后的结构"无懈可击"，而它引入的正是上面那条因果性倒退
- 更早还有两处硬错误：称"多头带来沉重 KV cache"（实测单头与 32 头**同为 4.29 GB**，§3.12）、称多头把大矩阵"切碎"（投影仍是三次完整大 GEMM）

**绿灯 + 自信的措辞 ≠ 正确。** 这和 §2.9 记的"绿灯不等于证明"是同一条，只是这次的绿灯来自别人。

### 3.14 资源盘点：参数量与 FLOPs（handout transformer_accounting）

#### 两条法则

```
① 矩阵乘：A(m×n) @ B(n×p)  =>  2*m*n*p  FLOPs
   (每个输出元素是一次长度 n 的点积 = n 乘 + n 加)

② 由 ① 推出的捷径：
   x[T,d_in] @ W[d_in,d_out] = 2*T*(d_in*d_out) = 2 * token数 * 参数量

   物理意义：每个 token 过一遍这个矩阵，每个参数被用一次(1乘+1加)
   => 数完参数量就等于数完了 FLOPs，不必重新列矩阵
```

符号：`V` 词表、`d` d_model、`d_ff`、`L` 层数、`T` 序列长度（= 一次 forward 里的 token 数）。

> `T` 和 `d` 是**正交的两个方向**：`T` 是"有多少个 token"，`d` 是"每个 token 多宽"。整张表里只有 `Q@K^T` 和 `scores@V` 让 `T` 出现两次——**那是 $T^2$ 的唯一来源**。

#### (a) 参数量与显存

|---|---|---|---|---|
| token_embeddings | `V*d` | 80,411,200 | 321.6 MB | 4.90% |
| q/k/v/output_proj | `4*d^2` ×L | 491,520,000 | 1,966.1 MB | 29.96% |
| w1/w2/w3 | `3*d*d_ff` ×L | 987,955,200 | 3,951.8 MB | 60.22% |

```
N_params = 1.64 B          fp32 权重 = 6,561.8 MB  (6.56 GB)

```

⇒ **参数量里 `V*d` 算两份，FLOPs 里只算一份。** 这个不对称在 (d) 里是关键。

#### 化简成一行（(c)(d)(e) 全靠它）

```
N_params ≈  2*V*d  +  12*L*d^2

FLOPs    ≈  2*T*( V*d + 12*L*d^2 )  +  4*L*T^2*d
            \____________________/     \_________/
             A 类 激活×权重             B 类 激活×激活
             有参数,  线性于 T           无参数,  平方于 T
```

对照精确值：3.185 + 0.322 = 3.507 TFLOPs vs 3.517 TFLOPs，差 0.3%（因为 `d_ff=4288` 不是精确的 `(8/3)*1600=4266.7`）。

#### 三个值得单独记的结构

**① `8/3` 是从哪来的**

```
经典 FFN (ReLU, 2 矩阵, d_ff=4d) :  d*4d + 4d*d    = 8*d^2
SwiGLU   (3 矩阵, d_ff=(8/3)d)   :  3*d*(8/3)d     = 8*d^2
```

**完全相等。** SwiGLU 比经典 FFN 多一个矩阵，把系数从 `4` 降到 `8/3` 正是为了让参数量持平——这样和旧模型比才公平。handout 那句 "nearest multiple of 64 to (8/3)·1600" 就是这么来的。

于是每层 `4*d^2`(attn) + `8*d^2`(ffn) = **`12*d^2`**，**这个 `12*L*d^2` 对用不用 SwiGLU 都成立**，值得背下来。

**② FFN 的参数和算力都是注意力投影的两倍**

`8d^2` vs `4d^2`，2:1。这个比例贯穿整张表。（经典 Transformer 是 `12d^2` vs `4d^2` = 3:1。）

**③ 头数在 `Q@K^T` 里被消掉**

```
单头   :  2*T^2*d_k
h 个头 :  h * 2*T^2*d_k = 2*T^2*(h*d_k) = 2*T^2*d
```

因为 `h*d_k = d_model` 恒成立。**和 §3.12 里 KV cache 与头数无关是同一个原因**——凡是"每头一份、再加起来"的量，都和 `h` 无关。

#### 四大块的占比（GPT-2 XL, T=1024）

| 块 | 符号 | TFLOPs | 占比 |
|---|---|---|---|
| **FFN** | `2*T*8*L*d^2` | **2.023** | **57.5%** |
| Attention 投影 (QKVO) | `2*T*4*L*d^2` | 1.007 | 28.6% |
| Attention 打分 (QK^T, AV) | `4*L*T^2*d` | 0.322 | 9.2% |
| lm_head | `2*T*d*V` | 0.165 | 4.7% |

**(c) 的答案在这张表里，而且它是反直觉的**：最贵的是 **FFN（57.5%）**，不是注意力。而"真正的注意力计算"（那两次激活×激活）**只占 9.2%**——在 `T=1024` 这个长度上，Transformer 主要是一台矩阵乘机器，注意力只是配角。

> 这也解释了为什么 MoE 首先动的是 FFN 而不是注意力：那里才是 FLOPs 的大头。

#### Arithmetic intensity：FLOPs 占比 ≠ 时间占比

上面那张表**只回答了"算多少"，没回答"要多久"**。两者不等价，因为 GPU 可能卡在搬数据上而不是算数上。

```
Arithmetic Intensity (AI) = FLOPs / 从 HBM 搬运的字节数   [FLOP/byte]

Roofline:  AI > 机器平衡点  =>  compute-bound  (算力吃满，搬运不是瓶颈)
           AI < 机器平衡点  =>  memory-bound   (算力闲着等数据)

机器平衡点 = 峰值算力 / 显存带宽
  A100 :  312 TFLOP/s (bf16) / 2.03 TB/s  ≈ 154 FLOP/byte
  H100 :  989 TFLOP/s (bf16) / 3.35 TB/s  ≈ 295 FLOP/byte
```

把表里三类操作各自算一遍（bf16，2 字节/元素；假设每个张量只过一次 HBM）：

| 操作 | FLOPs | HBM 字节 | AI 公式 | AI @ XL, T=1024 | A100 判定 |
|---|---|---|---|---|---|
| 投影 `x@W` | `2Td^2` | `2(2Td + d^2)` | `Td/(2T+d)` | **449** | compute-bound |
| FFN `x@W1` | `2Td·d_ff` | `2(Td + d·d_ff + T·d_ff)` | `Td·d_ff/(Td+d·d_ff+T·d_ff)` | **545** | compute-bound |
| 打分 `Q@K^T` | `2T^2 d` | `2(2Td + hT^2)` | `Td/(2d + hT)` | **57** | **memory-bound** |

**结论和 FLOPs 表正好相反的地方：**

- FLOPs 上，注意力打分只占 **9.2%**，看着无关紧要
- AI 上，它是**唯一一个掉到平衡点以下的**（57 < 154），也就是**唯一一个在等数据而不是在算**的部分

⇒ **它占用的墙钟时间远超 9.2%。** 这就是 FlashAttention 存在的定量理由：它不减少 FLOPs（一个都不减），它减少的是**那个 `[h,T,T]` 中间张量的 HBM 往返**。

原因在字节数那一列：`Q@K^T` 要写出的 scores 是 `h*T^2 = 25 × 1024² = 2621 万`个元素，而它读进去的 Q 只有 `T*d = 164 万`——**输出比输入大 16 倍**。这正是 §3.12 那条"打分矩阵是 h 倍大"的代价，在 roofline 上的显形。

> 上表还**低估**了问题：朴素实现要把 scores 写出去、读回来做 softmax、再写出去、再读进来做 `@V`，是 4 趟 HBM 往返，实际 AI 比 57 还低。FlashAttention 把这些合并在 SRAM 里做，一趟都不写。

**同一个 T=1024 的矩阵，换个场景就翻转：**

```
训练 / prefill (T=1024) :  AI = Td/(2T+d) = 449   => compute-bound
推理 decode  (T=1)      :  AI = 1·d/(2+d) ≈ 1.0   => 极度 memory-bound
```

**同一份权重、同一个 kernel，只因为一次处理的 token 数从 1024 变成 1，就从算力受限变成带宽受限。** 这是自回归生成慢的根本原因，也是推理必须攒 batch、以及 KV cache（§3.12）成为核心瓶颈的原因。

> **和 §3.12 那条 roofline 判据的对照**：那里说"两个方案 FLOPs/参数量完全相同时，compute/memory 的论证无法区分它们"——那是**误用**（单头 vs 多头）。这里是**正用**：FFN 和注意力打分的 FLOPs 不同、AI 也不同，roofline 确实能区分。
> **同一个工具，区别在于被比较的两者在相关量上是否真的有差异。**

一次 forward 的 FLOPs 与四块占比：

| 模型 | 总 TFLOPs | attn 投影 | attn 打分 | FFN | lm_head |
|---|---|---|---|---|---|
| small | 0.292 | 0.058 (19.9%) | 0.039 (**13.3%**) | 0.116 (39.8%) | 0.079 (**27.1%**) |

**四条趋势，全部由次方决定**（`T` 固定，看对 `d` 的次方）：

```
attn 投影 :  8*T*d^2 * L    -> d 的 2 次方        占比 涨   19.9% -> 28.6%
FFN       :  6*T*d*d_ff * L -> d 的 2 次方        占比 涨   39.8% -> 57.5%
attn 打分 :  4*T^2*d * L    -> d 的 1 次方        占比 跌   13.3% ->  9.2%
lm_head   :  2*T*d*V        -> d 的 1 次方, 无 L  占比 崩   27.1% ->  4.7%
```

- **`lm_head` 塌得最狠（÷5.8）**：分子只有 `V*d`，而 `V=50,257` 是**固定**的，只随 `d` 线性增长；分母的主体 `12*L*d^2` 却是 `L` 和 `d^2` 一起涨。小模型里输出层是四分之一的算力，到 XL 只剩二十分之一。
- **`attn 打分` 缓跌**：它只有 `d` 的一次方，追不上 `d^2` 的两项。
- ⇒ 模型越大，**Transformer 越是"一台大矩阵乘机器"**，输出层和注意力打分都被稀释。

**一个与 `L` 无关的不变量**（这条比上面四行更有用）：

```
打分 / 投影 = 4*L*T^2*d / (8*L*T*d^2) = T / (2*d)

small  : 1024/1536 = 0.667   实测 13.25/19.88 = 0.667  ✓
XL     : 1024/3200 = 0.320   实测  9.16/28.62 = 0.320  ✓
```

**层数完全约掉了。** 注意力打分相对于其余部分的分量，**唯一的自变量是 `T/d`**，和模型有多少层无关。

#### (e) XL 把上下文拉到 16,384

`T: 1024 → 16,384` 是 ×16。但两类项吃到的倍数不同：

| 块 | 关于 T | 倍数 | T=1024 | **T=16,384** |
|---|---|---|---|---|
| attn 投影 | `∝T` | ×16 | 1.007 (28.6%) | 16.106 (12.1%) |
| FFN | `∝T` | ×16 | 2.023 (57.5%) | 32.373 (24.2%) |
| lm_head | `∝T` | ×16 | 0.165 (4.7%) | 2.635 (2.0%) |
| **attn 打分** | **`∝T^2`** | **×256** | 0.322 (9.2%) | **82.463 (61.7%)** |
| **总计** | | **×38.0** | **3.517** | **133.578** |

```
总 FLOPs:  3.517 -> 133.578 TFLOPs   =  ×37.98    (不是 ×16)
attn 打分占比:  9.2%  ->  61.7%      =  从配角变成主角
```

用不变量核对：`T/(2d) = 16384/3200 = 5.12`，而 `61.7% / 12.1% = 5.12` ✓

**交叉点**（线性项 = 平方项）：

```
2*T*(V*d + 12*L*d^2) = 4*L*T^2*d
=>  T* = V/(2L) + 6*d  ≈  6 * d_model     (V/(2L) 通常很小)

GPT-2 XL    d=1600  =>  T* ≈ 10,100
Llama-3-8B  d=4096  =>  T* ≈ 26,600
```

⇒ **上下文长度超过约 `6·d_model` 时，注意力的平方项压过整个模型的其余部分。** Llama-3 用 8K 训练还稳在线性区；同一份权重跑 128K 就深在平方区。**同一个模型，只因上下文长度不同，瓶颈就换了部件。**

> `T*` 里**没有 `L`**——线性项的 `12*L*d^2` 和平方项的 `4*L*T^2*d` 都带 `L`，约掉了。这和上面那个 `T/(2d)` 不变量是同一件事。

**再看一眼 arithmetic intensity**（上一节的公式）：

```
Q@K^T 的 AI = T*d/(2*d + h*T)

T=1024   : 1,638,400 / 28,800  = 56.9  FLOP/byte
T=16384  : 26,214,400 / 412,800 = 63.5  FLOP/byte
T->inf   : -> d/h = d_k = 64
```

**AI 略微上升，但渐近到 `d_k = 64` 就封顶了**，永远追不上 A100 的平衡点 154。

⇒ 长上下文是**双重打击**：打分既吃掉 61.7% 的 FLOPs（(e) 的结论），又**始终是唯一 memory-bound 的部分**（AI 那节的结论）。**这两条是独立的论证，合起来才是 FlashAttention 的完整动机。**

### 3.15 阶段性小结

**§3 全部完成**：Linear、Embedding、RMSNorm、SwiGLU、RoPE、Softmax、SDPA、MultiHeadSelfAttention、TransformerBlock、TransformerLM。`pytest tests/test_model.py` 13 passed。
**下一步**：§4 cross-entropy 与 AdamW。

从这些小题里提炼出的方法论，后面继续用：

1. **命名先行。** 模块树的属性名必须和参考实现的 state_dict 对齐。这是一个成本单调递增的决定：现在改是零成本，越晚改越贵。
2. **让错误尽早、尽响地暴露。** 用契约（签名给的维度）而不是数据（`weights.shape`）去构造模块；保持 `strict=True`；device 和 dtype 在构造时对齐。**响的错误比哑的错误便宜一个数量级。**
3. **测试覆盖不到的地方要自己兜**：初始化、device/dtype 一致性、数学不变量。这是 §2.9"绿灯不等于证明"在这一章的延续。
4. **形状断言优先于打印。** 断言让 bug 在产生的地方就炸，而不是三层之后。
5. **toy 尺寸手算。** 抽象规则看不懂的时候，造一个小到能手算的例子跑一遍（§3.6 那张 4×3 的表就是这么来的），比看十遍解释管用。
6. **"恰好对"不是"真的对"。** 已经出现三次：`v.shape[-1]` 在 $d_k=d_v$ 时对（§3.11 坑 1）、RoPE 的 positions 在测试传 `[1,seq]` 时对（§3.12）、`finfo.min` 被 $\sqrt{d_k}$ 除完仍够负。**理由错的代码会在假设变化时静默失效**，而不是报错。
7. **分层要守住**：底层组件只承诺自己那层的语义，不假设调用方怎么组织数据（RoPE 不进 SDPA、`...` 泛化前导维度让 MHA 免费复用）。反过来，**约束也要写在制造它的那一层**——head 维引起的广播风险属于 MHA，不属于 RoPE。
8. **警惕"贴心的容错"。** `if x is None: 跳过` 这类降级路径，单看都像健壮性，合起来是一张让错误安静穿过的网（§3.12 那六个静默失败里占了五个）。**缺省应该是"补全"而不是"跳过"**，补不出来就报错。
9. **让运算符替你检查类型。** `&` / `~` 不接受 float，`*` / `== False` 接受——选前者等于免费拿到一层防护，比"记得检查 dtype"可靠。
10. **优化把责任往上移时，要同时把契约收紧。** 把 mask 提到顶层构建（§3.13）省掉了 $L$ 次重复，但只要下层参数仍是可选的，就等于开了一条静默路径。**责任上移 ⇒ 下层的参数必须变必填**，否则收益是真的、倒退也是真的。
11. **绿灯不等于正确，别人的绿灯尤其。** 报告可能只跑了子集、可能对自己引入的倒退无感。**先跑全量测试、再读代码**，然后才轮到看结论。
12. **FLOPs 占比不等于时间占比。** 数完 FLOPs 只答了"算多少"，要答"要多久"必须再算一次 arithmetic intensity（§3.14）。注意力打分在 FLOPs 上只占 9.2%，在 roofline 上却是唯一 memory-bound 的部分——**优化目标应该由后者决定，不是前者。**
